## PART 1: THE VISION

### What We're Building

NayaNET is a new internet. Not a website. Not a platform. A **living world** where every person, business, and community gets a Smart App — a complete, intelligent, beautiful interface they run their whole world on.

The Smart Factory is how we build it. Not by hand-coding each app. Not by designing from scratch. By **assembling** from elite parts, in minutes, at 10-star quality, every time.

### The Mercedes Principle

Mercedes doesn't build each car from raw steel. They have:
- **Elite parts** — engines, transmissions, chassis — engineered once, perfected, then reused
- **Organized inventory** — every part catalogued, tested, ready
- **Assembly line** — skilled workers assemble in hours, not months
- **Quality gates** — nothing ships unless it's Mercedes-level

We are the Mercedes of smart apps. Our parts are interface components. Our factory is the assembly system. Our quality gate is the 10-star standard.

### The 3-Minute Promise

A complete Smart App page — Recipe + Parts + Shell + Data + Gate — assembled in 3 minutes. Not 3 hours. Not 3 days. **3 minutes.**

This is possible because:
1. The parts already exist (blessed, tested, 10-star)
2. The recipe defines exactly which parts and how they connect
3. The shell provides the structure
4. The data plugs in live
5. The gate verifies before it ships

### The Harvest Law Extends — The Eight Objects (Naya Code, 2026-11-17)

The Factory does not invent buttons, boards, or icons. It takes the eight Naya Code objects and recombines them — **board, pill button, tile, icon, digit tile, chip/tab, face circle, gauge/dial** — giving each its own color and its own word, the way the Code says. Every one of them is harvested verbatim from the three reference objects — **the top-left +** (the button), **the Smart Note board** (the board and the black), **the X button** (the inside) — measured against them by eye, never reinvented, never approximated. A new object is right when, held next to those three, it speaks the same language; the maker names which reference object it was measured against, never assumes it.

Two rules from the Code are build law, and the gate enforces them:

- **The orbit rule.** Every circle carries flow — one or more rings, or an orb, circling around it, slow (ambient 60–180s, concentric sets alternating direction, never frantic). The circling is what makes circles feel alive. A circle without flow is unfinished.
- **The alive rule.** Every board lights up whole on hover — it lifts, the outside light ignites in its own color, the white in the middle pops. A board or button that does nothing on hover is dead, and **dead on hover is a defect**, whatever else it does. The checker names the dead ones; the maker brings them alive.

### The Interface Framework (Summary)

The complete framework lives at `~/workspace/team-nitro/NAYA-INTERFACE-FRAMEWORK-V1.md`. The essence:

**Every screen is ONE viewport, ONE complete thought.** It answers in 2 seconds:
- What am I looking at?
- What can I do here?
- Why am I here?

**Four layers, never five:**
1. **Hero** (1 only) — The most important thing. 48-72px. Center zone.
2. **Supporting** (max 3) — Context. Smaller. Below or beside hero.
3. **Actions** (max 2, min 1) — What the user can do. Always visible.
4. **Ambient** — Status, metadata. Edges. Never competes.

**Spacing:** ONLY 4, 8, 12, 16, 24, 32, 48, 64, 96. No other numbers.

**Color:**
- Gold #ffbf3d = score/value (identity)
- Green #2fe89e = positive/live (semantic)
- Red #ff5e6c = negative/urgent (semantic)
- Purple #a06bff = identity
- Blue #3fb8ff = info
- Identity colors the THING. Semantic colors the CHANGE.

**Typography:** Max 3 sizes per screen. Display/Hero, Headline, Body/Caption.

**The 10-Step Build Process:**
1. Name the job (what does this screen DO?)
2. Choose the hero (what's the ONE thing?)
3. Place the hero (center zone, 48px+)
4. Add supporting (max 3, earn their place)
5. Add actions (1-2, always visible)
6. Fit check (does it fit the viewport? no scroll?)
7. Hierarchy check (hero dominates? layers clear?)
8. Beauty check (alive? depth? ignites on touch?)
9. Verify (render it, phone + desktop, touch everything)
10. Ship (only if 9+ and "wowie")

### Shared Vocabulary

**Use these words:**
- "hero" — the main element
- "screen" — one viewport, one thought
- "dead space" — empty area that serves nothing
- "cut off" — content clipped by viewport
- "earns its place" — justifies its pixels
- "viewport fit" — complete in one screen
- "2-second test" — user understands in 2 seconds

**Never say:**
- "make it pop" (meaningless)
- "more modern" (subjective)
- "clean it up" (vague)

### The Philosophy (Part 0)

**10-star is HOLISTIC.** All dimensions at once — look, feel, vibe, logic, intelligence, effectiveness, usefulness, helpfulness. Any dimension below 10 → whole below 10.

**Alive, not dead.** Interfaces ignite on touch. They breathe. They respond. Dead = static, flat, lifeless.

**The Precious Data Principle.** A user's 225 isn't a number. It's their effort, their journey. We present it like the most precious data in the universe — because to them, it is. Every pixel is an act of respect.

## PART 4: THE RECIPE — How Apps Are Defined

### What Is a Recipe?

A recipe is a **complete definition** of a Smart App page. It specifies:
- **Purpose:** What job does this page do?
- **Audience:** Who uses it? (citizen, visitor, owner?)
- **Parts:** Which blessed parts, in what arrangement?
- **Data:** What live data feeds each part?
- **Flow:** Where does the user go next?
- **Bullseye:** What does 10/10 look like for this page?

### Recipe Format

```markdown
# RECIPE: [Page Name]
**Job:** [One sentence — what does this page DO?]
**Audience:** [Who uses this?]
**Bullseye:** [What does perfect look like?]

## Screen 1: [Name]
**Job:** [What does THIS screen do?]
**Hero:** [Part #] — [What it shows]
**Supporting:** [Part #], [Part #] (max 3)
**Actions:** [Part #] (1-2)
**Data:** [What live data feeds this?]
**Viewport:** [Fits 900px? Mobile 390px?]

## Screen 2: [Name]
...

## Flow
[Screen 1] → [Screen 2] → [Screen 3]
[What triggers each transition?]
```

### The Two Official Formats — How Every Page Is Presented

Every page the Factory builds is presented in one of the two official formats — the citizen's choice, never the Factory's:

- **The unfold (going down).** Press the button, the next piece unfolds down the page. One board at a time, one idea each, three sentences per board. The letter unfolds down; the deck's unfolding is the model.
- **The slideshow (going sideways).** Press Next, the next screen slides in. One screen at a time, one image or board, with Back and Next.

The choice is offered the bridge way: in-a-nutshell first, then *"which presentation do you want?"* — click a button, see one presentation; click the other, see the other. About and Skills each get both presentations and a bridge; the same for Business and Space, so the citizen gets to know all about it, with a presentation right on the page.

Both formats are ONE idea: **press the button, go to the next experience.** Press the button, go to the next block, the next image, the next board. It feels interactive because it IS interactive — and in their brain they take bits in at a time, instead of taking the whole web page or the whole book. Human psychology: they can only take in so much. Break up the colors, have the contrast, have the elevation, make it feel alive — and the experience is a whole lot better for them. Bits at a time, never a wall.

One canonical implementation each, harvested verbatim from the proven source, reused everywhere, never reinvented per page. The canonical bytes are wired into the builder in Phase 2, when the official-formats round lands them — this Blueprint names the formats as the law now; it does not invent their bytes.

### The Core Recipe — The Universal Page

The one page the Factory builds over and over is the **Universal Smart App — the Smart Feed page**. It automatically syncs up the content and the users, and presents in the universal format. It is the core recipe because it morphs into so many different pages: Personal, Business, Space, World, and every topic's smart app.

The morph rule, stated plainly: **one core page, a Rubik's Cube matrix that morphs into its faces.** Turn the cube and a different face comes forward, but it is the same cube, the same machine, auto-organizing itself around what matches — and every face speaks the same language. That is why this one page has to be near perfect: every page the Factory ever builds is a face of it. The Trinity is the Dashboard, the Hub, and this page — everything gets built off that.

## PART 5: THE ASSEMBLY — 3 Minutes to a Page

### The 5 Elements

Every page = **RECIPE + PARTS + SHELL + DATA + GATE**

1. **RECIPE** — The definition (written, reviewed, 10/10)
2. **PARTS** — Blessed components from the inventory
3. **SHELL** — The Two-Bar Frame (top nav + bottom nav + viewport)
4. **DATA** — Live connections (Supabase, APIs, ledger)
5. **GATE** — Verification before it ships

### The 3-Minute Clock

**Minute 1: Assemble**
- Pull the recipe
- Pull the parts from inventory
- Place them in the shell per the recipe

**Minute 2: Connect**
- Wire the data sources
- Verify live data flows
- Test interactions

**Minute 3: Gate**
- Run the Design Gate (19 checks)
- Render on phone + desktop
- Score against the bullseye
- Ship if 9+, fix if not

### Stage Progression

**Stage 0:** Page Zero — The landing. Proves the factory works.  
**Stage 1:** Close shelf gaps — Bless the missing parts in demand order.  
**Stage 2:** Three recipes first — Pricing, Dashboard, Chart. BUILD NOTHING until recipes are 10/10.  
**Stage 3:** One timed page — 3 minutes, 9+ score, or back with defect named.  
**Stage 4:** Batch 12/day — The factory at speed.  
**Stage 5:** Factory learns — Every build improves the system.

## PART 8: THE AUTOMATION — Scaling to an Army

### The Factory Is the System

The Smart Factory isn't a team. It's a **system** that any Naya can operate:

1. **Recipes** define what to build (any Naya can read a recipe)

3. **Framework** defines how (any Naya can follow the 10 steps)
4. **Gate** verifies quality (machine-checkable, not subjective)

**Day 1:** Read the Framework. Read the Design Contract. Study 3 blessed parts.  
**Day 2:** Assemble a practice page from a recipe. Score it. Fix defects.

1. **The page** (shipped, live, 10-star)

**See it, fix it, write it down, share it.** In the same pass. If it isn't documented, it isn't done.

### The 12/Day Throughput

With 3 builders × 4 pages/day = 12 pages/day.

Each page:
- Recipe exists (written beforehand)
- Parts are blessed (from inventory)
