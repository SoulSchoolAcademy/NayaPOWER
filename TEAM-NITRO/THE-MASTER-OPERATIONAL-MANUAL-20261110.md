## 3.1 GitHub — the memory and the build

**Subtitle:** File, read, branch, merge — merges are Shawn's hand.
**Nutshell:** Every deliverable goes into GitHub (SoulSchoolAcademy/NayaPOWER) — pages, freeze points, reports, rules, working files. A checkpoint is not real until it is in GitHub, read-back verified. Local files are the working copy.

- **File:** use `~/workspace/team-nitro/gh-direct.py` (it mints the app token in memory and calls the API directly, never touching the token cache). - **Read-back verify every filing:** GET the file back and check the blob sha and sha256 match the local file byte-for-byte. A filing is not real until it is read back.
- **Branch:** one change, one PR, one branch per task. The local clone is diverged — never push from it; file via the Contents API.

## 3.3 Cloudflare — the doors

**Title:** The doors: workers, domains, deploys — nothing counts as deployed until proven live from the URL.
**Subtitle:** The proven rules, learned the hard way, in the order that matters.
**Nutshell:** Byte counts and file writes are not proof. A deploy is proven when the live URL serves the new bytes — curled from outside, matched by sha256, seen at phone width and desktop, scroll 0 and scrolled.

- **The law:** nothing counts as deployed until it is proven live from the URL. The Cloudflare master owns the workers, the domains, the deploys, the live bytes. Daily: every domain live and answering, every deploy verified from the live URL, every worker healthy.
- **Worker PUT (proven 2026-11-06 and 2026-11-08):** the metadata part comes first (`Content-Disposition: form-data; name="metadata"`, `Content-Type: application/json`, `{"main_module":"worker.js","bindings":[...]}`), then the script part (`name="worker.js"; filename="worker.js"`, `Content-Type: application/javascript+module`). A PUT with metadata but script part `application/javascript` 400s with Cloudflare error 10021 — the API parses the script as a classic service worker unless the part carries `application/javascript+module`. A PUT to an EXISTING module worker may succeed without metadata (format preserved) — a NEW worker will not. Durable helper: `~/workspace/project-intelligence/cf-worker.py` (get-script / get-subdomain / get-bindings / put-script; uses the registered connection, never touches a raw token).
- **Bindings rule:** a PUT's metadata REPLACES the non-secret bindings — secret bindings survive omission (stored separately); plain_text/service bindings are REMOVED when omitted; a secret listed WITHOUT `text` is HTTP 400 (safe failure, no change). Re-declare every plain_text/service binding with its known value in the metadata, and OMIT secrets (never list them text-less).
- **Workers.dev route:** new workers uploaded via API have their `workers.dev` route DISABLED by default — every request 404s with body `error code: 1042`. Fix: `POST /accounts/{id}/workers/scripts/{name}/subdomain` with `{"enabled": true}` (PATCH is 405 on that endpoint). Always curl the workers.dev URL after a fresh worker PUT; deployed-bytes matching does NOT catch this.
- **Reading a module worker back:** the Cloudflare GET for a module worker returns a MULTIPART document, not a bare script — parse the `worker.js` part to get the true script (the envelope adds ~185B); compare scripts, not envelopes.
- **The 1010 rule:** requests from this VM with Python-urllib's default `User-Agent` to a `*.workers.dev` hostname get HTTP 403 `error code: 1010` ("banned based on browser signature"); the SAME request with a browser UA (or curl) returns 200. When a worker URL 403s from a python script but curls fine, set a browser `User-Agent` header before assuming the worker is broken.
- **The token-verify probe is broken, not the deploy path:** the token verify probe (`GET /user/tokens/verify`) 401s on this token while the Workers Scripts + KV APIs work fine.
- **How to deploy the Hub and prove it live (the procedure the test asks for):** deploy through the established deploy path above (worker PUT with metadata + module content-type; enable the workers.dev route if it is a fresh worker), then curl the live URL from outside the VM, compare the served bytes' sha256 to the filed blob, and check the rendered page at phone 390 and desktop 1440, scroll 0 and scrolled. ## 7.2 The Five Gates — before every consequential action

**Title:** Is it right? Is it what they truly need? Is it mine to do? Is now the time? Can I prove it?
**Subtitle:** All five yes — act fully, at full power, no hesitation. Any gate no — stop, say why, propose the wise path.
**Nutshell:** Just because you can doesn't mean you should. Capability never grants authority.

1. **Is it right?** Does this serve the good of everyone it touches? Check consequences for people, privacy, trust, safety, the long-term mission. Evidence of harm or a hard stop = do not proceed.
2. **Is it what they truly need?** What is the human's actual goal — beneath the words, beneath the urgency? If you are interpreting deeper intent, say so openly. Never silently replace their judgment with your own.
3. **Is it mine to do?** Do you have the authority? Check permission, ownership, scope, and every decision reserved for Shawn's hand. Being capable of an action never grants authority to take it.
4. **Is now the time?** Check readiness, dependencies, reversibility, opportunity cost. Move at nitro speed when the road is right. Do not turn judgment into delay — but never let urgency pick the road.
5. **Can I prove it?** Define what done looks like BEFORE you act. Then verify with evidence — live bytes, rendered pages, real measurements — never with claims. Receipt before report. If you can't prove it, don't claim it.

**Protected gates are always Shawn's hand:** money, credentials, destructive actions, security and privacy changes, anything leaving the business, ratification — and merges. Never merge your own PRs. The moment a PR is merge-ready, send him "Shawn, merge:" plus the link, no batching.
