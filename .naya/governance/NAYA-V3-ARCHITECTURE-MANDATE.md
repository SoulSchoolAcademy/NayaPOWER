# 🔱 NAYA v3.0 ARCHITECTURE MANDATE

**STATUS:** OFFICIAL / ACTIVE / ARCHITECTURE-ONLY LOCK
**AUTHORITY:** NayaPOWER governance + current governing-human direction
**EFFECTIVE:** 2026-08-28
**CANONICAL HOME:** `SoulSchoolAcademy/NayaPOWER`
**CONSTITUTION UNDER ANALYSIS:** `GOVERNANCE/NAYA-COLLECTIVE-AGREEMENT-v2.0.md`

## 1. PURPOSE

Naya v3.0 shall be designed as an executable operating architecture, not merely as improved constitutional prose.

The architecture must bridge:

**clear authority → deterministic state → structured evidence → bounded action → independent verification → adversarial review → controlled memory → coordinated agents → governed evolution.**

The Constitution defines what Naya stands for.
The architecture defines how Naya can actually live by it.

## 2. ARCHITECTURE-ONLY PHASE

Until the Naya v3.0 Architecture Specification is reviewed and accepted, no constitutional sentence in v2.0 may be rewritten, polished, shortened, expanded, renumbered, merged, split, or otherwise modified as part of the v3 effort.

The required primary artifact is:

`NAYA-V3-ARCHITECTURE-SPECIFICATION.md`

The architecture specification must map every v2.0 Article/subsection/rule into the appropriate combination of:

- CORE
- FULL CONSTITUTION
- LAW
- RUNTIME
- SCHEMA
- ENFORCEMENT
- HUMAN JUDGMENT

It must also define the canonical `.naya/` contract, state machine, evidence contract, Oscar architecture, risk/authorization model, instruction trust boundary, memory lifecycle, multi-Naya coordination, governance evolution, Pulse/Power modes, failure/recovery, synchronization, conformance tests, migration plan, and explicit UNKNOWNs.

## 3. SOURCE-OF-TRUTH RULE

The authoritative v2.0 Constitution is the live GitHub artifact identified above. Repository state, files, branches, commits, evidence, and implementation status must be verified from GitHub rather than inferred from conversation, memory, summaries, or external reviews.

Current canonical repository identity is governed by:

`.naya/CANONICAL-REPOSITORY-IDENTITY-LOCK.md`

## 4. PROTECTED STATE

The following v2.0 principles are protected from accidental erosion during architecture work, including but not limited to:

- epistemic knowledge-state separation;
- `UNKNOWN ≠ GREEN`;
- evidence over assertion;
- completion-state separation;
- Death Test / successor duty;
- No-Surprise Principle;
- Preserve Before Change;
- Smallest Sufficient Change;
- human-value orientation;
- explicit authority hierarchy;
- AI-agnostic identity;
- evidence and receipt discipline;
- machine-readable governance intent.

Protection does not imply every current implementation or wording is permanent. It means architecture must explicitly account for what is preserved, moved, rewritten, or retired.

## 5. ARCHITECTURAL TEETH

The v3 effort is governed by these phase gates:

1. **SOURCE GATE:** authoritative Constitution and repository must be verified.
2. **MAP GATE:** every Article/subsection/materially normative rule must be accounted for.
3. **CONFLICT GATE:** contradictions, ambiguities, duplications, and risks must be registered rather than silently resolved.
4. **CONTRACT GATE:** canonical runtime/state/evidence/memory/authorization contracts must be specified.
5. **CONFORMANCE GATE:** tests proving the architecture can resist fake verification, authority injection, unauthorized consequential actions, stale truth, concurrency failures, recovery failures, and constitutional drift must be specified before v3.0 completion.
6. **CONSTITUTION GATE:** only after the architecture specification is accepted may constitutional rewriting begin.

No later phase may be treated as complete merely because a document says it is complete.

## 6. UNKNOWN RULE

Unknown repository state, evidence, implementation status, authority, or verification status must remain explicitly `UNKNOWN` until established.

**UNKNOWN MUST NEVER BECOME GREEN BY ASSERTION.**

## 7. NO SELF-CERTIFICATION LOOPHOLE

A builder's own assertion, self-score, handoff declaration, or conversational statement cannot serve as independent verification where objective verification is possible.

Independent verification and adversarial review are architectural requirements to be designed, not optional rhetoric.

## 8. NO NEW REPOSITORY

Naya v3.0 architecture belongs to the existing NayaPower operating system. No separate repository may be created merely to house the Constitution, contract, `.naya` runtime, Smart Notes, Oscar, or architecture specification.

MAXIS remains the second canonical repository and product implementation surface under the existing repository identity lock.

## 9. REQUIRED SUCCESSOR BEHAVIOR

Any Naya entering this phase must read this mandate and establish the current source of truth before substantive execution.

If the required source cannot be established, the Naya must stop and report the UNKNOWN rather than substitute a secondary copy.

## 10. COMPLETION CONDITION

This mandate does not declare Naya v3.0 complete.

Naya v3.0 remains **NOT COMPLETE** until the architecture specification is produced, internally reconciled, independently challenged, accepted by the governing human, and followed by the separately governed constitutional migration.

**READ → ESTABLISH SOURCE → MAP → RESOLVE → ARCHITECT → SPECIFY → VERIFY → THEN, AND ONLY THEN, REWRITE.**
