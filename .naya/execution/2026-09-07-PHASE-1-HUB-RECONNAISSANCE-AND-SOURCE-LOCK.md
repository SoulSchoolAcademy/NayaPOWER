## 1. NON-NEGOTIABLE LAWS

### LAW 1 — NEVER DESTROY THE HOUSE TO RENOVATE ONE ROOM

The current Hub is an existing product with accumulated UX, architecture, behavior, styling, state, and implementation intelligence.

Do not replace it with a simplified approximation.

Do not remove unrelated functionality.

Do not rebuild from memory.

Do not treat a large file as disposable merely because it is inconvenient to retrieve or edit.

### LAW 2 — SOURCE OF TRUTH FIRST

The authoritative working source designated for this phase is:

`NAYANETHUBONE.html`

### LAW 3 — FAITHFUL RECONSTRUCTION IS PERMITTED

If the available editing/retrieval interface cannot safely expose or modify the complete large source in one operation, reconstruct it in validated batches from the actual source.

Reconstruction means preservation, not approximation.

Every batch must be accounted for. No missing source may be silently invented.

### LAW 4 — IMPROVEMENT MUST BE REAL

Phase 1 does not redesign the product.

Later phases may improve existing UX/design when the result is demonstrably better. "Different" is not sufficient.

### LAW 5 — ONE SYSTEM, NOT COMPETING SYSTEMS

Do not create a second Hub, second Smart Note feed, second event model, second renderer, second storage model, or second deployment authority to avoid understanding the existing one.

### LAW 6 — NO CLAIM WITHOUT EVIDENCE

Distinguish:

`DOCUMENTED`
`OBSERVED`
`IMPLEMENTED`
`BUILT`
`DEPLOYED`
`RUNTIME-OBSERVED`
`VERIFIED`
`UNKNOWN`

A repository file or commit is not proof of live runtime behavior.

### LAW 7 — NO PROBLEM WITHOUT A SOLUTION PATH

If the intended route fails:

`STOP → INSPECT → DIAGNOSE → SEARCH KNOWN SOLUTIONS → CHANGE ROUTE → VERIFY → RECORD LEARNING → CONTINUE`

Never return the obstacle to Shawn without first exhausting reasonable supported alternatives.

### LAW 8 — DO NOT REPEAT A KNOWN BLOCKER

Search the NayaPOWER intelligence trail for existing laws, notes, activity, protocols, validators, and prior solutions before escalating or retrying a known failure mode.

## 4. REQUIRED RECONSTRUCTION METHOD

If the source must be reconstructed to permit safe editing later:

### Step 1 — Establish exact source identity

Record:

- branch
- commit
- blob SHA
- byte size
- line count if obtainable
- SHA-256 if obtainable
- HTML boundary count

### Step 2 — Partition the source

Create a logical map of the complete file, such as:

1. document/head
2. CSS foundation
3. shell/navigation
4. home/dashboard
5. Smart Note / Intelligence Feed
6. Activity/Now
7. reports
8. spaces/lists
9. mail
10. settings/profile
11. data/state
12. renderers
13. event handlers
14. initialization
15. closing document/runtime

The actual partitions must follow the real source. Do not force this example structure if the source differs.

### Step 3 — Retrieve each batch from the real source

Every batch must have a source range or other verifiable identity.

Never fill a missing region with guessed code.

### Step 4 — Reassemble only after coverage is proven

Before using a reconstructed copy for editing, verify that every source region is represented exactly once and that no region is missing or duplicated.

### Step 5 — Compare reconstructed identity

Where technically possible, compare byte count/hash or equivalent structural fingerprints against the source.

If exact byte parity cannot be established because of tooling limitations, do not pretend it was established. Record the limitation and use stronger structural verification instead.

### Step 6 — Freeze the baseline

The reconstructed/baselined representation becomes a working reference only. The original repository source remains authoritative.
