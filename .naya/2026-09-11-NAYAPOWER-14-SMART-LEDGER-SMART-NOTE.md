## 1. IN A NUTSHELL

Smart Ledger is NayaNET's evidence and integrity layer: a durable, timestamped record of meaningful actions and system events going into and out of NayaNET.

It is conceptually similar to some useful properties people associate with blockchain systems—timestamped events, chained history, integrity protection, verification, and durable lineage—but Smart Ledger is **not blockchain technology** and NayaNET is not attempting to create a blockchain.

The intended technology is **Collective Chain Technology (CCT)**: a purpose-built system using logic, mathematics, code, evidence, verification, provenance, and chained intelligence events to create a trustworthy collective intelligence network.

A simple way to understand it is:

`ACTION → SMART LEDGER → VERIFICATION → VALUE → POINTS → LEVEL → COLLECTIVE INTELLIGENCE`

Smart Ledger records what happened. Collective Chain Technology connects verified events and intelligence so the network can remember, learn, verify, and compound value.

## 2. HUMAN

Think of Smart Ledger as NayaNET's trustworthy receipt book.

When something meaningful happens—a Smart Note is created, someone shares useful intelligence, a contribution becomes collective wisdom, an outcome is verified—the system records that event.

- What happened?
- When did it happen?
- What system event occurred?

## 15. APPEND-ONLY / IMMUTABILITY PRINCIPLE

Smart Ledger should be **append-only and tamper-evident by design**, rather than relying on destructive editing of historical events.

If an earlier event needs correction:

`ORIGINAL EVENT → NEW CORRECTIVE EVENT → SUPERSEDES / QUALIFIES ORIGINAL`

The historical event should remain part of lineage where privacy, legal, and system requirements permit.

"Immutable" therefore means preservation of trustworthy historical lineage—not a promise that no data can ever be removed for privacy, legal, security, or operational reasons.

Any deletion/redaction policy must preserve integrity of the remaining chain and be separately specified.

## 16. PRIVATE PROVENANCE / PUBLIC PRIVACY

Smart Ledger may need to know internally where an event came from so the system can verify, audit, deduplicate, calculate, and protect the network.

That does **not** mean public users should see the underlying private provenance.

Canonical rule:

**INTERNAL PROVENANCE MAY EXIST WITHOUT PUBLIC ATTRIBUTION.**

The system must minimize exposed identity and sensitive source details.

This aligns with the Collective Intelligence Event requirement that collective objects do not expose contributor identity or raw private source material. See `SUPERBRAIN/COLLECTIVE-INTELLIGENCE-EVENT-SCHEMA.md`.

## 21. NEGATIVE VALUE AND THE ZERO FLOOR

The Ledger must record negative-value events when legitimate system evaluation determines that an action was unproductive or detrimental.

Examples may include:

- spam-like behavior;
- repeated low-value flooding;
- deliberately disruptive participation;
- manipulation of contribution metrics;
- other verified negative network impact.

Negative value is applied to the event/value layer.

**V1 member point balance does not display below zero.**

`DISPLAYED_POINTS = MAX(0, CALCULATED_CUMULATIVE_POINTS)`

This prevents the profile from becoming a punitive debt meter while still allowing the system to record negative behavior and use it for future scoring, rate limits, moderation, trust, eligibility, or remediation.

## 24. ANTI-GAMING / ANTI-GOODHARTING

The system must never confuse activity with value.

Therefore:

- a Like can be recorded without being worth more than its defined value;
- many comments do not automatically beat one exceptional contribution;
- repeated low-value actions can receive zero or negative value;
- reciprocal/farmed engagement must not generate unlimited value;
- duplicate collective wisdom must not generate duplicate collective learning events;
- downstream verified outcomes can be worth more than the initial activity that produced them;
- scoring rules must be auditable and explainable at the appropriate level;
- historical evidence remains independent of the scoring formula;
- the Value Engine can improve while the Ledger remains intact.

The objective is to reward **meaningful verified contribution**, not manipulation of the scoring mechanism.

## 30. VERIFICATION CONTRACT

A Ledger event can have states such as:

`RECORDED → EVIDENCE_AVAILABLE → VERIFIED → VALUED → APPLIED → OUTCOME_VERIFIED`

Not every event reaches every state.

The system must never imply that:

- recorded = verified;
- verified = valuable;
- valuable = correct forever;
- published = validated;
- repeated = true.

Where evidence changes, later events should qualify or supersede earlier conclusions.
