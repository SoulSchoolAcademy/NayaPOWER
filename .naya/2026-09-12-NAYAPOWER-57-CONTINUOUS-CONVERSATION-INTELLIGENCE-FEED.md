## 1. PURPOSE

Naya conversations are intelligence events, not disposable chat history.

When consequential work occurs in a Naya conversation, the resulting intelligence must be distilled into a timestamped Smart Note / project-state event so that other Nayas, systems, and future sessions can understand what changed without requiring Shawn to repeat the conversation.

The system therefore maintains a continuously evolving intelligence record:

CONVERSATION → DISTILL → SMART NOTE → PROJECT STATE → NOTIFICATION / ACTIVITY → RETRIEVAL → CONTINUATION

## 2. PRODUCT JOB

The feed exists to eliminate context fragmentation between Nayas and sessions.

A future Naya should be able to answer:

- What project are we working on?
- What is the current mission?
- What did Shawn just decide?
- What changed from the previous state?
- What is protected?
- What has been completed?
- What remains unknown or blocked?
- What is the single highest-value next action?
- Where is the evidence?

without asking Shawn to reconstruct prior conversations when the repository or intelligence system already contains the answer.

## 3. CANONICAL EVENT

Each consequential conversation turn produces, when material, a distilled intelligence event containing at minimum:

- timestamp;
- project / scope;
- human intent or decision;
- Naya interpretation;
- decisions made;
- work completed;
- evidence / references;
- protected baseline;
- unknowns / blockers;
- lessons;
- changed state;
- next action;
- execution continuation;
- provenance to the originating conversation/event where technically available.

## 7. FEED MODEL

### Activity Feed

A living operational stream of what is happening in the user's Smart Brain / Naya environment.

### Personal Intelligence Feed

Private-by-default intelligence owned by the user, including distilled Smart Notes and relevant PIS intelligence.

### Collective Intelligence Feed

Public/shared intelligence explicitly authorized for publication, discoverable according to publication/privacy rules.

The three feeds share a common event/intelligence foundation but have different authorization and projection rules.

## 8. DISTILLATION LAW

Do not dump raw conversation transcripts into the intelligence feed by default.

Distill the consequential intelligence.

Preserve enough provenance and evidence to recover the source when necessary.

A useful Smart Note answers:

WHAT HAPPENED → WHAT MATTERS → WHAT CHANGED → WHAT IS PROTECTED → WHAT IS NEXT

## 9. TIMESTAMP / EVOLUTION LAW

Every material state change is timestamped.

The feed is append-oriented and evolutionary. New intelligence updates the current project understanding; it does not erase useful history.

When two artifacts conflict, resolve by evidence, explicit human authority, and current timestamp/context. Do not treat an older artifact as current merely because it exists.

## 10. PROTECTION LAW

The system must never destroy a valuable current baseline merely to make an improvement easier.

Use:

UNDERSTAND → PRESERVE → RECONSTRUCT → IMPROVE → VERIFY

When a new implementation is materially better, retain the prior artifact as reference/history unless there is strong evidence that deletion is safe and explicitly authorized.

## 11. EFFICIENCY / EFFECTIVENESS LAW

Every implementation decision balances:

VALUE × QUALITY × VERIFIABILITY × CONTINUITY

against:

TIME × ENERGY × COMPLEXITY × RISK

The objective is not maximum code churn. It is maximum verified progress toward the finished product.

If surgical evolution preserves more working value with less risk, use it.

If the existing implementation has become structurally misleading or costly to repair, reconstruct from the strongest current reference while preserving the reference and extracting its lessons.
