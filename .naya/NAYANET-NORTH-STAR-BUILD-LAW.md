# 🔱☀️ NAYANET — NORTH-STAR BUILD LAW

**Status:** CANONICAL
**Authority:** NayaNET Product / Build Governance
**Effective:** 2026-09-02
**Scope:** Every NayaNET build, redesign, implementation, refactor decision, deployment decision, and AI-builder execution

## 1. PRIME LAW

> **NAYANET IS NOT A REFACTOR. NAYANET IS A NORTH-STAR BUILD.**

NayaNET must be built from the intended product experience backward — not from the limitations, structure, compromises, or historical decisions of an existing application forward.

The question is never merely:

> “How do we make the existing Hub better?”

The governing question is:

> **“If NayaNET did not exist yet, and we were given this mission today, what would we build?”**

Then build that.

## 2. SOURCE-OF-TRUTH HIERARCHY

For NayaNET product and experience decisions, authority is ordered:

1. **NayaNET North Star / Product Vision** — what the experience must be.
2. **Locked Design + Product Laws** — how it must feel, behave, communicate, and function.
3. **Build Directives / Quality / QA Gates** — how it must be built and verified.
4. **Existing Repository** — what may be reused, learned from, salvaged, adapted, replaced, or deleted.
5. **Existing Deployed Application** — evidence only; never conceptual authority.

When lower-level evidence conflicts with higher-level product authority, the higher-level authority wins.

## 3. REPOSITORY NON-AUTHORITY LAW

The existing repository is an **asset library, archaeological record, and engineering substrate**.

It is not the conceptual constraint for NayaNET.

Existing code does not become authoritative merely because it is:

- already implemented;
- older;
- familiar;
- difficult to replace;
- previously approved;
- currently deployed; or
- the path of least resistance.

**“It already exists” is never, by itself, a reason to keep it.**

## 4. REUSE / REPLACE LAW

For every existing capability or implementation, the builder must evaluate it against the North Star:

### KEEP

Keep it when it is excellent, aligned, useful, maintainable, and proven.

### ADAPT

Adapt it when the underlying capability is valuable but its current implementation or experience is not sufficient.

### REPLACE

Replace it when it materially prevents or weakens the North-Star experience.

### DELETE

Delete it when it is obsolete, contradictory, unnecessary, unsafe, or merely historical baggage.

### INVESTIGATE

Investigate before deciding when evidence is insufficient.

## 5. FRESH-EYES BUILD LAW

Every NayaNET builder must be capable of reasoning as though the previous application had never been seen.

The builder must first understand:

- the mission;
- the human outcome;
- the intended experience;
- the product model;
- the design laws;
- the functional requirements;
- the quality bar; and
- the proof required for completion.

Only then should existing implementation be evaluated as a possible accelerator.

Do not let archaeology become architecture.

## 6. CONFLICT LAW

When an existing implementation conflicts with the North Star:

> **THE NORTH STAR WINS.**

When an existing implementation is beautiful, functional, proven, and aligned:

> **REUSE IT.**

When an implementation is mediocre:

> **REPLACE IT.**

When its value or purpose is uncertain:

> **INVESTIGATE IT.**

When it exists only because a previous build settled for it:

> **IT HAS NO AUTHORITY.**

## 7. DEPLOYMENT EVIDENCE LAW

The existing deployed application may be inspected for:

- current behavior;
- runtime evidence;
- integration behavior;
- technical constraints;
- failures;
- useful assets;
- performance characteristics; and
- regression evidence.

It may **not** define what NayaNET is supposed to become.

Deployment evidence informs engineering judgment. It does not outrank the North Star.

## 8. NORTH-STAR ACCEPTANCE GATE

NayaNET is not complete merely because the old application was successfully modified, the build compiles, or individual requirements pass.

The final product must pass this human recognition test:

> **“If Shawn had never seen the old app, and we showed him the finished NayaNET for the first time, would he immediately recognize: YES. This is what I have been trying to explain.”**

The experience should communicate the intended identity and value without requiring prior knowledge of the previous implementation.

If the answer is not an unequivocal **YES**, the work is not finished.

## 9. BUILDER EXECUTION LAW

For every consequential NayaNET task:

**READ THE NORTH STAR → UNDERSTAND THE INTENDED EXPERIENCE → ESTABLISH PRODUCT/DESIGN LAWS → INSPECT REPOSITORY → MAP REUSABLE ASSETS → BUILD FROM FIRST PRINCIPLES → VERIFY AGAINST THE NORTH STAR → REPAIR GAPS → VERIFY → ACCEPT OR REJECT.**

Repository archaeology happens **after conceptual authority is established**, not before it.

## 10. 10/10 LAW

The builder must not optimize for “least change.”

The builder must optimize for the **smallest coherent change that produces the intended North-Star outcome at AAA quality**.

A large change is justified when the existing substrate materially prevents the correct outcome.

A small change is preferred when it fully achieves the intended outcome without unnecessary disruption.

The objective is not preservation.

The objective is **excellence**.

## 11. NON-NEGOTIABLE BUILDER REMINDER

Before changing NayaNET, the builder must be able to state:

1. **What NayaNET is supposed to be.**
2. **What this task is supposed to make it become.**
3. **Which product/design laws govern the decision.**
4. **What existing assets are relevant.**
5. **Which existing implementations are merely evidence.**
6. **What may be reused, replaced, or deleted.**
7. **How the North-Star outcome will be verified.**
8. **Why the finished experience deserves to be called NayaNET.**

If these cannot be answered from authoritative evidence, **INVESTIGATE BEFORE ACTING**.

## 12. CANONICAL STATUS

This document is a canonical NayaNET build-governance law.

Future Naya builders, agents, developers, and implementation directives must treat this law as binding for NayaNET work unless a later, explicitly governed canonical artifact supersedes it.

**North Star first. Repository second. Deployment is evidence. Build the NayaNET that should exist.**
