This is a release gate, not inspirational copy.

Never begin with:

> “How do we make the existing Hub better?”

> **“If NayaNET did not exist yet, and we were given this mission today, what would we build?”**

## 5. ARCHAEOLOGY BEFORE IMPLEMENTATION

Before selecting an implementation target or changing production code:

1. Resolve the current `main` HEAD of `SoulSchoolAcademy/NayaPOWER`.
2. Read the canonical NayaNET planning library in its defined order.
3. Read the North-Star Build Law.
4. Search the connected GitHub project set for NayaNET-related repositories and application artifacts.
5. Inspect candidate repositories for README, framework, entry points, deployment configuration, routes, assets, recent commits, and evidence of actual use.
6. Inspect known deployed destinations when accessible.
7. Identify which repository/application is the actual current implementation, which are experiments, which are historical packages, and which are empty or obsolete.
8. Record evidence for the determination.
9. Select the implementation target explicitly.
10. Do not modify a candidate merely because its name looks right.

### Archaeology classification

Every candidate must be classified as one of:

**AUTHORITATIVE IMPLEMENTATION / ACTIVE CANDIDATE / EXPERIMENT / ASSET SOURCE / HISTORICAL / EMPTY / OBSOLETE / UNKNOWN**

Do not silently promote a candidate into authority.

## 6. ASSET DECISION MATRIX

For every materially relevant existing component:

- **KEEP** — excellent, aligned, useful, maintainable, proven.
- **ADAPT** — valuable underlying capability; experience or implementation needs work.
- **REPLACE** — materially weakens the North Star.
- **DELETE** — obsolete, contradictory, unsafe, unnecessary, or historical baggage.
- **INVESTIGATE** — insufficient evidence.

“It already exists” is never sufficient justification for retention.

## 10. EXPERIENCE STANDARD

The target experience is:

**alive · premium · intelligent · simple · immersive · warm · cinematic · fast · trustworthy · app-like**

It is not generic SaaS.

The primary interaction should make complexity disappear from the human's view.

> **Complexity belongs in the system. Simplicity belongs with the human.**

## 11. ENGINEERING STANDARD

Prefer the simplest architecture that can truthfully deliver the required capability.

For static experiences:

- prefer ordinary HTML/CSS/JS;
- minimize dependencies;
- keep assets local where appropriate;
- design iframe-safe behavior from the beginning;
- keep runtime seams explicit;
- do not introduce backend infrastructure without a real requirement;
- do not introduce Wrangler merely because it is convenient;
- never hide a missing capability behind simulated UI.

For production runtime capabilities, use the canonical architecture and explicit contracts rather than ad-hoc client behavior.

## 12. QA / OSCAR

Every substantive build follows:

**BUILD → VIEW → WHY IS THIS NOT A 10? → REPAIR → VERIFY → DOCUMENT → COMPOUND**

Attack for:

- generic/template appearance;
- unclear first action;
- weak information hierarchy;
- visual noise;
- fake capability;
- dead controls;
- broken mobile layouts;
- iframe clipping;
- accessibility failures;
- poor keyboard navigation;
- low contrast;
- excessive motion;
- performance waste;
- state/persistence errors;
- security/privacy failures;
- contradictions with later NayaNET blocks;
- anything that makes the experience feel like an old app being renovated instead of NayaNET being born.

## 13. DEVICE / EMBED STANDARD

At minimum inspect:

`320 / 360 / 375 / 390 / 414 / 480 / 600 / 768 / 900 / 1024 / 1280px`

The experience must remain complete and usable inside a constrained iframe.

Respect `prefers-reduced-motion`.
