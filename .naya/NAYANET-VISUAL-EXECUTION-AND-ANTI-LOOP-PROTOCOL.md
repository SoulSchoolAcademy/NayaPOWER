# 🔱☀️ NAYANET — VISUAL EXECUTION & ANTI-LOOP PROTOCOL

**STATUS:** CANONICAL EXECUTION LAW
**SCOPE:** Every NayaNET visual build, repair, redesign, refinement, deployment, and verification task.
**PURPOSE:** Prevent repeated edits to the wrong layer, cosmetic patch loops, source/runtime divergence, false progress, regression, and declarations of completion without visible evidence.

---

# 1. PRIME LAW

> **NEVER REPEAT AN EDIT LOOP WITHOUT PROVING WHICH LAYER FAILED.**

The Naya must not keep modifying the same source file because the visible result did not change.

When the human reports **“nothing changed,” “it looks the same,” “the lights disappeared,” “you changed the wrong thing,”** or equivalent feedback, the Naya MUST treat that as a possible SYSTEMIC FAILURE, not as a request for another cosmetic tweak.

The first responsibility is to determine WHY the visible result did not change.

---

# 2. THE FIVE-REALITIES MODEL

Every visual task has five distinct realities:

1. **INTENT** — what the human actually wants.
2. **SOURCE** — the exact HTML/CSS/JS/assets implementing it.
3. **RELEASE** — the exact commit/package intended for deployment.
4. **RUNTIME** — what the deployment target actually serves.
5. **RENDER** — what a human actually sees.

These are not interchangeable.

> **SOURCE ≠ RELEASE ≠ RUNTIME ≠ RENDER.**

A source edit is not visual progress until the chain reaches the rendered target.

---

# 3. THE ANTI-LOOP TRIGGER

If the user reports no visible change after an attempted repair, STOP cosmetic iteration.

Do not immediately:

- rewrite the same CSS;
- change another gradient;
- add another overlay;
- rename the same stylesheet;
- create another “final” file;
- claim the browser is cached without evidence;
- ask the human to judge an unverified source change;
- call the work complete.

Instead execute the **ZERO-CHANGE DIAGNOSTIC**.

---

# 4. ZERO-CHANGE DIAGNOSTIC

### STEP A — Establish current HEAD

Prove:

- repository;
- branch;
- current HEAD SHA;
- exact files changed by the attempted repair;
- exact commit containing those changes.

### STEP B — Prove source wiring

Trace the actual entry point:

**HTML → stylesheet chain → JavaScript → assets → runtime configuration**

Determine:

- which stylesheet is last in cascade;
- whether duplicate/legacy rules remain active;
- whether JavaScript changes classes/styles/DOM after load;
- whether pseudo-elements or overlays obscure the intended component;
- whether responsive rules override desktop rules;
- whether the intended asset is actually loaded;
- whether the requested file belongs to the runtime being served.

### STEP C — Prove release path

Identify:

- deployment workflow;
- trigger condition;
- working directory;
- build/package step, if any;
- deployment command;
- target name/project;
- credential dependency;
- latest run for the exact commit;
- deployment conclusion.

### STEP D — Prove runtime identity

The live target must be tied to the intended release by evidence.

If runtime identity cannot be proven, status is:

**NOT LIVE VERIFIED.**

Do not describe a source improvement as a live improvement.

### STEP E — Observe the render

Obtain an actual screenshot/render of the target whenever visual judgment is required.

Compare:

**REQUESTED → SOURCE → DEPLOYED → OBSERVED**

Record the first divergence.

---

# 5. THE WRONG-FILE DEFENSE

Before editing any file, answer internally:

> **WHY THIS FILE?**

The answer must identify its relationship to the actual runtime.

A file named `final`, `ultimate`, `master`, `north-star`, `polish`, or similar has no authority merely because of its name.

Authority comes from:

- current entry-point wiring;
- current cascade/order;
- current runtime imports;
- current deployment path;
- current product authority.

> **FILENAMES DO NOT PROVE AUTHORITY. EXECUTION PATH DOES.**

---

# 6. THE “LAST AUTHORITATIVE FILE” TRAP

A previous authoritative file may contain the right intent but still be stale, bypassed, overridden, or disconnected from the runtime.

Therefore every Naya must distinguish:

**AUTHORITATIVE DOCUMENT**
from
**ACTIVE IMPLEMENTATION**
from
**DEPLOYED IMPLEMENTATION**
from
**OBSERVED EXPERIENCE**.

Never copy a previous “final” implementation forward merely because it appears authoritative.

First prove that it is the active implementation and determine why it is active.

---

# 7. CHANGE-OR-DON'T-CHANGE TEST

Before editing, state the expected visible consequence.

Example:

> “After this release reaches the target, the purple full-screen background must be replaced by a black/obsidian circular environment, with a continuous 360° jewel circumference and a single traveling illumination.”

If the edit cannot plausibly cause that consequence, it is the wrong edit.

After deployment, ask:

> **DID THAT EXACT CONSEQUENCE OCCUR?**

If no, do not call the work successful.

---

# 8. FRONT DOOR NORTH STAR

The canonical visual target is:

**DEEP PURPLE VOID → BLACK/OBSIDIAN LIVING ORB → CONTINUOUS JEWEL CIRCUMFERENCE → BLACK CONSOLE → CLEAR HUMAN ENTRY**

The orb and console are separate objects.

The console is not a floating card on a purple page.

The center must feel calm, manufactured, intentional, and premium.

The circumference must feel like a field of high-end jewels rather than a colored CSS ring.

---

# 9. RING OF POWER LAW

The circumference contains a permanent field of individual jewel points distributed around the full 360°.

Jewel colors may travel through:

**MAGENTA → VIOLET → BLUE → CYAN → GREEN → YELLOW → GOLD → ORANGE → RED → MAGENTA**

The jewels remain mostly dormant.

One traveling illumination continuously passes around the circumference.

When it reaches a jewel:

**DORMANT → CATCH LIGHT → SHINE → AFTERGLOW → DORMANT**

The result must read as:

> **a living ring of jewels being activated by passing energy.**

It must NOT read as:

- three colored blobs;
- one giant rotating gradient;
- a straight moving line;
- a generic neon border;
- a white dot with a colored shadow;
- a cluster of lights moving together.

# 11. STATE LAW

The front door must visibly distinguish:

**IDLE → FOCUS → TYPING → READY → ENTERING**

Name input:

- idle/rest = obsidian + green outline;
- focus/typing = purple outline/glow;
- focus must not physically jump or move;
- valid name = clear ready state.

Enter button:

- disabled = restrained purple illumination;
- valid/ready = green GO state;
- hover = elevated;
- press = physical depression;
- entering = deliberate transition;
- no fake waiting spinner.

---

# 12. VISUAL PROOF LAW

For visual work, the minimum acceptable evidence chain is:

**SOURCE PROOF + DEPLOYMENT PROOF + RENDER PROOF**

If any one is missing, label the corresponding claim precisely.

Examples:

- Source proof only → **IMPLEMENTED; NOT LIVE VERIFIED**
- Deployment proof only → **DEPLOYED; VISUAL HUMAN REVIEW REQUIRED**
- Render proof only without source traceability → **OBSERVED; RELEASE IDENTITY UNKNOWN**
- All three + acceptance review → **LIVE VERIFIED**

A screenshot is not proof that the current source produced it unless release identity is established.

---

# 13. NO-REGRESSION RULE

When repairing a visual system, compare against the protected baseline.

A repair is unacceptable if it improves one requested dimension while silently destroying another protected capability.

At minimum check:

- name input;
- Enter action;
- navigation to `/hub.html`;
- Naya identity;
- mission copy;
- responsive behavior;
- accessibility labels;
- existing functional scripts;
- asset loading;
- deployment configuration.

---

# 14. ONE-CHANGE-CAUSE PRINCIPLE

When diagnosing a stuck loop, make the smallest change that can prove or disprove the suspected cause.

Do not stack five speculative changes and then infer which one worked.

If the suspected cause is deployment, fix deployment evidence first.

If the suspected cause is cascade, prove cascade first.

If the suspected cause is DOM/JS mutation, inspect JS first.

If the suspected cause is visual geometry, inspect the render and geometry first.

If the suspected cause is cache, prove cache identity before adding more cache-busting tokens.

---

# 15. THE MASTER DECISION LOOP

For every material defect:

**OBSERVE → DEFINE GAP → ROOT CAUSE → OPTIONS → CHOOSE → CHANGE → VERIFY → CRITIQUE → REPAIR → VERIFY AGAIN**

The Naya must answer:

- What exactly is wrong?
- Why is it wrong?
- What evidence supports that diagnosis?
- What alternatives were considered?
- Why is this repair better?
- What could the repair break?
- How will success be observed?

---

# 16. HUMAN FEEDBACK IS EVIDENCE

Statements such as:

- “It looks exactly the same.”
- “The lights are gone.”
- “I don't see the change.”
- “You keep doing the same thing.”
- “This is worse.”

must be recorded as observations, not dismissed as subjective resistance.

They identify a gap between intended and perceived outcome.

The Naya may disagree with a preference, but it may not ignore observed divergence.

---

# 17. COMPLETION GATE

A Naya may say **DONE** only when:

1. the correct source was changed;
2. the intended release was created;
3. deployment succeeded when deployment is in scope;
4. the live target is tied to the intended release;
5. the actual render was inspected when visual work is involved;
6. the requested visible consequences occurred;
7. protected functionality still works;
8. the master critic found no unresolved material defect within scope;
9. known limitations are disclosed;
10. the next Naya can continue without reconstructing the diagnosis.

Otherwise use:

**IMPLEMENTED / VERIFIED / DEPLOYED / LIVE VERIFIED / HUMAN REVIEW REQUIRED / BLOCKED / UNKNOWN**

as appropriate.

---

# 18. NEXT NAYA CONTINUITY RECEIPT

Every visual execution must leave:

- exact objective;
- exact active runtime;
- exact files changed;
- exact commit SHA;
- exact deployment target;
- deployment result;
- observed render result;
- first known divergence;
- root cause;
- repair performed;
- remaining gap;
- one highest-value next action.

Never leave the next Naya with “try again.”

Leave it with **what failed, why, what changed, what proved it, and what remains.**

>
> **STOP THE LOOP. FIND THE BROKEN LAYER. FIX THE CAUSE. PROVE THE RENDER. THEN MOVE FORWARD.**
>
> **NEXT NAYA > CURRENT NAYA.**
