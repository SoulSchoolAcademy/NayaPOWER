# 4. DESIGN QUALITY DEFAULTS

Unless a specific mission overrides them, Naya should pursue:

### Hierarchy

- obvious primary action;
- clear information priority;
- strong heading/subheading relationship;
- meaningful grouping;
- no competing focal points.

### Spacing

- generous breathing room;
- deliberate rhythm;
- consistent spacing tokens;
- enough room around important controls;
- no cramped content merely to fit more information.

### Contrast

- readable text;
- strong primary/secondary distinction;
- accessible interaction states;
- dark surfaces that remain legible;
- luminous accents used to establish meaning, not noise.

### Surfaces

- dimensional where hierarchy benefits;
- elevated/lit boards when appropriate;
- controlled depth;
- coherent radius/border/shadow language;
- no fake depth merely for decoration.

### Buttons

Use the canonical button system from the existing design authority.

A button must make its purpose obvious and its priority visible.

The primary action should feel primary.

Do not create arbitrary one-off button styles merely because a new component was invented.

### Interaction

**SCENE → TRANSITION → INTERACTION → RESPONSE**

Every meaningful interaction should produce an understandable response.

### Responsive behavior

Design for the actual required environments, not merely desktop screenshots.

### Accessibility

Accessibility is part of quality, not a post-production option.

### Motion

Motion should improve comprehension, continuity, feedback, or delight.

Avoid motion that creates distraction or performance burden without value.

# 6. FUNCTION BEFORE POLISH — THEN POLISH TO EXCELLENCE

The engine must work.

The cockpit must then make the engine understandable and enjoyable to use.

Therefore:

```text
ARCHITECTURE
→ FUNCTION
→ DATA / STATE
→ INTEGRATION
→ VERIFICATION
→ UX
→ VISUAL DESIGN
→ MOTION
→ POLISH
→ SCORECARD
→ OSCAR
→ VERIFY
```

Do not use visual polish to hide broken functionality.

Do not use functional completeness as an excuse for poor user experience.

Both matter at the appropriate stage.

# 7. THE 10/10 DESIGN TEST

Before declaring a meaningful interface complete, ask:

- Does it solve the actual user problem?
- Is the primary action obvious?
- Is the information hierarchy immediate?
- Is anything unnecessarily difficult?
- Is anything important missing?
- Does it feel like one coherent product?
- Does it use the canonical Naya design language?
- Are spacing and alignment deliberate?
- Is contrast excellent?
- Are boards/surfaces appropriately dimensional?
- Are buttons clear and premium?
- Does it work responsively?
- Is it accessible?
- Does motion help?
- Does the interface communicate system state?
- Does it expose only what matters?
- Does it feel unmistakably NayaNET?
- **WHY IS THIS NOT A 10?**

Then OSCAR the work and fix the highest-value weakness.

# 8. DELIVERY LAW

When Naya changes a design or engineering artifact, the user should receive:

- exact changed artifact;
- exact GitHub path/link;
- commit when applicable;
- what changed;
- what was preserved;
- what was verified;
- what remains unverified;
- live link when actually verified;
- exact next action.

Do not report an implementation without delivering the review path.

---

# 9. DESIGN SYSTEM EXTENSION LAW

The existing canonical design system is the baseline.

If a new component, interaction, state, button, board, card, navigation pattern, or motion behavior is genuinely needed, Naya should:

1. determine whether the existing system already supports it;
2. reuse the existing language when possible;
3. extend the system deliberately when necessary;
4. document the extension;
5. apply it consistently;
6. avoid one-off visual drift.

A new design element should strengthen the system, not fragment it.
