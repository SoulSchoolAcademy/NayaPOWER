## Classification model

### CANONICAL
Current durable intelligence already represented by the canonical IB system.

### MIGRATABLE
Contains durable intelligence that should be distilled into a canonical IB.

### PROJECTION
A representation of a canonical object, such as Feed, Activity, Report, Library, receipt, or UI projection. Keep it as a projection; do not duplicate it as a second brain object.

### LEGACY COMPATIBILITY
Older format/path retained because runtime or tooling still references it. Do not use it for new writes.

### HISTORICAL
Valuable record of prior decisions, implementation, experiments, or reasoning. Preserve for provenance; it cannot silently override current truth.

### DUPLICATE / SUPERSEDED
Its useful meaning is already represented by a newer or more authoritative object. Preserve provenance and link it to the surviving canonical object; do not create a competing IB.

### NOISE / RETIRED
No durable value, obsolete operational scratch, duplicate without unique provenance, or material that no longer contributes useful intelligence. Do not delete until references and provenance have been checked. Prefer explicit archive/retirement.

## Duplicate rule

Never create a new IB merely because an older file has a different filename.
Before creating an IB: search the canonical registry; search related canonical topics; compare semantic meaning; decide CREATE vs UPDATE vs SUPERSEDE vs PROJECTION; preserve provenance.

## Deletion rule

No destructive mass deletion is part of this migration.
The first cleanup pass removes ambiguity, not history.
A file may be deleted only after its contents are represented or intentionally retired, inbound references are known, no runtime depends on it, provenance is preserved, and retirement is recorded.

## Verification rule

Repository canonicalization and live intelligence learning are different claims.
A migrated file proves SOURCE → CANONICAL REPOSITORY INTELLIGENCE.
It does not by itself prove SOURCE → LIVE EVENT → INTELLIGENT BLOCK → INDEX → LEARNING → RETRIEVAL → HUB/FEED → RELOAD.
That second chain must be independently runtime-verified.
