# 🔱 NayaPOWER Law — Canonical Intelligence Before Creation

**Status:** CANONICAL — PROPOSED FOR RATIFICATION BY HUMAN DIRECTOR  
**Date:** 2026-09-25  
**Scope:** Every Smart Note / Intelligent Block creation, retrieval, migration, learning, and projection path.

## The law

> **If a concept has multiple names, locations, schemas, identities, or creation paths, Naya MUST resolve the canonical contract before creating new intelligence.**

### Enforcement rule

No Naya, coder, UI, workflow, runtime helper, migration, or automation may create a new Smart Note / Intelligent Block until it has resolved:

1. the canonical contract;
2. the canonical identity authority;
3. the canonical persistence authority;
4. the canonical source-event/provenance boundary;
5. the permitted projections and legacy aliases.

**Unknown canonicality is a creation blocker.** Naya must reconcile first, not guess.

## One object

**Smart Note** is the human-facing name.

**Intelligent Block (IB)** is the canonical machine identity and durable intelligence object.

There is one canonical object, one immutable IB identity, one provenance chain, one lifecycle, and many projections.

## One identity

The canonical identity is:

`IB-XXXXXX`

allocated only by the live canonical Smart Note receiver / authoritative persistence boundary.

The following are **not alternate identities**:

- source event UUID;
- database row UUID;
- receipt UUID;
- transaction UUID;
- repository path;
- Smart Note display title;
- legacy Smart Note number;
- UI DOM id;
- historical `SN-...` id.

They are lineage, transport, projection, or compatibility references.

## One persistence authority

The canonical durable machine object is the owner-scoped Intelligent Block persisted in the governed runtime.

The canonical source event and its receipt establish provenance.

Repository Markdown is a **human-readable projection**, not an independent identity allocator or competing source of truth.

## Many projections

Permitted projections include:

- canonical repository Smart Note Markdown;
- Smart Feed;
- Activity;
- Intelligent Library;
- Reports;
- Search;
- Naya context;
- Dream / Replay;
- Smart Lists;
- Smart Share / Spaces when authorized;
- historical compatibility views.

A projection must retain the canonical IB identity and source-event lineage.

## Creation law

Creation MUST follow:

`INPUT → CANONICALIZE → AUTHORIZED RECEIVER → IB ID → PERSIST → EVENT/RECEIPT → INDEX → PROJECTIONS → LEARNING → VERIFY → HANDOFF`

A local script MUST NOT:

- allocate an IB number;
- infer the next IB number from a repository cursor;
- create a competing note store;
- treat a UI object as the intelligence source;
- treat a Markdown file as proof of runtime persistence;
- silently create a second identity.

## Retrieval law

Retrieval MUST resolve canonical intelligence by authorized canonical identity / lineage and semantic intelligence retrieval.

It MUST NOT depend on arbitrary folders, filenames, stale UI copies, or historical numbering.

## Migration law

Every legacy representation is classified as one of:

- **CANONICAL**
- **MIGRATABLE**
- **PROJECTION**
- **LEGACY_COMPATIBILITY**
- **HISTORICAL**
- **DUPLICATE / SUPERSEDED**

Migration preserves provenance and never silently creates a second intelligence object.

## Cold-Naya law

A cold Naya must be able to discover this law before creating or retrieving Smart Note intelligence.

The architecture must remind the Naya. Memory of the law is not sufficient.

## North Star

> **Resolve before you create. One intelligence object. One identity. One truth path. Many projections.**

This law exists to prevent:

**Naya A invents A → Naya B invents B → Naya C cannot find either → Shawn reconstructs the system → Naya D invents C.**

That is fragmentation, not compound intelligence.
