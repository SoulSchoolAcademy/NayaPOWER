# 04 — Canonical Intelligence Lifecycle

## Three non-negotiables
**NO INTELLIGENCE WITHOUT CANONICALIZATION.**
**NO CANONICAL INTELLIGENCE WITHOUT AN INTELLIGENT BLOCK.**
**NO INTELLIGENT BLOCK WITHOUT AN INTELLIGENCE EVENT.**

## Lifecycle
**CAPTURE → CANONICALIZE → ASSIGN IB ID → PERSIST → COMMIT INTELLIGENCE EVENT → INDEX → PROJECT → LEARN → RETAIN → RETRIEVE → APPLY → VERIFY → UPDATE LEARNING → COMPOUND**

Capture records meaningful experience or intent. Canonicalization determines durable value and reconciles it with current understanding.

The live canonical receiver is the sole authority for assigning an immutable IB ID. Nayas, files, scripts, tests and migrations must never calculate, guess, increment or reserve an IB number.

A repository Smart Note is a human-readable projection created only after authoritative identity allocation. Markdown alone is not completion.

## Canonical Smart Note structure
Every canonical Smart Note uses:
1. IN A NUTSHELL
2. DATE / TIME
3. WHAT
4. WHY IT MATTERS
5. HUMAN
6. CHILD
7. GRANDMA
8. NAYA
9. MACHINE
10. WHAT WE LEARNED
11. CONNECTIONS
12. HOW TO APPLY
13. WHAT IT ULTIMATELY MEANS
14. WHAT'S IN IT FOR YOU / US
15. NEXT ACTION

## Event boundary
Canonical creation is an Intelligence Commit Event, not merely a UI notification. The event feeds downstream indexing and learning.

## Learning boundary
Persistence, verification and learning are separate states. A persisted object can be candidate learning without being validated learning.

## Replay
Canonical intelligence remains replayable so a later Naya can retrieve, understand, reflect, learn, apply and verify without rewriting history.
