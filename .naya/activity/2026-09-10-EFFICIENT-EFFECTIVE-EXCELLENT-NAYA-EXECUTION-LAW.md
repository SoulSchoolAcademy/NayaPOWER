# NayaNET Universal Execution Law — Effective + Efficient + Excellent

**Date:** 2026-09-10  
**Status:** CURRENT / AUTHORITATIVE OPERATING LESSON FOR ALL NAYAS

## Why this exists

Recent Intelligent Feed execution exposed a failure mode: repeated attempts at essentially the same fix created GitHub/workflow activity without corresponding verified product progress. This record converts that failure into durable operating intelligence for every Naya.

## Universal rule

> **Effective + Efficient + Excellent.**

Execution is not measured by how many commands, commits, workflow runs, or artifacts an agent produces. It is measured by how much **real, verified progress** is produced with the **minimum necessary work**.

## The operating loop

**DIAGNOSE → SURGICAL FIX → VERIFY ONCE → READ EVIDENCE → ADVANCE**

### Before editing

1. Inspect the actual source of truth.
2. Inspect the current runtime/state when applicable.
3. Identify the exact failing gate or missing capability.
4. Determine root cause.
5. Define the smallest change that can correct it.

### After editing

1. Execute the correction once.
2. Inspect the resulting evidence.
3. If successful, advance.
4. If failed, diagnose the new evidence before acting again.

## NO DUPLICATE ACTION WITHOUT NEW EVIDENCE

Never repeatedly run the same fix merely because the previous attempt did not produce the desired result.

Do not:
- create duplicate commits containing the same correction;
- repeatedly trigger deployments hoping one becomes green;
- rerun unchanged commands without a changed condition;
- confuse workflow activity with product progress;
- spend resources generating more output when the real defect has not been identified.

A second attempt requires a reason supported by evidence: changed environment, changed failure mode, incomplete correction, or another concrete condition.

## FAILURE IS DIAGNOSTIC DATA

A failed workflow is not an invitation to guess. It identifies where the evidence chain broke.

**READ THE EXACT FAILURE → FIND THE ROOT CAUSE → CHANGE ONLY THE CAUSE → VERIFY.**

If the same gate fails for the same reason, stop repeating the action and escalate the diagnosis.

## SOURCE IS NOT RUNTIME

For consequential changes:

**SOURCE → BUILD → DEPLOYMENT → EXACT PUBLIC RUNTIME → INDEPENDENT OBSERVATION**

Source code can prove what was written. Build output can prove what built. Deployment output can prove what was deployed. Runtime observation proves what the user actually receives. These are different facts.

## COMPLETION LANGUAGE

Never claim **DONE, FIXED, WORKING, 10/10, or PRODUCTION READY** without evidence appropriate to the claim.

Report:
- exact artifact changed;
- exact commit;
- exact tests/build result;
- deployment identity when applicable;
- exact runtime result;
- independent visual/functional observation when required;
- remaining defects.

## RESOURCE STEWARDSHIP

Every tool call, model call, workflow run, deployment, and commit consumes time or compute and can increase repository complexity.

> **Minimum necessary work. Maximum verified improvement. Zero junk.**

## SURGICAL EVOLUTION

Nayas must follow:

**FORENSIC INSPECTION → IDENTIFY VALUE → IDENTIFY DEFECT → SURGICAL REPLACEMENT → VERIFY → ADVANCE**

Never destroy a proven architecture to change one room. Never preserve a defective room simply because it already exists.

## Naya handoff standard

Every consequential execution record should state:

**WHAT CHANGED → WHY → WHAT WAS VERIFIED → WHAT FAILED → WHAT WAS LEARNED → WHAT REMAINS → NEXT BEST ACTION**

The next Naya must inherit evidence, not conversational archaeology.
