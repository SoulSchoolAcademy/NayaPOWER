**DEPTH → LIGHT → STATE → RESPONSE → CONSEQUENCE**

**MATERIAL · DEPTH · LIGHT · COLOR · STATE · MOTION · TOUCH · CLARITY · CONSEQUENCE · MEMORY**

# 5. COMPONENT STANDARD

## 5.1 POWER OBJECT — BUTTONS

A button is a physical action object, not a colored rectangle.

### REST

- black/deep obsidian core
- dimensional bevel or layered surface
- subtle glass/material response where appropriate
- fine silver/white perimeter light
- restrained semantic halo
- physical shadow/elevation
- high legibility

### HOVER

- object rises slightly
- perimeter light becomes clearer
- semantic color emerges
- highlight travels or changes position subtly
- shadow changes to communicate elevation
- label becomes brighter
- no explosive glow

### FOCUS

- keyboard focus is unmistakable
- uses the same visual language as hover without depending on a mouse
- never removes accessibility outline

### PRESS

- object physically depresses
- elevation reduces
- shadow collapses
- black center deepens
- semantic light compresses/intensifies
- label remains crisp

### ACTIVE / SUCCESS

The component visibly resolves into its new state.

### Primary ENTER button

The entrance button is a signature NayaNET object.

It must:

- sit directly below the name field
- be approximately the same visual width as the input assembly
- use a black center/core rather than a flat purple fill
- contain a restrained white/diamond-like light
- have dimensional elevation
- use purple as intelligence response, not as a giant painted rectangle
- feel tactile and premium
- depress physically on press
- immediately communicate that it opens the portal

### Semantic button colors

- **Green:** proceed / enter / active / growth
- **Purple:** Naya / intelligence
- **Magenta:** creation / energy accent
- **Gold:** significance / achievement / signature moments
- **Cyan:** connection / flow
- **Blue:** knowledge / trust
- **Orange:** action / momentum
- **Red:** danger / destructive actions only
- **White/silver:** neutral controls

A board is a destination object.

It must feel like a **door into a place**, not a card in a dashboard.

### REST

- black/near-black core
- dimensional surface
- visible perimeter edge light
- semantic identity color present but restrained
- subtle inner illumination
- icon/glyph with optical depth
- atmospheric halo
- physical shadow/occlusion

**Important:** an unhovered board must not become visually dead.

### HOVER

- board lifts
- perimeter becomes brighter
- semantic color becomes more visible
- internal light expands
- glyph becomes more dimensional
- surrounding environment reacts subtly

### PRESS

- board compresses/depresses
- light tightens
- state changes immediately

### ACTIVE

A world becomes the destination/environment.

Do not use a tiny modal, tooltip, or toast as the primary result of entering a world.

# 12. MOTION & MICRO-INTERACTION

Motion exists to communicate:

- state
- relationship
- transition
- consequence
- continuity

Not decoration.

### Required state model

Interactive objects should support as applicable:

`REST → HOVER → FOCUS → PRESS → ACTIVE → SUCCESS`

and:

`LOADING / ERROR / REDUCED MOTION`

### Motion characteristics

- calm at rest
- immediate at interaction
- physical on press
- meaningful during transitions
- restrained during ambient animation
- never delays basic task completion

### Reduced motion

Every animated system must have a reduced-motion behavior.

Do not remove essential state communication when motion is disabled.

# 21. MANDATORY AI EXECUTION WORKFLOW

Every build follows this sequence.

## PHASE 1 — LOAD

Load:

1. Product Constitution
2. Design System Standard
3. Master Build & Execution Directive
4. Project Build Directive
5. Relevant repository/deployment evidence

## PHASE 2 — INVESTIGATE

Before editing:

- identify the authoritative repository
- identify the authoritative branch
- identify the active runtime
- inspect current implementation
- inspect existing capabilities
- inspect deployment configuration/evidence
- identify what is protected
- identify what is broken
- identify what is obsolete
- identify what is missing

Do not begin by writing code.

## PHASE 3 — PLAN

Create an internal implementation map:

`REQUIREMENT → COMPONENT → FILE → STATE → BEHAVIOR → QA TEST`

For every major requirement, know where it will be implemented before changing it.

## PHASE 4 — BUILD

Implement the system coherently.

Do not patch symptoms indefinitely.

If the design system is wrong, correct the system rather than stacking another override.

## PHASE 5 — VERIFY

Verify:

- syntax
- structure
- interactions
- state transitions
- accessibility
- responsive behavior
- persistence
- real assets
- truthful capability
- error handling
- performance
- component physics
- design consistency

## PHASE 6 — SELF-CRITIQUE

Ask:

> **WHY IS THIS NOT A 10?**

Evaluate the experience as:

- a child
- a grandmother
- an ordinary user
- a design expert
- an interaction expert
- an accessibility user
- a front-end engineer

Fix the highest-impact deficiencies before delivery.

## PHASE 7 — COMMIT

Commit only after verification.

Use clear commit messages.

Never claim a commit is production deployment.

## PHASE 8 — DEPLOY / DELIVER

Deploy through the authoritative deployment path when available.

If deployment tooling is unavailable, deliver the verified repository state and explicitly report deployment status as unverified.

## PHASE 9 — REPORT

Report four things:

1. **Built** — what changed
2. **Verified** — what was actually tested
3. **Committed** — exact commit/reference
4. **Deployment** — deployed, pending, or unverified

Never blur these categories.
