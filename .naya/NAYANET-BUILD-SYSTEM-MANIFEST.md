## 0. UNIVERSAL BUILD GATE

Before any substantive app build under Naya Power, the builder MUST activate:

**`.naya/NAYAPOWER-UNIVERSAL-APP-BUILD-GATE.md`**

That gate is the reusable compression/activation layer for the canonical build-intelligence set.

The required behavior is:

**READ → UNDERSTAND → OBEY → APPLY → VERIFY**

The human should not have to paste the same standards into every build conversation when repository access is available.

The Universal App Build Gate does not replace detailed source documents. It makes them part of standard operating procedure and tells the builder when each is applicable.

## 4. DOCUMENT-LOADING RULE

Do not load everything indiscriminately.

Use:

> **FULL SYSTEM AWARENESS + SELECTIVE DEEP LOADING**

The AI must know the governance map before acting, then load the smallest authoritative set necessary for the current task.

### Mandatory before code changes

1. repository identity;
2. canonical runtime/context briefing;
3. current project state if present;
4. applicable governing laws;
5. Universal App Build Gate;
6. NayaNET product authority when applicable;
7. current project directive;
8. relevant design/quality standards;
9. actual implementation files;
10. relevant capability contracts;
11. QA/release gate.

### Never do this

```text
Read one document → start coding → discover contradictions later.
```

### Do this

```text
Orient → Activate → Source-lock → Inspect → Define proof → Build.
```

Record relevant behavior before editing when practical.

## 7. DECISION ENGINE

For every material implementation decision:

```text
QUESTION
  ↓
CAN AUTHORITY ANSWER IT?
  ├─ YES → obey authority
  └─ NO
      ↓
CAN CURRENT REPOSITORY EVIDENCE ANSWER IT?
  ├─ YES → use evidence
  └─ NO
      ↓
IS IT A SAFE IMPLEMENTATION CHOICE?
  ├─ YES → choose simplest robust option
  └─ NO → investigate / escalate
```

The AI may optimize implementation.

It may not optimize away product intent, protected capability, proof, accessibility, security, or explicit human direction.

At minimum consider:

- idle;
- hover;
- focus;
- active;
- pressed;
- selected;
- loading;
- success;
- error;
- disabled;
- empty;
- unavailable;
- speaking;
- listening;
- transitioning;
- mobile/responsive variants;
- reduced-motion variant where relevant.

A visual change without a meaningful state or consequence is decoration, not intelligence.

## 10. DATA / CAPABILITY INTEGRITY

A capability is real only when the underlying path exists and is connected.

Do not use:

- fake analytics;
- fake user records;
- fake AI responses presented as live intelligence;
- placeholder media where real assets are required;
- dead buttons that imply capability;
- simulated persistence presented as durable persistence;
- UI labels that imply functionality not implemented.

If a capability is intentionally illustrative, it must be clearly treated as such and must not be mistaken for production behavior.

---

## 11. RESPONSIVE SYSTEM

Mobile is an intentional experience.

Do not merely shrink desktop.

For every major experience, verify:

- touch target size;
- hierarchy;
- content priority;
- navigation;
- player behavior;
- text wrapping;
- viewport overflow;
- keyboard/input behavior;
- reduced motion;
- loading/error states;
- orientation changes where relevant.

---

## 12. ACCESSIBILITY SYSTEM

Accessibility is part of the product, not a final cosmetic pass.

Verify as applicable:

- semantic HTML;
- keyboard operation;
- visible focus;
- logical focus order;
- labels and names;
- ARIA only where necessary;
- live regions for meaningful dynamic updates;
- screen-reader comprehension;
- sufficient contrast;
- text scaling;
- reduced motion;
- alternative input;
- audio controls and captions/transcripts where required.

---

## 13. PERFORMANCE SYSTEM

Optimize for perceived and actual responsiveness.

Protect:

- fast initial interaction;
- non-blocking media/audio;
- progressive loading;
- stable layout;
- efficient event handling;
- sensible asset sizes;
- bounded animation work;
- no unnecessary network requests;
- graceful degradation.

Do not sacrifice experience quality for premature micro-optimization, but do not ship known avoidable performance failures.

 ↓

Never infer a live URL or live state from historical memory.

---

## 15. PROOF SYSTEM

Every important claim needs an evidence class.

### Code proof

The relevant code/config exists at the expected commit.

### Automated proof

Tests/lint/build/type checks pass where applicable.

### Runtime proof

The affected runtime executes successfully.

### Live proof

The actual user-facing deployment is checked.

### Human proof

A human can judge subjective experience that machines cannot establish.

The final report must identify which proof classes actually passed.

## 16. CONTINUITY SYSTEM

At handoff, the system should preserve:

- what happened;
- what changed;
- what was learned;
- what matters now;
- what is blocked;
- what is next;
- what proves success.

The existing NayaPOWER context system already defines canonical runtime briefing and running-feed mechanisms. Use them rather than creating parallel memory authorities.

---

## 17. FAILURE-RECOVERY SYSTEM

When something fails:

1. stop pretending it succeeded;
2. capture exact failure evidence;
3. determine whether the failure is local, architectural, environmental, deployment-related, or unknown;
4. identify the smallest responsible repair;
5. repair;
6. rerun the relevant verification;
7. check for regressions;
8. update continuity artifacts when material.

Do not stack speculative fixes on top of an unknown root cause.

---

## 18. ANTI-LOOP RULE

The system exists partly to prevent endless cycles.

If repeated attempts are failing, do not simply retry the same approach.

After two materially similar failures:

**STOP → DIAGNOSE ROOT CAUSE → RE-SOURCE-LOCK → CHANGE STRATEGY → VERIFY**

If the blocker is external, record it as BLOCKED rather than generating more speculative code.

## 19. COMPLETION CONTRACT

A task is complete only when:

- authority was loaded;
- current reality was established;
- protected surface was identified;
- intended change was implemented;
- acceptance criteria were checked;
- meaningful regressions were checked;
- 10/10 review was performed;
- repairable high-impact defects were repaired;
- verification was repeated;
- commit exists;
- deployment status is accurately stated;
- remaining unknowns/limitations are explicit;
- next Naya has a clean continuation state.
