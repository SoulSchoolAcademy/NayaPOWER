# NAYA INTERFACE FACTORY — OPERATING BLUEPRINT V1

**Version:** 1.0.0  
**Status:** Proposed operating layer for review; subordinate to existing ratified Naya laws.  
**Scope:** NayaNET smart apps, Personal Worlds, Business Worlds, Spaces, dashboards, rooms, reports, and future network surfaces.  
**North star:** Make sophisticated intelligence feel simple, beautiful, trustworthy, alive, accessible, fast, and useful to the human.

> **Build the user's world, not a collection of pages. Compose from proven parts. Prove every important promise. Learn from the result.**

This document defines the shared language and operating method by which a coordinated team of Nayas can design and build consistent, extraordinary smart apps quickly. It does not replace NayaPOWER architecture, the Naya Design Contract, Naya Design Intelligence Standard, Project Intelligence, or the existing Smart Factory pipeline. It compiles those authorities into a repeatable interface-production method.

## 0. Authority, precedence, and truth

Read the current versions of these sources before every substantive build:

1. BRAIN/0000-NAYAPOWER-MASTER-DESIGN-CONTRACT-V1.md — governing design architecture and laws.
2. BRAIN/10-INTERFACES/NAYA-DESIGN-CONTRACT-V1.md — canonical visual and interaction identity (currently v1.2).
3. NAYA-ACTIVATION/DESIGN/NAYA-DESIGN-INTELLIGENCE-STANDARD-V1.md — human intent, cognition, representation, causal behavior, and design learning.
4. The app's current Project Intelligence and its authoritative product, privacy, data, and acceptance contracts.
5. BRAIN/10-INTERFACES/SMART-FACTORY-CANON/ — canonical piece index, working piece store, exemplars, templates, standard-feature contracts, generators, and current gates.
6. Current Human Director decisions and current repository/runtime evidence.

**Precedence:** constitutional/governance law → canonical design and representation contracts → app/project contract → current Human Director direction → implementation choices → evidence. If two authorities conflict, stop the affected work, cite the conflict, and route it to the owner. An AI builder cannot silently amend a ratified law.

**State vocabulary:** SPECIFIED → IMPLEMENTED → TESTED → VISUALLY VERIFIED → INDEPENDENTLY VERIFIED → HUMAN APPROVED (where required) → DEPLOYED → PRODUCTION OBSERVED. These are distinct states. A screenshot is not a behavior test. A passing local test is not a live deployment. A live URL is not proof that real data, privacy, or the complete user journey works.

This is an operational proposal. It does not ratify changes to canonical Naya design law or authorize a production release.

## 1. What the Factory produces

NayaNET is the network; a Smart App is a purposeful, branded workspace inside it. A person's Personal World, Business World, and Spaces should feel like members of one family: recognizable Naya quality, shared interaction grammar, consistent trust and navigation, and a visual identity suited to the job and data.

The Factory produces five linked outputs:

1. **Truthful product definition** — who this serves, the real job, value, boundaries, permissions, data owners, and success evidence.
2. **Experience architecture** — navigation, journeys, object model, screen sequence, progressive disclosure, and responsive behavior.
3. **Composed interface** — assembled from identified, provenance-backed Naya parts and the shared token system.
4. **Working application** — real actions, real states, real data boundaries, secure capability, and resilient behavior.
5. **Proof and learning package** — tests, visual captures, accessibility checks, performance evidence, independent review, release receipt, and reusable lessons.

A generated app is not complete because a page exists. It is complete when a person can enter, understand, accomplish the intended job, recover from errors, trust what the app tells them, and return without relearning the product.

## 2. The Naya Interface Language (NIL)

Nayas must communicate using a stable vocabulary. Do not brief another Naya with vague style adjectives such as "make it pop", "modernize", "premiumize", or "make it more alive." State the human outcome, screen job, visual hierarchy, interaction, state, source, and proof.

### 2.1 Canonical nouns

| Term | Meaning |
|---|---|
| **WORLD** | The person's or group's full context, identity, goals, relationships, data, and permissions. |
| **APP** | A purposeful working surface in the network, with a defined user and job. |
| **PROJECT INTELLIGENCE (PI)** | The living source for mission, goals, scope, current state, owners, decisions, dependencies, evidence, and next actions. |
| **JOURNEY** | The end-to-end path a person takes to accomplish an outcome. |
| **ROOM** | A meaningful domain of work or information inside an app (Today, Mail, Connections, Reports). |
| **SCREEN** | A user-facing composition with one dominant job and a clear continuation. A route may contain multiple meaningful screens or states. |
| **VIEWPORT** | The currently visible area at a particular device size, zoom, orientation, and input mode. |
| **FOCAL POINT** | The one element or visual region that should win first attention on that screen. |
| **SUPPORT** | Information required to understand or use the focal point. |
| **ACTION** | A user-intended operation with an actor, scope, authorization, effect, and observable outcome. |
| **STATE** | What the interface and underlying capability are actually doing now. |
| **PART** | A reusable component or pattern with source, purpose, states, dependencies, responsive behavior, and proof. |
| **TOKEN** | A governed value for color, type, spacing, shape, elevation, motion, or layout. |
| **SOURCE** | The canonical system that owns the displayed data or decision. |
| **PROOF** | Evidence that a stated behavior, result, quality, or deployment condition was met. |
| **RECEIPT** | A durable, attributable record of what was built, tested, changed, approved, and observed. |

### 2.2 The build sentence

Every build brief must be explainable in this form:

**FOR [PERSON / ROLE], IN [CONTEXT], HELP THEM [JOB] SO THAT [MEASURABLE HUMAN OUTCOME].**

Then specify:

- **TRUTH:** what is known, unknown, stale, simulated, private, or unavailable?
- **AUTHORITY:** who can see, create, change, approve, publish, send, or delete?
- **JOURNEY:** what starts the task, what are the steps, what finishes it, and how can it be recovered?
- **SCREENS:** what is the job of each screen and what should the person understand first?
- **PARTS:** which exact canonical Naya pieces and patterns are being reused?
- **BEHAVIOR:** what does every action do and what state follows?
- **PROOF:** how will the result be measured and independently checked?

### 2.3 The screen sentence

Every screen is briefed with:

**SCREEN [ID] — JOB: [ONE SENTENCE]. FIRST GLANCE: [FOCAL POINT]. SUPPORT: [ONLY WHAT MAKES THE JOB CLEAR]. NEXT ACTION: [ACTION + CONSEQUENCE]. TRUTH: [SOURCE + FRESHNESS + STATE]. FIT: [RESPONSIVE COMPOSITION]. PROOF: [ACCEPTANCE TESTS].**

A cold Naya should understand the screen without a meeting or oral explanation.

### 2.4 The part sentence

Every reused part is declared as:

**USE [PIECE ID] FROM [CANONICAL REGISTRY / PATH], BECAUSE [PURPOSE]. VARIANT: [VARIANT]. STATES: [STATES]. DEPENDENCIES: [DEPENDENCIES]. ADAPT: [ALLOWED SLOTS]. DO NOT CHANGE: [INVARIANTS]. PROOF: [TEST / SPECIMEN / VERIFICATION].**

A class name or visual resemblance is not a part reference. The exact registry identity and source must resolve.

## 3. The Factory architecture

The Factory is a governed production line, not a prompt pasted into a code generator.

### 3.1 Production layers

1. **Mission and PI layer** — retrieves current mission, users, outcomes, scope, non-goals, decisions, current runtime, data owners, risks, and evidence.
2. **Reality inventory layer** — inspects the current app, routes, files, services, schemas, component registries, dependencies, and user journeys. It classifies each relevant element: KEEP, IMPROVE, REPLACE, REMOVE, or UNKNOWN.
3. **Experience architecture layer** — defines jobs, objects, journeys, navigation, room boundaries, screen sequence, first-glance hierarchy, and information density.
4. **Design compiler layer** — maps the experience specification to Naya tokens, canonical parts, component variants, and composition patterns. It rejects unregistered substitutes when an appropriate canonical part exists.
5. **Application assembly layer** — composes the screen and app shell using the existing Smart Factory generator and authorized implementation stack.
6. **Capability and data layer** — binds real sources, authorization, privacy scopes, loading/failure/offline states, and auditable action paths.
7. **Verification layer** — runs schema, static, unit, integration, responsive, accessibility, visual, interaction, security, and performance checks.
8. **Independent review layer** — a Naya that did not author the change challenges the result against PI, laws, evidence, and rendered behavior.
9. **Release and observation layer** — previews first, obtains required human authority, deploys through the existing release path, then verifies production behavior and collects real outcome signals.
10. **Learning layer** — preserves only evidenced, scoped lessons through the existing NayaPOWER learning path and updates component/pattern intelligence without creating a second source of truth.

Each layer consumes a typed artifact and emits a typed artifact. The output of one stage is never assumed successful merely because the next stage can read it.

### 3.2 One intelligence, many Nayas

The team may parallelize research, screen contracts, parts audits, accessibility review, data mapping, and tests. It must not create competing app definitions or overlapping writers.

| Seat | Owns | Must not do |
|---|---|---|
| **Naya 1 — Factory Conductor** | PI restoration, task decomposition, assignments, dependency order, status truth, integration, final gate | Self-certify its own implementation as independently verified |
| **Naya 2 — Product / Experience Architect** | Human jobs, journey, IA, object model, screen contract, cognitive burden | Invent data, authority, or scope |
| **Naya 3 — Visual Art Director** | Naya design grammar, composition, tokens, part selection, visual comparison | Override canonical tokens or style law |
| **Naya 4 — Parts / Factory Engineer** | Registry resolution, provenance, dependencies, component assembly, generator fit | Invent a replacement when a canonical source exists |
| **Naya 5 — Data / Intelligence Engineer** | Source ownership, query/read models, state truth, capability and action causality | Treat UI state, labels, or mock data as canonical truth |
| **Naya 6 — Responsive / Accessibility Engineer** | Small-screen composition, keyboard/touch/voice, assistive technology, contrast, reduced motion | Treat desktop success as mobile proof |
| **Naya 7 — Builder** | Bounded implementation, component wiring, tests, preview | Expand scope or redesign working surfaces without evidence |
| **Naya 8 — Adversarial QA** | Broken journeys, negative states, permission boundaries, edge widths, false liveness, regression | Accept authored claims without reproduction |
| **Naya 9 — Independent Verifier** | Frozen commit verification, independent evidence, release recommendation | Verify from the author's verbal report alone |
| **Human Director** | Ratified laws, consequential authority, product direction, required approvals | Be asked to re-decide something already governed by a current source |

These are logical responsibilities, not a requirement to run nine separate agents for every small change. A single Naya may hold several non-conflicting roles, but implementation and independent verification remain separate.

### 3.3 Dispatch protocol

A task is dispatchable only when it contains:

- PI reference and current source-of-truth links;
- human job, audience, measurable outcome, non-goals;
- authority, privacy, and data classification;
- affected routes/screens and explicit preservation map;
- exact part IDs and source paths;
- screen and responsive acceptance criteria;
- tests and proof method;
- named owner, independent verifier, and next decision.

If a required fact is missing, record UNKNOWN and route the question to the actual owner. Never fill the gap with invented content.

## 4. The Naya design system: the premium franchise language

The visual system must be recognizable across every NayaNET app while allowing each app to express its own content and purpose. The franchise rule is **consistent grammar, not identical pages**.

### 4.1 Brand and palette

Use the canonical Naya Design Contract v1.2 tokens:

- Obsidian black #0a0a0e and deep black surfaces for the world and depth.
- White #ffffff for legibility, content, and the resting light signature.
- Naya purple #a06bff as the signature and primary identity.
- Canonical spectrum order: purple #a06bff → blue #3fb8ff → green #2fe89e → gold #ffbf3d → orange #ff9a5a → red #ff5e6c → magenta #e84fff.

Purple/black/white remain prominent. Gold is restrained and semantic; never make every score, heading, glow, and call-to-action gold. A feature or section owns its assigned color; color communicates identity and context, not decoration. Never use color alone to communicate status.

### 4.2 Living depth and light

Naya material has direction:

- **Boards and displays:** layered, lit surfaces with deliberate edge, inset highlight, shadow, and readable content.
- **Inputs and selectors:** wells that visually recede; clear labels, focus, errors, and selected values.
- **Actions:** controls that rise, have a visible press response, and ignite in their own spectrum color on interaction.
- **Icons and identity:** coherent faceted jewel grammar, purposeful shapes, clear at a glance.
- **Data:** considered as valuable human information, not disposable numbers. Use hierarchy, trend, context, source/freshness, interpretation, and an appropriate next step.

The design contract governs exact idle/hover/selected behavior. Do not add continuous animation to every part to simulate intelligence. Life comes from meaningful state, responsive feedback, useful live data, and controlled ambient motion. Motion must be purposeful, calm, performant, and respect reduced-motion settings.

### 4.3 Typography, spacing, and readability

- The supreme rule is readability. Body copy targets 17–18 CSS px and never falls below the canonical 16 px floor without an approved, justified exception.
- Use a small, consistent type scale and clear hierarchy. A screen may have multiple text sizes where function requires it; do not force every screen into three font sizes if doing so harms semantics.
- Use the canonical spacing scale: 4, 8, 12, 16, 24, 32, 48, 64, 96 CSS px. A token exception requires a documented reason and reusable token proposal.
- Every element earns its place. Dense information is grouped and progressively disclosed; don't shrink type to force a desktop layout onto a phone.
- Content labels use human language. Technical states may be shown with plain-language explanation and optional detail.

### 4.4 Geometry and composition

- Horizontal boards/cards are the default for content; circles/orbs are reserved for identity, presence, small metrics, or meaningful radial instruments.
- Repetition creates rhythm; use one coherent grid, consistent alignment, deliberate spacing, and restrained variation.
- Full-width layout does not mean stretching text to unreadable line lengths. Use width intelligently: wide data zones, readable text measures, and responsive columns.
- The hero/primary focal point is dominant, not necessarily a huge headline. It may be a key metric, task, person, chart, message, decision, or creation surface.
- Use one dominant focal point per screen. Keep only the context, supporting data, and actions needed to understand or complete that screen's job.

## 5. The Screen Principle — corrected for real devices and real work

A screen is **one complete thought**, not a screenshot that must be crammed into one fixed height.

At first glance, a person should quickly understand:

1. Where am I?
2. What matters here?
3. What can I do next?
4. What will happen when I do it?

The first viewport should present orientation, one dominant focal point, essential support, and a clear next action. The rest of the page may continue vertically when the job genuinely requires it. Scrolling should reveal the next meaningful group or thought—not a random continuation of an overloaded card.

### 5.1 Four visual layers

Use these as a composition grammar, not an inflexible component quota:

1. **FOCAL** — one primary object, result, task, or insight.
2. **SUPPORT** — the smallest context needed to understand it.
3. **ACTION** — the next useful thing the person can do, with one clear primary action and at most one secondary action in the first-view action group unless the workflow demands more.
4. **AMBIENT** — quiet identity, metadata, freshness, provenance, or supporting status at the edges.

Some screens are intentionally read-only, exploratory, or data-dense. They may have no primary CTA or may expose additional actions in context. The rule is hierarchy, not artificial uniformity.

### 5.2 Viewport-fit law

**Viewport-fit means nothing important is clipped, obscured, unreachable, or forced into two-dimensional page scrolling. It does not mean every page must be exactly one viewport tall.**

- Fit the initial thought to the available viewport when the job is naturally bounded (confirmation, decision, quick status, single-step action).
- Permit normal page scrolling for reports, feeds, lists, long forms, and complex work.
- Avoid nested scroll regions by default. Use them only when they preserve a meaningful task model (for example, a large data grid) and provide clear keyboard/touch operation.
- Never place an essential action below a fixed bar that obscures it. Include safe-area insets and scroll padding.
- A fixed bottom bar must not consume so much mobile height that the user loses the focal content. Consider compact mode, contextual bars, or a menu when primary content is more important.
- Sticky headers, tabs, and navigation must not cover keyboard focus, anchors, validation messages, or the software keyboard.
- Avoid automatic horizontal scrolling for page content. A genuinely two-dimensional table or canvas may have its own explicit, accessible interaction model.

### 5.3 Screen map

Before coding, create the ordered screen map:

**ENTRY → ORIENT → PRIMARY JOB → DETAIL / SUPPORT → DECISION / ACTION → RESULT → CONTINUATION**

For each screen, record its entry condition, exit condition, back/escape behavior, scroll behavior, preserved context, and route. No dead-end screens; no orphaned actions; no unexplained route jumps.

## 6. App architecture and standard families

Every app uses a shared NayaNET shell and only the rooms its product intelligence justifies. The shell should offer consistent identity, global discovery/search where available, navigation, user context, and app-level actions. A shell is a projection, not a new source of truth.

Common app families:

- **WORLD / HOME:** identity, current state, relevant people and activity, creation door, next best action.
- **TODAY / COMMAND:** prioritized work and decisions, evidence, waiting states, and clear next steps.
- **OBJECT / DETAIL:** one person, project, space, message, booking, note, or other canonical object with its story and permitted actions.
- **CREATE / EDIT / INTAKE:** guided, voice-capable, one-question-at-a-time when appropriate, editable, recoverable, no fabricated defaults.
- **COLLABORATION:** people, roles, relationships, discussions, files, and permission-aware actions.
- **MAIL / COMMUNICATION:** conversation truth, recipient identity, draft/send/reply states, consent, delivery status, and receipts.
- **LISTS / WORKFLOW:** items, ownership, priority, status, filters, bulk action safeguards, and history.
- **REPORTS / ANALYTICS:** the question, the headline finding, trend/comparison, definitions, source/time window, caveats, and meaningful next step.
- **LIBRARY / KNOWLEDGE:** findability, preview, provenance, version, access, and reuse.
- **SETTINGS / IDENTITY:** user-controlled preferences, security, privacy, connections, and understandable consequences.

These are reusable patterns, not a mandate to ship every room in every app. A room exists when it serves a real job and has real content, permissions, and actions.

## 7. The canonical parts library

A part is not merely a copied HTML fragment. It is a versioned design capability with a defined role, provenance, behavior, integration contract, and proof.

Every Factory part record must eventually include:

- stable ID, name, family, semantic purpose, and use_when / avoid_when;
- canonical source path, source version/hash, provenance, and registry status;
- slots, properties, variants, tokens, dependencies, and compatibility;
- states: rest, hover, focus-visible, active/pressed, selected, disabled, loading, success, empty, error, unavailable, and permission-denied where applicable;
- keyboard, touch, voice, screen-reader, contrast, reduced-motion, and responsive behavior;
- visual specimen at representative widths and states;
- unit/interaction/accessibility tests and known limits;
- owner, verifier, adoption history, and supersession link.

### 7.1 Canonical reference pieces

The current Smart Factory sources identify five crowned reference exemplars. Resolve them against the current canonical index and working store at build time; the list below is the starting reference set, not a claim that every variant is production-ready on every framework:

- NAYA-BTN-009 — Reference Button / hero action.
- NAYA-BRD-001 — Reference Board / living content surface.
- NAYA-INP-008 — Reference Well / text input.
- NAYA-INP-009 — Reference Select / choice input.
- NAYA-HRO-001 — Reference Hero / title and orientation.

Use the canonical Design Blocks registry for blocks such as naya-btn, primo, orbit-btn, board, nl-field, nl-table, nl-chart, and other registered sources where appropriate. Their catalogue status does not automatically mean they are tested, compatible, or production-proven in the current target app.

### 7.2 Assembly, not arbitrary invention

Prefer, in order:

1. exact canonical part whose applicability matches;
2. canonical variant or composition pattern;
3. a small extension using documented slots/tokens while preserving invariants;
4. a proposed new part only when the registry has a real gap.

Never fork a component to avoid reading its source. Never copy a part and then silently restyle it. Never replace an existing strong part because a new Naya prefers another aesthetic. A new part must demonstrate a meaningful advantage, be tested, and be entered into the correct canonical registry under its own governance.

## 8. Functional intelligence: every control has a causal contract

Every visible control must be one of: navigation, action, input, selection, disclosure, or status. A status indicator is not a button. A decorative element must not masquerade as an action.

For every interactive control define:

**CONTROL → USER INTENT → ACTOR → SCOPE → AUTHORITY → PRECONDITIONS → CAPABILITY → EFFECT → OBSERVABLE RESULT → RECEIPT**

Specify:

- what the user expects;
- which actor acts and in which authority scope;
- the server-side capability or route that performs the work;
- what is changed, created, read, sent, or deleted;
- how success is confirmed;
- what appears during delay, offline, failure, retry, and duplicate submission;
- whether the action is reversible and how to undo;
- what is logged and what the user can inspect.

Buttons must do exactly what their labels promise. Icon-only actions require an accessible name. Destructive, financial, external-send, privacy, or permission-changing actions require safeguards proportional to consequence and explicit confirmation where warranted.

### 8.1 State contract

Every data-bearing surface handles, as applicable:

**INITIAL → LOADING → LIVE | CACHED | STALE | EMPTY | ERROR | OFFLINE | UNAVAILABLE | FORBIDDEN**

Every action handles:

**IDLE → PENDING → SUCCESS | REJECTED | FAILED | TIMEOUT**

The interface uses human-readable state labels, clear recovery, and source/freshness where it affects trust. Never call cached data live. Never present demo data as real. Never show a green live pulse just because a CSS animation is running. A zero and an unknown value are not interchangeable.

### 8.2 Data and intelligence contract

Every displayed value has:
- canonical source and query/read-model identity;
- owner and permission scope;
- meaning, unit, aggregation, and date range;
- freshness timestamp or refresh policy;
- derivation method where computed;
- known gaps, confidence, and provenance where material;
- empty, stale, offline, error, and unauthorized behavior.

Every insight explains why it matters and points to supporting evidence or a safe next action. Recommendations are not facts, predictions are not outcomes, and a score never grants authority.

## 9. Mobile-first, responsive, accessible, and fast

Responsive design is a composition problem, not a desktop page shrunk down.

### 9.1 Required viewport tests

At minimum, render and inspect:

- 320 × 640 CSS px (minimum narrow reflow);
- 360 × 800;
- 390 × 844;
- 430 × 932;
- 768 × 1024;
- 1024 × 768;
- 1440 × 900;
- 1920 × 1080.

Also test portrait and landscape for important workflows, device safe areas, virtual keyboard open, touch, mouse, keyboard, and 200% / 400% zoom. The exact width at which a layout changes is determined by content fit, not by assuming a specific phone model.

### 9.2 Responsive rules

- Start with a single logical content flow. Add columns only when each column remains useful and readable.
- Use fluid sizing and content-driven breakpoints. Prefer grid/flex and container-aware composition over fixed widths.
- At narrow widths, reorder content by user priority, not by whichever column happened to come first in desktop markup.
- Convert wide toolbars into compact, reachable actions. Do not hide critical actions in hover-only UI.
- Charts must retain readable labels and have a text/data alternative. Tables may use a deliberate compact or horizontal-scroll treatment when two-dimensional comparison is essential.
- Forms remain usable with on-screen keyboards. Labels, help, errors, and submit actions stay visible and associated.
- Avoid hover-only meaning; touch and keyboard must expose equivalent affordances.
- Respect safe-area insets, browser chrome changes, and reduced motion.

### 9.3 Accessibility baseline

Target **WCAG 2.2 AA** for all shipped web interfaces, with stricter Naya house rules where applicable:

- readable contrast: 4.5:1 for normal text and 3:1 for large text;
- Naya house target: important controls at least 44 × 44 CSS px, with adequate spacing;
- semantic HTML, landmarks, headings, labels, form error association, accessible names, and alt text;
- full keyboard operation, logical focus order, visible focus, focus not obscured by sticky UI;
- no color-only status, no motion-only meaning, no inaccessible drag-only interaction;
- screen-reader announcements for meaningful async changes, not noisy continuous updates;
- reduced-motion support and no seizure-risk flashing;
- clear language, predictable navigation, error prevention, and recovery.

The W3C criterion for minimum target size is not identical to Naya's stricter 44 px house rule. Do not describe the 44 px rule as the WCAG AA minimum; it is the project's chosen usability floor.

### 9.4 Performance and runtime quality

Use field measurement whenever available. At the 75th percentile, aim for:
- LCP ≤ 2.5 s;
- INP ≤ 200 ms;
- CLS ≤ 0.1.

Lab measurements are diagnostic, not proof of field performance. Track bundle weight, image/audio payloads, API latency, main-thread work, and loading-state behavior. Keep the first meaningful interaction fast; defer noncritical animation and content. A visual effect that harms performance or readability is a defect, not a premium feature.

## 10. App quality scorecard and hard gates

This scorecard is app/interface-scoped. It does not change the ratified NayaPOWER System Scorecard or its weights.

Rate each dimension 0–10 with evidence, scope, method, and verifier:

1. **Human value** — does this materially improve the user's world or job?
2. **Purpose and clarity** — can the user understand where they are, what matters, and what happens next?
3. **Information architecture** — are rooms, objects, navigation, hierarchy, and screen sequence logical?
4. **Visual identity and craft** — does it feel unmistakably Naya, coherent, premium, precise, and alive without visual noise?
5. **Interaction and causality** — are controls intuitive, responsive, honest, and complete?
6. **Intelligence and usefulness** — are insights relevant, explainable, timely, and actionable?
7. **Truth, privacy, and safety** — are data, authority, provenance, and risks correctly represented and enforced?
8. **Accessibility and inclusion** — can people with differing abilities and input modes use it?
9. **Responsive quality and performance** — does it work beautifully across actual viewports and runtime conditions?
10. **Reliability and evolution** — is it tested, maintainable, reusable, observable, and able to learn without creating duplicate truth?

**Threshold:** 9.0 is the minimum to call an area ready; 9.5+ is AAA; 10 is the aspiration. A weighted or average score cannot conceal a failed hard gate. Any critical defect in truth, security, privacy, authorization, broken primary journey, accessibility blocker, data loss, or production failure blocks shipment regardless of score.

For every dimension below 9.0: name the miss, corrective action, owner, and re-score condition. A self-assessment by the implementer is provisional; independent verification supplies the release recommendation.

## 11. The Naya build loop

Run in order. Parallelize work only after dependencies and file ownership are explicit.

| Stage | Naya action | Required output | Gate |
|---|---|---|---|
| 0 — RESTORE | Read current law, PI, current code, routes, previous decisions, and active work | Context receipt with refs and current commit | No build from stale memory |
| 1 — DEFINE | Distill the human job, audience, outcome, and non-goals | Human Outcome Brief | Outcome is concrete |
| 2 — INVENTORY | Inspect live routes, UI, data, capability, registry, dependencies | Reality + Preservation Map | No unknown owner hidden |
| 3 — MODEL | Define objects, relationships, journeys, permissions, sources | Product/Capability Map | One canonical owner per fact |
| 4 — ARCHITECT | Map app shell, rooms, routes, screen sequence, progressive disclosure | Experience Architecture | Every room earns its place |
| 5 — CONTRACT | Write screen briefs and action/state/data contracts | Machine-readable interface brief | Schema and semantic gate pass |
| 6 — COMPOSE | Resolve canonical parts and tokens; choose composition patterns | Part Manifest + Design Plan | IDs and sources resolve |
| 7 — BUILD | Implement the smallest complete vertical slice | Working app slice | No orphan controls or mocks |
| 8 — VERIFY | Run tests, capture viewports/states, test user journeys and negative paths | Test + Visual + Accessibility Receipts | Hard gates pass |
| 9 — CHALLENGE | Independent Naya reviews frozen commit and reproduces evidence | Independent Verification Report | No author-only proof |
| 10 — PROMOTE | Preview, obtain authority, deploy using current release mechanism | Deployment Receipt | No premature production claim |
| 11 — OBSERVE | Test production with real permissions, data, and devices | Production Observation | Real behavior confirmed |
| 12 — LEARN | Record measured outcome, regressions, reuse and lessons | Scoped learning receipt / PI update | Learning is evidenced |

### 11.1 Smallest complete slice

Build vertically through one real user journey: UI → action → authority → service → canonical data → observable state → receipt → recovery. Do not build ten attractive screens on top of a fake data path and call it an app.

### 11.2 Review rules

- The builder preserves existing behavior unless a documented change is necessary.
- Reviewer inspects the exact frozen commit, not a moving branch.
- Visual review uses real rendered screenshots at specified widths and states.
- Automated tests do not replace human visual judgment; visual judgment does not replace behavior tests.
- A failed gate changes the causal diagnosis. Do not repeat the same unsuccessful repair without new evidence.
- A production link is shared only when active, merged, and proven according to the release contract.

## 12. Living intelligence and premium data presentation

A Smart App should feel alive because it is aware of the user's actual world—not because every card glows or every number animates.

For every important data surface, answer:

1. What does this number/object mean to the user?
2. Why does it matter now?
3. What changed over the selected period?
4. Compared with what baseline?
5. What is the source and freshness?
6. What is missing or uncertain?
7. What should the user do next, if anything?

Use the right representation:
- single value → metric with unit, context, and direction;
- change over time → line/area chart with dates and clear scale;
- comparison → aligned bars or table;
- composition → proportion/donut only when parts sum meaningfully;
- sequence → timeline or journey funnel;
- status across work → clear state list/board;
- relationship → network/constellation only when relationships are meaningful and navigable.

Never use a gauge just because it looks impressive. Never animate a value as if it is changing in real time unless the source actually updates in real time. Provide an accessible text summary and data alternative for visualizations.

## 13. Franchise consistency without cookie-cutter apps

The Factory standardizes:
- identity, tokens, depth, lighting, typography, icon grammar, navigation principles;
- component behavior and state language;
- privacy, truth, accessibility, responsiveness, and release gates;
- component provenance and quality evidence.

The Factory does **not** standardize:
- every app's information architecture;
- the number of rooms or cards;
- every hero, chart, or visual composition;
- business logic or permissions;
- all user journeys into one generic dashboard.

Each app gets a distinct PI-backed experience plan. Brand consistency is carried by the design grammar; product quality is carried by the fit to the user's actual job.

## 14. What the Factory must measure

Track factory throughput and actual user outcomes separately.

**Factory measures:** time from complete brief to working preview; percentage of builds assembled from canonical parts; registry resolution failures; failed tests by class; visual regression rate; rework caused by missing PI; independent verification pass rate; deployment failure rate; component reuse with verified compatibility.

**User measures:** task completion; time to successful completion; errors and recovery; repeated effort; search success; comprehension of important data; accessibility issues; perceived trust; usefulness of recommendations; retention only where appropriate and consented.

Never optimize for screens produced, components consumed, commits, clicks, AI tokens, or animation count as proxies for human value. Measure benefit, harm, cost, risk, and user effort.

## 15. Immediate implementation sequence

The blueprint is the operating language. The next engineering steps are deliberately staged:

1. Adopt this brief schema and validator as a **pre-build design gate** alongside—not instead of—the existing 13 standard-feature contracts.
2. Create one end-to-end reference brief for a bounded NayaNET app journey (Personal World / Today) and validate it against the live piece registries.
3. Build a reference screen gallery with each canonical part rendered in rest, hover, focus, pressed, disabled, loading, and error states.
4. Wire the new pre-build brief into the current factory dispatcher only after compatibility tests prove it preserves current build contracts and fail-closed behavior.
5. Run one real generated app from PI through preview, mobile/desktop verification, independent review, and production observation.
6. Measure the first ten builds; promote only proven reusable patterns and update the protocol from evidence.

**Do not begin by rewriting the entire Factory or replacing its templates.** Preserve its live contracts and generators. Add the missing operating language and a bounded gate first; integrate incrementally.

## 16. Acceptance of this operating layer

This V1 is ready for team trial only when:

- the schema parses and the validator's positive/negative tests pass;
- a valid brief resolves current project, screen, part, source, state, and acceptance fields;
- an intentionally incomplete brief fails closed with actionable errors;
- the sample brief passes without invented live state;
- a cold Naya can use the document and sample to produce a correct screen plan;
- one bounded preview is visually inspected at narrow and wide viewports;
- independent review identifies no critical truth, privacy, behavior, accessibility, or responsive blocker.

This file alone does not establish those implementation results. Record each in the accompanying PR and later implementation receipts.
