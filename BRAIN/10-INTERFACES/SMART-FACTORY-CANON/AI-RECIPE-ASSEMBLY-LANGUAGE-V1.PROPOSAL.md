# NayaNET — AI Smart-App Assembly Language (REVIEW PROPOSAL V1)

**2026-10-31 · Shawn's design direction, interpreted as a bounded engineering interface · NOT RATIFIED · NOT DEPLOYED.**
**Current owner:** existing Nitro / Resolve / Power Factory, Design DNA and Dashboard lanes. **No new renderer, database, component library, agent bus or Hub is authorized by this file.**

## What we are creating

A human describes a useful goal. NayaPOWER supplies governed intelligence, identity, permission and continuity. NayaNET supplies one connected Personal/Business/Space world. The **existing Smart Factory** uses current approved parts to construct a beautiful, working, useful app, while an independent verifier proves the real result. This is a proposed **interoperability language**, not a competing implementation.

**Assembly sentence: `RECIPE + PARTS + SHELL + DATA + GATE → AUTHORIZED HUMAN OUTCOME`.**

- **RECIPE:** authoritative PI child record, exact project and source version, audience, user job, human outcome, screen/SCENE cards, clear acceptance and owner.
- **PARTS:** current model IDs, status, working import source and states. `BRAIN/10-INTERFACES/SMART-FACTORY-CANON/CANONICAL-PIECE-INDEX.json` governs lifecycle. `pieces.json` is the actual working store. Canonical + present means eligible to evaluate, **not production-qualified**; retired/superseded/missing ⇒ DENY new builds without deleting historical references.
- **SHELL:** the existing approved NayaNET chrome, Smart Bars, identity, global context, safe insets, layout grammar and responsive behavior. Never duplicate the shell or invent a personal credential system.
- **DATA:** real source and event lineage, identity scope, permissions, time/units, freshness, write behavior, idempotency, honest loading/error/empty/denied states, actual persisted result.
- **GATE:** read-only structural preflight, actual render on phone/tablet/desktop, real-action tests, negative security tests, independent different-seat scorecard, exact source/deployed SHA, PI evidence and cold-successor restoration.

## A standard SCENE card

`SCENE(id, human_job, hero, context[0..3], primary_action, optional_secondary, ambient_provenance, part_ids, data_refs, states, viewport_and_safe_area, proof, next)`

**Human test in two seconds:** What am I seeing? Why does it matter? What useful action can I take? One strong hero and one useful primary action should be immediately understandable in the **actual usable viewport after fixed chrome**. Complex record content and accessible explanations may scroll naturally; never impose a blanket no-scroll law, hide a critical action, reduce ordinary body text below the ratified floor, or break reflow to force a viewport-fit screenshot.

## Naya physical language

This file **inherits** the ratified `BRAIN/10-INTERFACES/NAYA-DESIGN-CONTRACT-V1.md` and `BRAIN/10-INTERFACES/NAYA-DESIGN-ANATOMY/` human/AI/machine canon. It introduces no alternative palette, physics, typography or component primitives.

Every Naya element is a useful object with **purpose → semantic role → current approved part → layered obsidian depth → white readable content/rim → own-color interaction feedback → actual states → authorized action/data → accessible responsive geometry → evidence**.

Buttons rise, inputs sink; boards contain one meaningful subject; icons have unique meaning; charts present **magnitude + shape + direction + a human sentence**, plus period, scope, provenance and real drilldown. Animated data may change only from actual data or meaningful interaction. Dead buttons, false LIVE badges, invented stats, fake success messages and unauthorized sharing veto release.

**Do not silently reconcile contradictory lawful-looking values.** Current Design Contract v1.2 has a seven-token spectrum and body 16px floor; a newer Anatomy tongue shortens the walk and permits 14px details; selected-state wording also differs. Existing design owners and human authority must reconcile this *at the canonical source* before enforcing disputed details as code.

## The existing-team execution protocol

1. Integrator refreshes main, boot, constitution, mission, PI and ownership. No cold worker starts from a stale summary.
2. Intent designer writes one human outcome and full RECIPE; never 25 speculative parallel projects.
3. Experience director gives each SCENE a proper hero, meaningful context, action placement and data visual—not stock dashboard cards.
4. Parts librarian resolves actual current canonical IDs and importable working-store entries; refuses the wrong lifecycle.
5. Builder composes within the **current source seam**; binds real scoped data and actions; never duplicates CSS or governance.
6. Device/UX specialist inspects exact rendered HTML at **320×700, 390×844, 768×1024, 1440×900**, landscape, 200/400% zoom, touch, keyboard, screen-reader, reduced-motion and safe-area behavior. Existing first-screen audit **draft PR #3144** is a bounded candidate instrument for the Dashboard.
7. Different-login verifier proves persistence, authentic receipts, owner-to-owner DENY, errors, performance, and tested/deployed bytes; builder is not judge.
8. Continuity steward saves source SHA, truth classification, actual improvement, lessons, blockers and one next authorized move in PI and the official board/mail paths.
9. Repeat with a second app using the exact approved parts; time first render, first useful action and independently qualified release separately. Aim for **under ten minutes** for suitable templated cases, with three minutes only a *measured research target*.

## Machine-readable companion contract

Proposed **`NAYA_APP_RECIPE_V1`** carries exactly: `contract`, `version`, `build_status`, `project_intelligence`, `recipe.scenes`, `parts`, `shell`, `data.datasets`, `data.actions`, `gate`. Each scene references actual declared parts, data and actions. Two modes:

- **DRAFT:** structural correctness, present canonical parts and known gaps can pass; unwired actions and unverified authority remain loudly marked OPEN.
- **RELEASE_CANDIDATE:** require bound actions, real permission and proof references, separate verifier, exact source/deployment match, no unresolved placeholders. A JSON pass is **never itself** evidence that services, privacy or visual quality work. Those proofs must be independently reproduced.

Proposed falsifiers: retired `NAYA-BTN-034` ⇒ DENY; superseded `NAYA-INP-001` even though stored ⇒ DENY, suggest canonical `NAYA-INP-008`; verified but not importable `NAYA-BRD-031` ⇒ NOT ELIGIBLE; canonical `NAYA-BTN-009` is eligible to evaluate, not automatically live-approved; invented action names and missing 320px viewport ⇒ DENY.

## Quality and no-go

Eight established dimensions: visual, function, intelligence, honesty, performance, reliability, accessibility and craft. **10/10 goal; 9.5+ AAA target and independently passed gates**. A score cannot average away failed permissions, false data, clipped primary action, nonfunctional main control, inaccessible flow, unreviewed source or mismatched deployment.
