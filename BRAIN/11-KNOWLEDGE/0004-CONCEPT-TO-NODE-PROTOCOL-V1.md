# Concept → Intelligent Node Protocol V1

**Status:** CANONICAL SPECIFICATION — deterministic promotion/rejection protocol

The temporary Concept series becomes input to the permanent intelligence chain.

```
CONCEPT SOURCE
→ EXTRACT
→ DISTILL
→ TYPE
→ RECONCILE
→ CONNECT
→ PROVE
→ PROMOTE
→ INDEX
```

One conversation may produce zero, one, or many canonical objects. The system must not force a whole conversation into one Node.

## Candidate envelope

Every candidate MUST identify:

- stable candidate ID;
- source reference(s);
- distilled proposition;
- proposed type;
- intended purpose;
- epistemic state;
- applicability;
- proposed relationships;
- authority implications;
- proof requirement;
- candidate disposition.

## Deterministic decision table

| Condition | Disposition |
|---|---|
| durable + supported + non-conflicting | PROMOTE candidate |
| duplicate semantic object | MERGE with lineage |
| replaced by newer supported understanding | SUPERSEDE |
| useful source but not durable intelligence | RETAIN-AS-SOURCE |
| obsolete historical understanding | HISTORICAL |
| evidence directly conflicts and is unresolved | CONTRADICTED |
| insufficient evidence to decide | UNKNOWN |
| intentionally non-canonical material | ARCHIVE |

## Rejection law

A candidate MUST NOT be promoted because it is eloquent, recent, frequently repeated, or machine-readable.

If required evidence is absent, emit a rejection/failure receipt and retain the candidate/source lineage for later reconciliation.

## Human instruction boundary

The human may explicitly request:

> “Naya, preserve this”

or

> “Naya, make a Node from what matters here.”

That request authorizes preservation intent; it does **not** override type validation, provenance, privacy, authority, contradiction or proof requirements.

## Completion

A promoted object is not considered VERIFIED merely because it passed population. Verification remains an independent proof state.
