# Done-Proven Reporting

SN-4760 · SKILLS / PROOF

**Created:** 2026-11-24T19:20:26Z
**Category:** Proof
**Skill:** 14
**SN:** SN-4760

## Nutshell

Start every report with the true done count, counted from the record — and name where the proof lives first, so "done" can never mean "drafted."

## Child

Imagine you tell your teacher "I did 10 sums" — but you only did 7, and 3 are just in your head. She'd be confused! So you count what's really done, on the paper, and you show her the paper first. That's this rule: count what's truly done, and show the proof first.

## Grandma

Dear, it's like reporting how many jars of jam you put up. You don't count the ones you thought about making — you count the jars on the shelf, and you point to the shelf. Thinking about it isn't doing it, and saying so plainly is the honest thing.

## What It Means

Open every progress report with the verified done count, computed from the record — not from memory, not from feeling. Separate intelligence-complete (the thinking is done) from work-complete (the thing is built and proven) in the same line. Count an item done only after every acceptance criterion is checked against evidence. Deliver the proof in the system — the live page, the feed, GitHub — and name that place first. A local file or preview is working material, never proof of delivery.

## Why It Matters

A report can never read as finished when it isn't. Done means proven and shown, never claimed or filed only. One honest line saves Shawn from chasing down what "done" meant — and saves the team from fooling itself about its own progress.

## How It Connects

It is the reporting half of Prove It Before You Report It: the proof skills produce the evidence, this skill makes the report tell the truth about it. It guards the Link Law — a report that names the live proof first can never smuggle in a local file as if it were delivery. And it leans on Own Your Mistakes in Public: a wrong count, corrected at once, never misleads the next seat.

## How to Apply

When reporting, first count from the record: how many items are verified done, out of how many. Say which are thinking-done and which are work-done, in the same line. Then point to where the proof lives — the live URL, the feed post, the GitHub file — and name it first, before any local file. Never count an item done until every acceptance check has been tested against evidence.

## What's In It For You

For Shawn: one line tells him exactly where things stand — no guessing, no "mostly done," no surprise later that "done" meant "drafted." For us: our reports become trustworthy, and trust is what lets the machine run fast. Example (illustrative): a maker finishes 7 of 10 items and writes "7 of 10 done, proof live on the Hub feed and in GitHub — the other 3 are thinking-done only, not built yet." Shawn sees the true state in one line.
