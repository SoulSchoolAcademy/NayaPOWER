## 🟣 CHILD NOTE

Imagine you and a friend both have the same notebook, and you each copy the whole notebook, add your own line, and put your copy back. Whoever puts theirs back last wins — the other person's line is gone, and nobody tells them. That is what happened to the shared-state file: the dispatcher added its lines, but another writer put its copy back after, and the dispatcher's lines disappeared. The fix is easy: after you put the notebook back, open it again and check your line is still there. If it is not there, your write did not happen, no matter what you wrote in your diary about it. And until there is one notebook-keeper instead of two, the dispatcher simply does not write those lines at all.

This note's evidence is a confirmed loss with before/after: t3417's log claims throttle_t3417/cite_t3417 added and last_night_dispatcher_tick → t3417; the t3418 live read shows both keys absent and the tick stuck at t3414 (20:47Z). The rotation file repeats it one tick later (t3418's claimed keys absent at t3419; only tick_count landed). The mechanism has three legs. First, whole-file rewrite: both writers read the file, modify in memory, and write the whole file back — there is no merge, no lock, no re-fetch, so the last writer's snapshot silently replaces the earlier writer's delta. Second, silent success: the loser's own log records the write as landed (both t3417 and t3418 logs claim their keys added), so nothing in the writer's own telemetry contradicts the loss — only an independent re-read catches it, which is SN-1995's read-back rule applied to the state file. Third, cadence overlap: the director pass (every 30 min) and the dispatcher (every ~10 min) both write the same file on overlapping schedules, so the collision is structural, not a one-off. The standing mitigation is the t3405 skip rule — the dispatcher writes no shared-state keys (in force t3418, t3419) — and the owed root repair is a single-writer or atomic-merge path for the state file.
