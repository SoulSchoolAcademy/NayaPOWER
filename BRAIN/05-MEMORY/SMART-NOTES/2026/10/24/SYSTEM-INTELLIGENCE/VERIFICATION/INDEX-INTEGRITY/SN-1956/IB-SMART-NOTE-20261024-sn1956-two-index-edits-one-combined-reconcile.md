## 🩷 HUMAN NOTE

Think of the index as a sealed box with a wax seal stamped on it. The seal is the manifest hash: it proves exactly what is inside the box. Now imagine two people each open a copy of the box, change what is inside, and stamp a new seal on their own copy. Each seal is perfectly correct for its own copy — but there is only one box in the end. If you take the first person's sealed box and put it on the shelf, then take the second person's sealed box and put it on top, you have not combined anything: you have just overwritten one seal with another, and nobody has ever checked the box that results from both changes together. That is what happened with the two pull requests: both edited the same index, both carried a different seal, and the combined result had never been verified. The fix is not to be faster at landing them one by one. It is to stop, put both sets of changes into one box together, stamp one fresh seal on that combined box, and verify that seal before anything lands.

Put both changes into one list together, stamp one fresh seal on that combined list, and check that seal — before either change is accepted on its own. One list, one seal, one check. Never two landings for one list.

## 🟠 NAYA NOTE

This is the concurrent-edit sibling of the manifest-staleness family, and the distinction is what makes it a new lesson rather than a restatement. SN-1866 proved a single filing can be stale when its regen never recomputes the manifest hash; SN-1868 proved a guard can be stale when it recomputes only on the append path and never on the edit path. Both are one writer, one seal, one broken recompute. The #3036/#3037 hazard is two writers, two seals, and no broken recompute at all: each filing may be internally correct, and the combined state is still unverified, because a whole-index seal is a claim about the entire entry set at once. Merging the first PR changes the entry set the second PR's seal was computed against, so the second PR's seal is stale the moment the first lands — not because anyone skipped a step, but because seals do not compose. The enforcement therefore cannot be "recompute harder on each PR"; it has to be a merge-lane refusal: while another open PR touches the same index.json, neither PR lands alone, and the only landing vehicle is the combined reconcile (single index, regenerated manifest, VERIFY at an exact SHA). The disposition detail matters for a cold successor: both PRs stayed open past a four-hour disposition clock with disposition held by the Integrator/merge lane — this is a merge-lane decision, not a filing-lane repair, and the hazard stays open until the combined reconcile lands, however long that takes.
