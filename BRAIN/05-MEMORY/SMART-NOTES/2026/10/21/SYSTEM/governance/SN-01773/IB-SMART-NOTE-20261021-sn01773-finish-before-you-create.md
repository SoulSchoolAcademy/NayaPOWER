# Finish Before You Create: Complete the Open Work Before You Make More

**ID:** IB-SMART-NOTE-20261021-sn01773-finish-before-you-create
**Created:** 2026-10-21
**Category:** SYSTEM / Governance

## IN A NUTSHELL

Shawn's word, 2026-10-21 ~10:36 PDT, clarifying his pull-request directive from earlier the same morning (~09:18 PDT) after it was misheard as something about "poll requests" and reviews: he did NOT say "no pull requests," and he is not asking for a freeze on creating them. He said: get every open pull request finished and completed until the count is zero — no pile of pull requests waiting. And the real message underneath, in his words: "don't create more work until the work is done." The failure pattern he is naming: the team goes and creates more work — new pull requests, new efforts — without completing the work already open, so the open pile grows and nothing ever reaches done. Zero is reached by COMPLETING, not by avoiding. The order of work for every seat: do the work you are supposed to do — finish the open pull requests first — and only then create new work, which is created to be finished, not to be added to a pile.

## HUMAN

Think of a kitchen counter covered with half-made sandwiches. Nobody can eat a half-made sandwich, and every new one somebody starts makes the counter worse. Shawn's rule is simple: finish the sandwiches on the counter. Hand them out. Get the counter clear. THEN start making more — and when you start one, you finish it. The problem was never that the team makes sandwiches. The problem is forty started and none served.

## CHILD

Finish the puzzle that's already on the table before you open a new box. If you keep opening new boxes, you end up with pieces everywhere and not one finished picture. Done pictures are the point — not opened boxes.

## GRANDMA

It's like a good cook on a Sunday, dear. She doesn't start the potatoes, the roast, the pie, and the soup all at once and leave every pot half-done — the meal that matters is the one that reaches the table. She finishes one dish properly, serves it, and then begins the next with a clear counter and a clear head. A table full of finished food feeds people. A kitchen full of beginnings just makes a mess that somebody still has to clean.

## NAYA

Standing law from Shawn's word (2026-10-21 ~10:36 PDT, chat, clarifying his ~09:18 PDT directive): (1) The open pull-request count is driven to zero BY COMPLETION — merge what is proven at the bar, fix what is fixable, close what is proven dead — never by leaving them sitting and never by a ban on creating. (2) The creation gate: while open pull requests exist that a seat could be advancing, that seat does not open new pull requests or start new work streams; its capacity goes to the unfinished work first. (3) A new pull request is opened only as the vehicle for work that will be carried to done — a pull request is a promise to finish, not a parking spot. This sharpens the no-queue law (2026-10-21 ~08:36 PDT) and its issues+PRs extension (~09:19 PDT): those said no backlog; this one names the mechanism that CREATES the backlog — starting new work ahead of finishing old work — and bans the mechanism, not the work. Standing venues that stay open by function (the live board, the master directive, mission state, the scoreboard) are the workplace, not backlog, and are untouched by this law.

## MACHINE

Rule: for any seat holding open pull requests it can advance, new work creation is gated behind completion — capacity flows to the oldest completable open pull request first (merge at the bar, fix, or proven-dead close), and a new pull request may be opened only as the vehicle for work that will be carried to done in the same push. Decision change: dispatch order is finish-first by law; the open pull-request count is driven to zero by completions and kept at zero, re-derived from live GitHub bytes every time it is cited, never asserted from memory. Mechanism: unfinished work compounds — every open pull request holds context, review attention, and rebase debt against a moving main, and each new one opened dilutes the capacity that would have finished the earlier ones, so creation-ahead-of-completion is the engine that manufactures backlogs; completion converts the same capacity into closed, verified value and frees the context entirely. Falsifiability: a new pull request that is itself the completion vehicle for existing work (a fix that must land as its own pull request, a carrier replacement like PR #2828 replacing the closed #2468) is inside the law, not an exception to it; the law is re-decided only on evidence that finish-first ordering measurably blocks a higher-value completion. Enforcement: the continuous count discipline of the no-queue law — a seat that opens a new pull request while completable pull requests sit idle is out of law and the new work is paused until the older work is carried. Provenance: Shawn Vibert, spoken 2026-10-21 ~10:36 PDT in the main chat, clarifying his ~09:18 PDT directive after it was misheard. Cross-references: the no-queue law and its issues+PRs extension (MEMORY.md, 2026-10-21); SN-01769 (resolved is a proven state, not an asserted one — the closeout-semantics cousin); SN-01768 (retire by proof, not by paper).

## WHAT IT ALL MEANS

This law names the engine underneath every backlog the system has ever had. A queue is never created by the work itself — it is created in the gap between starting and finishing, every time a seat reaches for something new while something open waits. Banning the backlog (the earlier law) treats the pile; this law treats the behavior that piles: creation is the easiest, most rewarding-feeling motion in the system, and completion is the only one that produces value anyone can use. It also protects the meaning of the number zero. Zero open pull requests reached by avoidance would be a frozen system hiding from work; zero reached by completion is a system that finishes everything it touches — the counter is clear because the work is done, served, and in the world. That is the difference between a team that looks caught up and a team that is caught up, and it is why this clarification had to be captured in Shawn's own words: the mishearing ("no pull requests") would have frozen the very motion the law exists to direct.

## WHAT'S IN IT FOR YOU

For Shawn: the counts you watch actually fall for the right reason — work finishes, lands, and clears, instead of new work quietly routing around the old. You stop hearing what the problem is for days, because the team's first move is now the completion in front of them. For every Naya: a clear counter is freedom — finished work frees its context entirely, so the next task starts clean instead of competing with forty half-held threads, and a new pull request you open carries a simple honor: it exists to be finished. For everyone who uses the Hub: finished work is what shows up — completed, verified, usable — instead of a growing museum of almost.

## HOW IT APPLIES

When any seat is about to start something, run three checks in order. **Is there open work I can advance?** → advance the oldest completable pull request first: merge it if it is proven at the bar, fix it if it is fixable, close it if it is proven dead — with the proof, never the assertion. **Am I opening this new pull request as a parking spot?** → if the honest answer is yes, stop; a pull request is a promise to finish, opened only for work that will be carried to done in the same push. **Is the new pull request actually the completion vehicle for old work?** → a fix that must land separately, or a carrier replacing a closed one, is inside the law — name that in the body so the count tells the truth. Living example: this note itself. It was staged on the carrier branch this morning, where the Hub cannot see it; under this law's own spirit — finish the work, don't admire it — it was carried the last step onto main the same day it was spoken, in the canonical nine-section form the Hub sync reads, so the lesson is live instead of filed.
