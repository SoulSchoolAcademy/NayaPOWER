## ✦ IN A NUTSHELL
A Project Intelligence count quoted without its filter is not a number — it is a trap. On 2026-10-26 the canonical table (work_items: 364 rows, 339 distinct keys) and the legacy table (project_intel_items: 281 rows, 254 keys) were joined two ways: whole-table, matched by item_key only, gives 184 canonical keys missing from legacy, 99 legacy keys missing from work, and 79 state-conflict keys; the project-scoped subset gives 188 missing, 8 stale, and 13 conflicts. Both are "right" under their filters — and /pi reads the canonical table while /projects reads the legacy projection, so the two faces disagree by construction until the projection is unified. Rule: every PI count quote names its filter, both tables' row and distinct-key counts, and which face reads which table — or it is struck from the report.

## 🩷 HUMAN NOTE
Imagine two people counting the same warehouse: one counts every shelf in the building, the other counts only the shelves in one aisle — and then they argue about whose number is "the" count. Neither is lying; they just counted different things and forgot to say so. Add a second problem: the shop window shows one person's count and the back office shows the other's, so customers and staff see different truths. The fix is a label on every number — what was counted, from which shelves — and one day, one warehouse list that both windows read.

## 🟣 CHILD NOTE
Imagine you and your friend both count the toys in the playroom, but you count all the toys and your friend counts only the red ones — then you argue about how many toys there are. You are both right about your own count, but wrong to argue, because you counted different piles. So whenever you say a number, you have to say which pile you counted. And if two signs show different numbers, check whether they are looking at different piles before you believe either one.

## 🔵 GRANDMA NOTE
Dear, it is like two kitchens keeping two different recipe boxes for the same family — one box has all the recipes, the other has only the ones someone copied over, and some of those copies are out of date. If you ask "how many recipes do we have?" you will get two answers, and both will sound sure of themselves. So always ask: which box did you count, and how many cards are in each box? And until both kitchens cook from the same box, expect the menus to disagree.

## 🟠 NAYA NOTE
Cold successor, never quote a PI count bare, and never quote one face's count as the job count. The divergence on 2026-10-26 is structural, not a measurement error: a scoped join silently subsets rows before the join, so the "missing" figure changes with the filter (184 whole-table vs 188 scoped), and the state-conflict figure changes even more (79 vs 13). The scoped figures are a subset story; the whole-table figures are the full story; neither may be quoted as if it were the other. Until the legacy projection is retired or unified with the canonical table, /pi and /projects will keep disagreeing, and the honest sentence is always: "under filter F, table A (rows/keys) vs table B (rows/keys) gives X" — plus which face reads which table. The parity audit (tools/reporting/project_content_parity.sql) is the check that runs before any PI count is quoted as a job count.
