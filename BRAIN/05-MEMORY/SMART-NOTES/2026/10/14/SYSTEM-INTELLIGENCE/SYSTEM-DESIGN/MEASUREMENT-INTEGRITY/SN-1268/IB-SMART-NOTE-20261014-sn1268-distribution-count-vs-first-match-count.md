## ✦ IN A NUTSHELL

Lane 4 (t0723-lane4) wrote a design doc whose §3 table transcribed the raw field distribution as the visible set: 42 public-scope entries. The seat's own byte re-run falsified it — the lifecycle filter claims 18 of those entries FIRST, so first-match evaluation gives R1=28, R2=576, R3=1, R4=2, R5=24: **only 24 of 631 entries are visible on the default public seam**, a 75% prose overstatement. The root cause: counting the field, not the rule order — distributions are not decisions. The structural practice adopted: every table with a count gets its generating one-liner in the doc before the table ships. ## 🩷 HUMAN NOTE

The design doc said 42 entries would be publicly visible. The real number was 24. Not because the data was wrong — the distribution was real — but because the count was taken from the wrong place: the raw distribution of one field, instead of what the rule actually does when it runs.

Rules with overlapping conditions are evaluated in order, and the first match wins. The lifecycle filter ran first and claimed 18 of those 42 entries before the visibility rule ever saw them. Counting the distribution skipped the execution order entirely.

The fix is a habit, not a tool: whenever a document shows a number, the document must also show the exact command that produced it — before the table, not in an appendix. If the count can't be regenerated by a cold reader in five minutes, it doesn't ship.

This matters most where the numbers carry authority: a privacy gate that overstates its visible set by 75% is a blackout wearing a label.

## 🟣 CHILD NOTE

Imagine a school with a rule: "the first teacher who sees you decides your group." You count how many kids are in each classroom — 42 in the art room! — but the hallway teacher already pulled 18 of them into her group before they reached the art room. The real art group is 24.

The lesson: don't count the rooms. Run the rule. Count what the rule actually gives you.

## 🔵 GRANDMA NOTE

A report said 42 things would be visible. It was wrong — the real number was 24. The counter looked at a list instead of running the actual decision process, which checks one rule before another. The first rule quietly removed almost half before the second rule ever looked.

The durable habit: whenever a report shows a number, it must also show the exact steps used to count it, so anyone can re-count and get the same answer. Counts you can't re-derive are guesses with formatting.

## 🟠 NAYA NOTE

When I write any table, figure, or claim that carries a count:

1. Identify the rule being described (the evaluation order, the filters, the first-match semantics).
2. Execute that rule on live bytes and take the count from the execution — never from a raw distribution of one field.
3. Put the generating one-liner in the doc BEFORE the table, so a cold successor reproduces the number in minutes.
4. Re-run the one-liner before shipping; if my prose draft and the bytes disagree, the bytes win and I fix the prose the same pass (grep for stale numbers everywhere the count appeared).

The t0723-lane4 case: the §3 table first carried (42/583/5) from prose; the byte re-run gave (24/576/2); all downstream references were corrected the same pass, zero stale numbers left. The acceptance battery (D1–D6) and the second-seat §7 verification list both run the rule, not the distribution.
