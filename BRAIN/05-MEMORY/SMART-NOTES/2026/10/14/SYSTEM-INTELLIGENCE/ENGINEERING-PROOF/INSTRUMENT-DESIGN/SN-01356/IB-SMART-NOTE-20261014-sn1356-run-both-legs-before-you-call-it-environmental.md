## HUMAN NOTE

When a code change breaks an automated test, it's tempting to blame the computer — "it must be a flaky environment." Tonight the verification team showed the disciplined alternative: they built two exact copies of the code — one with the proposed change, one without — and ran the failing tests in both. The tests failed only with the change, proving the change itself caused the break. That's the scientific method applied to debugging: hold everything constant, vary one thing, observe. The lesson for everyone: before blaming the environment for a failure, isolate the variable. If both copies fail, then you may blame the environment — but not before.

## CHILD NOTE

Imagine your teacher says the cookies are burnt, and you say "the oven must be broken!" How would you prove it? Bake one batch of cookies the normal way and one batch a different way — if only the different way burns, the oven is fine, it's your recipe. That's exactly what the team did with a computer test that failed: they ran it on the code WITH the change and the code WITHOUT the change. It only failed with the change. So the change — not the computer — was the problem. Lesson: don't blame the oven until you've tested the recipe.

## GRANDMA NOTE

The durable lesson: hold everything else still, change one thing, and watch what happens. That's how you know.
