## ✦ IN A NUTSHELL
A sync that is not re-run against its own output is a claim, not a proof — and a partial sync can make the gate worse. The board rotation from #2793 to #3066 was supposed to clear stale pointers by syncing main's mission-state file from the snapshot branch. Re-running the fixed boot-pointer gate three ways measured the opposite of the intention: fixed gate vs unsynced tree, 9 stale pointers; fixed gate vs synced tree, 10. The sync removed 1 old mission-state violation and added 2 of its own, because the snapshot's own migration line names #2793 twice on a line carrying no dead-word, so the gate counts it twice. The 8 activation-file violations never moved. The lesson is mechanical: validate a repair and a sync against the post-fix, post-sync bytes — count before, count after, and require the count to fall. A sync that only "leaves DEGRADED" is not a pass, and a sync payload that itself violates the gate is not a fix.

## 🩷 HUMAN NOTE
Imagine you are tidying a room by replacing an old map on the wall with a new one — and the new map itself has the old address written on it twice, in a footnote nobody marked as "old." You took down one wrong address and put up two. That is what happened here: the snapshot file meant to replace the stale mission-state file carries its own migration note naming the retired board twice, without the word that tells the gate "this mention is historical, not live." The gate counts what it sees, not what you meant, so the count went from 9 to 10. The fix is not to try harder; it is to measure: run the gate on the tree after the sync, compare the count to before, and refuse any sync that raises it. And never call "it no longer crashes" a pass — the gate leaving its confused state is the start of the check, not the end of it.

## 🔵 GRANDMA NOTE
Dear, this one is about measuring a fix instead of trusting it. The team needed to replace a stale file that pointed at a retired board, using a fresher snapshot. The snapshot was fresher — but its own migration note mentioned the retired board twice without marking those mentions as history. The checking gate counts every unmarked mention, so after the swap the count rose from nine to ten: one old problem gone, two new ones arrived in the very file meant to fix things, and eight other stale pointers in the activation files never moved at all. So the standing rule is plain: never accept a swap on its intention. Run the check on the swapped tree, compare the numbers before and after, and require the number to fall. A check that stops being confused is not a check that passes — only a clean run, exit zero, is a pass.
