## ✦ IN A NUTSHELL
Test a gate against the input's actual bytes, not the format you assumed. The boot-pointer gate's LIVE_BOARD_RE tolerated bold and whitespace after "board" but not a colon — while the snapshot it polices writes "Live board: #3066" in colon form. The gate therefore went DEGRADED (exit 1, no evaluation) on a phrasing miss, and the real violation — main's mission-state file still the 2026-10-22 version naming retired board #2793 — hid behind the same DEGRADED label. The gate author encoded the format they remembered; the writer's format varied along a dimension the author never enumerated. A gate tested only on hand-written fixtures will always carry this hole, because fixtures are written from the same memory that wrote the gate. The rule is mechanical: every gate change ships with a test run against a current copy of the input it polices, and the accepted-phrasing set is pinned in a comment naming the forms tested.

## 🔵 GRANDMA NOTE
Dear, this one is about testing a checker against the real thing instead of your memory of it. The team has a gate that checks whether files still point at a retired board. The gate was written to recognize the phrase "Live board" followed by a number — but the real file writes "Live board:" with a colon after "board," and the gate had never been taught the colon form. So the gate stopped, confused, and reported itself broken — and while it was stuck, the actual stale file it was supposed to catch sat there uncaught. The standing rule is plain: whenever you change a checker, run it on the real file it checks, not on examples you made up. Examples you make up share your blind spot; the real file does not. And pin the list of accepted spellings in a comment next to the checker, so nobody has to guess what it accepts.
