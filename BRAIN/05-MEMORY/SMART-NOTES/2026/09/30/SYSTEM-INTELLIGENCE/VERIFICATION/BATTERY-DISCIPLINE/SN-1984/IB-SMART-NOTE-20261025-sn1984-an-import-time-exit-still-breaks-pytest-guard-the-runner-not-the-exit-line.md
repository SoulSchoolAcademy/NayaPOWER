## ✦ IN A NUTSHELL
A file that exits 0 at import still breaks pytest: `SystemExit(0)` looks like success in a shell, but at collection time pytest treats ANY exit signal as an INTERNALERROR — the exit code you see depends on who imports you. The named gap was a test/check file, `tools/test_check_merge_consensus_lane_tags.py` on the #2460 branch, that ran its whole 30-check battery at import and ended with `sys.exit(...)`. Importing it ran 39 output lines and raised `SystemExit(0)`; under `python -m pytest -q` it produced exit 3 with INTERNALERROR and "no tests ran". The fix that holds is moving the work into `main()`, not wrapping the last line: a script moved all 30 top-level `check()`/`e2e()` calls and the summary print into `main()` in original order, replacing the trailing exit with `if __name__ == "__main__": sys.exit(main())`. The guarded file imports silently (`PASS=0, FAIL=0`, no battery, no exit signal), runs standalone byte-identically (30 passed), and under pytest gives exit 5 ("no tests ran") with zero INTERNALERROR lines; a forced-fail control exits 1 with "30 passed, 1 failed", so the guard returns failure instead of masking it. Guard the runner, not just the exit line: the battery itself was the side effect, not only the final `sys.exit`.

## 🩷 HUMAN NOTE
Imagine a recipe card that, the moment you pick it up to read it, starts cooking the whole meal and then announces "done!" — even if you only wanted to check one ingredient. In a shell, that announcement looks like success. But pytest does not pick up a file to "read" it the way you do: when it collects tests, it imports the file, and any exit signal during import — even a successful one — is treated as an internal error, because a file being collected should never decide to exit. The lesson is simple and general: a file must be safe to import. Reading it must do nothing but define things. The actual work belongs behind a `main()` door that only opens when the file is run directly. Wrapping the last exit line is not enough, because the battery running at import was the problem, not just how it ended.

## 🟣 CHILD NOTE
Imagine a toy box that, every time you open the lid just to look inside, dumps all the toys out and then shouts "all done!" That is fine if you wanted to play, but not if you only wanted to peek. Pytest peeks inside files to find tests, and if the file dumps everything out and shouts "done" during the peek, pytest gets confused and calls it an internal error — even though the shout meant "success." The fix is to put all the playing inside a special box called `main()` that only opens when you run the file on purpose. Just changing the last shout does not help; you have to stop the dumping when someone is only peeking.

## 🔵 GRANDMA NOTE
Dear, this one is about a file that could not be looked at without acting. The check file ran its whole battery the moment anyone imported it, and finished by exiting — which, run on its own, looked like a clean success. But pytest looks at files by importing them, and to pytest any exit during that look is an internal error, success or not. So a file that is "fine" when run alone can still break a whole test collection. The moral to carry: never let a file do work at import time. Defining is safe; doing belongs behind the door that only opens when the file is run as a program. And a forced failure still reports failure, so the guard does not hide bad news.
