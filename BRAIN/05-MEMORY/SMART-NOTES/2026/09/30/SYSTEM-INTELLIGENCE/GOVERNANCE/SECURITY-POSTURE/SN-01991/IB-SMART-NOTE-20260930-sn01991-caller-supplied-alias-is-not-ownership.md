## ✦ IN A NUTSHELL
A SECURITY DEFINER function that takes its owner from a caller-supplied parameter is not owner-private — it is caller-authorized. The 2026-10-25 read-only audit found anonymous EXECUTE on SECURITY DEFINER owner-private payment/booking RPCs whose ownership check compares a caller-supplied alias against the row, with no issuer-bound check — and an anonymous scheduled-mail RPC with write side effects. The mechanism is exact: SECURITY DEFINER runs as the owner and bypasses row-level security, so any "ownership" test inside the function that reads its identity from a parameter tests attacker-controlled input against data — the caller names the victim, and the check passes. Owner-private describes where the function lives, not who it obeys. The rule: identity must come from the authenticated issuer (the session, auth.uid()), never from a parameter; a different-auth caller must fail the RPC; and no anonymous RPC carries write side effects. Routing, in order: metadata-only audit, smallest coupled correction, different-auth verifier, human gate before production.

## 🩷 HUMAN NOTE
Imagine a bank vault whose guard asks every visitor, "Whose box are you here for?" — and then opens whichever box the visitor names, without ever checking the visitor's own ID card. The vault is "owner-private" in the sense that only the bank's own key opens the boxes — but the guard takes the owner's name from the visitor's mouth, so any visitor who knows a name walks out with that person's box. That is what a caller-supplied alias does inside a SECURITY DEFINER function: the function runs with the owner's full power, and its ownership check trusts a name the caller chose. The fix is not a stronger door — it is checking the visitor's own ID card instead of asking them who they are. And a mailbox that lets a stranger post letters that actually move money is not a mailbox at all; anonymous hands must never carry write side effects.

## 🔵 GRANDMA NOTE
Dear, this one is about a lock that checks the wrong thing. A database function marked SECURITY DEFINER runs with the owner's full power, skipping the usual row protections — that is by design. But the payment and booking functions the audit found take the owner's name from a parameter the caller supplies, and then "check ownership" by comparing that supplied name against the row. A caller who names someone else passes the check, because the check never looks at who is actually calling — only at the name they offered. So the function is owner-private in name only; in practice it obeys whoever names a victim. The standing rule is plain: identity comes from the caller's own authenticated session, never from a parameter they hand you; prove it by having a different, wrongly-authorized caller try and fail; and never let an anonymous caller trigger anything that writes. The routing is fixed too: audit read-only first, make the smallest coupled fix, verify with a different authorization, and keep a human gate before anything reaches production.
