## ✦ IN A NUTSHELL

The learning system had one runtime surface still able to over-claim learning: `naya-decision-context` treated ACTIVE `learning_evidence` **presence** as `influenced: true`. Presence in context is retrieval/context availability — not demonstrated causal influence. A new falsifier failed on current main exactly because active evidence produced `influenced: true`. PR #1733 repairs it by separating `LEARNING_CONTEXT_AVAILABLE` from causal influence in the schema: evidence can be present without influencing anything, and `influenced` stays **false** until a controlled intervention + outcome + independent verification establish it. GREEN after repair: decision-context 13/13, focused learning regression suite 64 passed / 1 skipped, `git diff --check` clean.

The durable rule: **a field that asserts influence from mere presence is a category error — it fabricates the very property the learning system exists to prove.** Availability and influence are different claims with different proof bars: availability is proven by a retrieval receipt; influence is proven only by a controlled behavioral difference (family: SN-0510, influence is a number) or by the canonical causal chain (intervention → outcome → independent verification). The schema must carry both fields separately, and influence must default to false — the burden of proof runs one way.

Why this is brain-grade: the whole learning loop stands on the claim "this lesson changed what the system did." If the runtime can stamp `influenced: true` whenever a note merely sits in context, every learning receipt downstream becomes self-certifying — and the system can never tell the difference between a lesson it remembered and a lesson it used. That is the merry-go-round wearing a lab coat. The separation is mechanical, not aspirational: the flag's setter is gated by the causal proof, not by the retriever.
