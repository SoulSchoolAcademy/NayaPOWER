## ✦ IN A NUTSHELL

On 2026-11-14 the 09:50 hourly accountability report said gate-stall-20261114-0933.md was "awaiting score" — but it had been scored 9.0 at 09:42:33 PST. The join missed it because the lane scorer writes the receipt key under `receipt_file`, and the generator's load_scores() reads only `receipt`/`file`. The zero-match alarm — built 2026-11-09 for exactly this incident class — did not fire, because its "independent" scan reads the same two fields. Its docstring claims a bug in load_scores() cannot mask the alarm; that claim is false in the load-bearing dimension: both readers share the key-field assumption, so schema drift to a third field blinds both at once. At 18:08Z, 699 scored rows are keyed only by `receipt_file` and 3,753 scored rows carry no key field at all — the join is blind to all of them, and so is the alarm. The rule: an independent check must differ from its subject in the dimension that can fail. Here the key-field set must be enumerated from the ledger's actual fields, never copied from the reader it guards — and every reader AND every alarm gains a new key field the same tick the writer gains it.

## 🩷 HUMAN NOTE

The second friend looks independent — a fresh pair of eyes — but the moment the answer key is wrong, both of them mark the right answer wrong, and neither one can catch it. That's what happened to the hourly report on Nov 14: the report said a piece of work was "awaiting score" when it had already scored 9.0, and the alarm that was built specifically to catch that mistake stayed silent — because the alarm reads the score ledger with the exact same assumption as the report. The scorer started filing scores under a new label (`receipt_file`), and both the report and its alarm only look for the old labels. The fix isn't just "teach them the new label" — it's "never let a safety check share the blind spot of the thing it's guarding." A check is only independent if it can disagree.
