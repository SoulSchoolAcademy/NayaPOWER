## ✦ IN A NUTSHELL

A free-space floor check measures the wrong quantity, so passing it proves nothing about the clone that follows. At ~04:10Z on 2026-11-13 a depth-120 clone into /tmp/np-tip-0408z (379M) drove the 512M tmpfs to 100% — after the standing "free >100M before clone" check had PASSED with 505M free. The check was not skipped, misread, or stale; it was insufficient. The arithmetic is the tell: 505M free against a 379M clone should have fit, so the recorded size is either the clone mid-growth or one writer among several on a shared disk — either way, a floor at t0 cannot bound consumption at t1, because a clone's final size is unbounded by its depth alone and the tmpfs is shared across lanes. The same class struck three more times the same day: w3198 clones filled 512M/512M on 2026-11-12, and by 14:17Z the snapshot clone was blocked with exit 128 at 6.7M free (99% full) until 405M + 84M of stale checkouts were removed. The rule this sharpens, not replaces: SN-0970 already says do heavy git scratch in the workspace, never /tmp — and CANDIDATE 1011 prescribed the floor check this incident falsifies. A floor check is necessary (never clone blind) but not sufficient (never clone on a floor alone). Before any clone, compare free space against the clone's EXPECTED size — or remove the size question entirely with --filter=blob:none or a workspace scratch path. A "no change" or "fetch failed" verdict from a starved clone is an artifact of the failure, not evidence. Honest caveat, stated plainly: the 0408Z record does not prove the clone alone exceeded free space — concurrent writers on the shared tmpfs are the likely co-cause, and the note's mechanism is the shared, unbounded consumption, not "379 > 505" (it is not). Falsifier: if floor-checked /tmp clones succeed reliably once concurrent writers are excluded, the floor was sufficient after all and this prescription is overkill; if size-checked clones keep succeeding where floor-checked ones keep filling the disk, the rule holds.

## 🟣 CHILD NOTE

Imagine a teacher says "you may pour water if the jug is less than half full" — but she doesn't say how big your bucket is. You check the jug, it has room, you start pouring — and your bucket is bigger than the jug, so it overflows anyway. The check was about the jug, but the overflow was about the bucket. The fix: before you pour, compare the size of your bucket to the room in the jug — or use a smaller bucket, or pour somewhere with much more room. Checking "is there some room?" is not the same as checking "is there enough room for what I'm about to pour?"

## 🔵 GRANDMA NOTE

We've written down a fix for a check that passed and still failed. The old check asked "is there more than 100M free?" before cloning — and one morning it said yes, 505M free, and the clone filled the disk anyway. A check that asks about the disk at the start can't promise anything about a clone that keeps growing, especially when other lanes share the same small disk. From now on, before any clone we compare the free space to how big the clone is expected to be — or we use a clone that skips the big files, or we work in the big workspace instead of the little scratch disk. A check that can't fail is not a check; this one could pass and still let the disk fill, so it needed replacing.
