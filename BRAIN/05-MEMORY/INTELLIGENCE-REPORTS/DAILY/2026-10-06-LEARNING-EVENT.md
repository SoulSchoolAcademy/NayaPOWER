### 3. Parallel-first, and no lane ever hits a dead end
- **What it is:** Shawn ratified parallel execution as standing doctrine — if work can be done in parallel, do it in parallel; sequential performance of independent work is an execution defect. It was forged in three languages the same day (Law 0013, PR #1651, merged with post-merge faithfulness proof) and captured as SN-0459. The evening sharpened it into the "no dead end" directive: one priority never blocks every other lane — keep system work moving continuously, and re-staff failed agents instead of letting their work die with them.
- **What it means:** Parallelism is bounded by real dependencies and measured capacity, not by habit or turf.
- **Why it matters:** The day itself proved the negative case: the agent fleet repeatedly lost runtimes to daemon restarts, and work survived only where it had been checkpointed outside the runtime.
- **What's in it for me:** When you dispatch, dispatch independent lanes together; when an agent dies, its progress must already exist on disk for a successor — write progress under the goal's working files as you go.
- **How it connects:** The elite-specialist model arrived the same day: each specialist owns one craft, drives it honestly to 10/10, then takes the next highest-value task; a specialist who finds a hole within their authority fixes it rather than merely reporting it.
- **What changes tomorrow:** From now on, we run independent work in parallel and checkpoint every lane's progress to disk instead of serializing work and letting it die inside a single runtime.

### 7. Restarting a crashing process is not a cure — root-cause the mechanism
- **What it is:** The Reveal narration bake died, was restarted, died again — five watchdog restarts by evening. Direct inspection found the mechanism: two workers each holding a ~4GB TTS model on a 7GB VM = guaranteed OOM kills → BrokenProcessPool → restart → same crash. The fix was not another restart; it was changing the shape: single-worker bake, and the watchdog's restart command permanently changed to match. The honest status recorded that evening was precise: mechanism root-caused and relaunched, stability not yet proven.
- **What it means:** A watchdog that resurrects a doomed configuration is an loop that manufactures the same failure forever.
- **Why it matters:** Hours of "progress" (2/37 files, then 5/37) were spent inside a crash cycle that arithmetic alone could have condemned at the first death.
- **What's in it for me:** After the second identical failure, stop and root-cause the mechanism before any rerun — and do the capacity math (workers × footprint vs. machine) before choosing a configuration.
- **How it connects:** The same discipline appeared in miniature in the notifications build: the coordinator reported 25/25 tests; a direct rerun counted 24/24. The verified count supersedes the reported count — reported numbers are claims until re-run.
- **What changes tomorrow:** From now on, we fix the mechanism that produces the failure (and prove the failure stopped) instead of restarting the process and calling the restart a repair.
