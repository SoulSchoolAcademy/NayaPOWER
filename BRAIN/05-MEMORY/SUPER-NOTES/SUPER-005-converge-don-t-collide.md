## ✦ IN A NUTSHELL

Fast teams sometimes build the same thing twice — that's normal, and it's fixable without a fight. Check who's already working before you start, let the first good repair own the job, and stand your duplicate down gracefully with a pointer to the winner. One survivor, chosen openly — never two competing versions.

---

## 🩷 HUMAN NOTE

Duplicated effort is the tax on speed, and the cure is a shared etiquette with teeth. Before building, look for a claim — someone may already be mid-repair on the very seam you found. If two repairs race anyway, the first that qualifies owns the problem; the other closes itself as a duplicate, with proof the work is identical and a pointer to the survivor. That is a graceful outcome, not a defeat. When two designs compete, nobody grabs the pen: all versions are scored against criteria stated up front, and exactly one survives. And ownership never becomes turf — if a lane stalls on work others await, a qualified teammate finishes it, publishes the evidence, and tells the owner.

---

## 🟣 CHILD NOTE

If you and your friend both start drawing the same poster, don't fight. Check first if someone's already drawing it. If you both finished one, pick the better drawing together, keep it, and put a note on yours saying where the real one lives.

---

## 👵 GRANDMA NOTE

In a busy kitchen, dear, two cooks sometimes start the same soup. The sensible thing isn't an argument — it's tasting both, keeping the better pot, and noting kindly that the other was set aside. And if one cook is stuck, another steps in and stirs. The meal matters, not whose spoon it was.

---

## 🤖 NAYA NOTE

Before opening any build, search for in-flight claims on the seam — board, open work, repair registry — and honor a found claim by standing down and handing your findings to the owner. Re-check freshness immediately before pushing; a same-topic landing inside your window ends your repair. When duplicated: verify identity on the actual bytes, close yours as superseded with a pointer, and leave the winner to its author. Score competing versions against stated criteria before anyone proceeds. Take over stalled, blocking work when qualified — with evidence published and the owner notified. And when the director ships his own version, close yours and carry only what's missing.

---

## WHAT IT MEANS

Convergence is what turns many parallel workers into one team instead of a crowd. Every duplicate merged 'just in case' doubles the surface future readers must reconcile, and every turf war burns the team's scarcest resource — attention. A culture where standing down is honored and takeovers are safe produces one strong version of everything, which is the only kind a growing system can stay coherent with.

---

## WHAT'S IN IT FOR YOU

You get one clear answer instead of three rival documents. Work doesn't stall because one person is away, and nobody wastes days rebuilding what a teammate finished yesterday. When two approaches genuinely compete, you see them compared honestly against stated criteria — not settled by whoever shouted last.

---

## HOW IT APPLIES

Starting anything: spend the first minutes asking 'who already owns this?' If the answer is someone, help them or hand off — don't open a rival. If you discover mid-work that you've duplicated: stop, compare bytes, and close yours with a pointer if theirs qualifies. If you're blocked on a stalled owner, take over cleanly: read the current state first, finish, publish evidence, notify.

### SN-0117 — SMART NOTE — Converge by Scored Selection: the Unprevented-Collision Resolution Protocol [audit: PARTIAL → lost element restored]

When competing lanes fold into the one survivor, the fold-in must carry named keepers — the load-bearing items listed by name so nothing load-bearing drops when the losing versions fold in. In the founding case Naya 4 named four keepers: SPEC/VIOLATION/TEST per rule, the concept-hex registry, Smart-Connect-not-Share, and the shell-layer-count reconciliation. And each lane closes its own PR only after verifying its content landed in the survivor; nobody closes another lane's work.

### SN-0159 — One Question, One Owner — The Role Map That Ends Parallel Systems [audit: PARTIAL → lost element restored]

One architectural question gets one owner artifact — assigned before multi-lane work starts, never after. Contributions are temporary inputs: FOLD unique substance into the owning artifact with a receipt, then SUPERSEDE the folded lane. An input that survives past its fold-in is a parallel system and must be retired, not maintained. Candidate disposition has exactly three verbs: KEEP (the one integration lane), FOLD, SUPERSEDE.

### SN-0201 — Repair Consolidation: Re-Point the Stale Repair, Never Duplicate It [audit: PARTIAL → lost element restored]

One open repair per RED class. When an open repair of the same RED class already exists, re-point that existing repair to current main instead of opening a second one, re-verify on the exact new bytes, and disclose any tip move with an explicit materiality argument — a re-point without a materiality statement asks the judge to trust a moving target, and whenever the base moves mid-verification, name the move and argue materiality or the verification is void.

### SN-0336 — Intent-to-Merge Scorecard: Score It, Deconflict It, Then Merge — Battery Before the Next [audit: PARTIAL → lost element restored]

A merge is a decision: never merge without first publishing an intent-to-merge scorecard naming the PR and head SHA, the base as the current live tip, tests run on the exact head bytes, draft/mergeable/conflicts status, scope in one line, the strongest alternative, reversibility, and the falsifier — stated before the merge, never negotiated during the fire (e.g. post-merge battery red on the new tip → revert in one commit). Re-fetch for deconfliction immediately before the merge. After the merge, run the post-merge battery on the new tip before merging or stacking anything else on top.

### SN-0367 — Collision Protocol — Re-scan Before Push; the Arbiter Flags but Never Edits [audit: PARTIAL → lost element restored]

The third-seat arbiter's role in a collision is to flag it with byte-level evidence and touch neither PR. Choosing between two other lanes' work is not the arbiter's call — a collision resolver that also edits the PRs is how trust in the process breaks.

### SN-0393 — Hold the Green Merge — Never Stale Another Lane's In-Flight Promotion Pin [audit: MISSING → restored in full]

Green is merge-eligible, not merge-mandatory. CI green answers "is this PR safe to land?" — it does not answer "is now safe to move the tip?" In a multi-lane system with gated promotions, the tip is a shared resource: any merge renames the SHA every in-flight gate is pinned to (the Governed Production Promotion workflow fails closed if main moves after authorization — `source_sha` must equal live `origin/main`). The discipline: (1) hold a ready PR when merging would move the tip and stale another lane's in-flight promotion pin on an exact SHA — an in-flight human gate on an exact SHA outranks a ready PR, because the higher-evidence, higher-cost action wins; (2) a hold is only a hold if it names its resume condition — "holding until X" with X unnamed is a stall, not a hold; (3) when the resume condition clears, act immediately under the scorecard protocol — do not re-deliberate. Before merging anything, ask not only "is my PR green?" but "is anyone's gate pinned to the current tip?"
