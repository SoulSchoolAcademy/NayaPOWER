## ✦ IN A NUTSHELL

When something fails twice, suspect the setup, not the person. Name the real choice hiding under a stuck argument, fix the conditions that keep producing the failure, and let a bounded, honest attacker test the result.

---

## 🩷 HUMAN NOTE

A note failed — and the audit found the system itself had been teaching two contradictory ways to file it. A count drifted three times — because two sides disagreed about what the count even meant, and each repair just patched the number. A test scored the product down when the test's own room was too small to run in. The pattern: repeated failure is information about the system. So name the false choice out loud ('two bad plans' is usually hiding one good integrated one), classify disagreements honestly instead of recounting, and give an attacker a small, clear, read-only job — bounded attacks find real holes without breaking anything.

---

## 🟣 CHILD NOTE

If lots of kids keep tripping on the same step, you don't blame the kids — you fix the step. If two grown-ups argue 'this way or that way,' sometimes there's a third way that uses both. And it's smart to ask a friend to try to find the holes in your fort — politely, and only where you said they could look.

---

## 👵 GRANDMA NOTE

When the same mistake keeps happening in a household, dear, it's usually the house, not the people — a confusing cupboard, a rule written two ways. You fix the cupboard. And a wise family invites a trusted friend to point out what's rickety, within limits everyone agreed on. That's not criticism; that's care.

---

## 🤖 NAYA NOTE

Naya audits the system before judging a seat: contradictory instructions, invented locations taught by the repo itself, and environment limits wearing product clothing all count as system defects with system owners. She names the false choice and states the integrated model before executing a multi-part build, and settles classification disputes at the classification, not by recounting. Her adversarial work is bounded, read-only, and contract-crisp — sized to find defects, never to roam.

---

## WHAT IT MEANS

Blame feels like accountability but usually just hides the cause, so the failure returns wearing a new name. A repeated failure is the system describing itself — in its contradictions, its cramped test rooms, its unsettled definitions. Reading failure that way turns every incident into a repair of the conditions, which is the only kind of repair that stays repaired.

---

## WHAT'S IN IT FOR YOU

You get fixes that hold. Instead of the same problem returning every few weeks with a new apology, the cause underneath gets repaired once. Arguments that felt stuck open up, because the real, third option gets named. And the system gets stress-tested by friends before strangers ever find its weak spots.

---

## HOW IT APPLIES

On the second occurrence of any failure, stop and audit the setup before the person: instructions, definitions, environment, tools. Write the false choice down and state the integrated alternative before building. When a number keeps drifting, settle what it means before recounting it. Commission bounded, read-only red-team passes with crisp contracts, and fix what they find at the root.

### SN-0130 — Intelligent Block — SN-130 [audit: PARTIAL → lost element restored]

Three-strikes class escalation: when the same repair class recurs a third time, stop patching instances — the owning lane must issue a written ruling on the class (placement rule + count rule + one deliberate bump), and no fourth instance may be patched before that ruling lands. Instance patches never close a class dispute. In the source case the 05-MEMORY projection-count drift had been repaired three times (#1251, #1301, and the current instance) because the runtime registry counted SN-018 once while the file counter counted it twice — the ruling question was whether verified projections live under `SMART-NOTES/SN-*/` as counted notes or relocate to a projections path.

### SN-0346 — Environment Failures Must Never Wear Product Clothing [audit: PARTIAL → lost element restored]

Measurement tooling must fail loud on environment shortage: a harness that cannot measure must announce the shortage with a dedicated fatal exit (in the source repair, FATAL exit 3) and abort the affected check as an environment failure — never silently convert it into a product score. Suppressing the error is prohibited: `2>/dev/null` on anything that can carry a failure reason is a lie in the instrument — in the source case it swallowed "No space left on device" (five ~117MB clones into a 512MB `/tmp` tmpfs) and dead clones were scored as index defects on a provably green tip.
