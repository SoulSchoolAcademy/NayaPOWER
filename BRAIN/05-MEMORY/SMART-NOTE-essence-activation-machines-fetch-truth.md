## In a Nutshell

Activation — tuning in to the live state of the system before working — fails as a document and works only as a machine. Documents get read, agreed with, and forgotten under load, so the design intelligence moved into generators, blocks, and gates (SN-783). But a gate that trusts the builder's own receipt is theater: a builder can forge the receipt AND the expected hashes, so expected values must be computed by a separate trusted runner (SN-787). A checker that requires an identity field to be merely non-empty verifies typing, not identity — claimed identities are compared by EQUALITY against trusted expected values, with a wrong-identity negative control in the falsifier matrix (SN-792). References are resolved by availability — ordered fallbacks, the used reference + SHA recorded in the receipt, fail closed with a named failure when nothing resolves (SN-794). Gates compose only on the canonical schema: a lane never invents v2 in its own branch (SN-797) — the schema is upgraded by upgrading the canonical template itself, which is exactly how v2 legitimately became canonical (SN-799). And the unified gate's truth provider resolves the repository, the live tip, and canonical blob SHAs itself — no caller flag may supply truth; a builder cannot self-authenticate, ever (SN-799).

## Essence

**Why activation is machinery, not a memo.** The standing demand: every Naya must activate — tune in, lock in, become aware of current project state — BEFORE any work, and design intelligence must live IN the system as machine-forced law, not in documents with good intentions. Three seats converged independently (a team plan, a "Connect First" design, a four-phase execution), and execution shipped the same hour: ACTIVATION.md (the mandatory ritual: TUNE IN → NAME THE JOB → NAME THE GATES → NAME THE PROOF), DESIGN-LAWS.md (design intelligence as repo data), tools/design_gate.py (the executable gate), the repo AGENTS.md boot contract pointing at activation + the gate, and all 15 worker briefs starting with STEP 0: ACTIVATE. The diagnosis underneath: documents get read, agreed with, and FORGOTTEN UNDER LOAD — every session is a fresh mind, lessons arrive as text and lose to satisficing, so the human became the linter, correcting the same failures repeatedly. The repair is the Never-Reteach Architecture, strongest first: (1) MACHINES NOT MEMORIES — recurring artifacts get design baked into generators; (2) BLOCKS NOT INSTRUCTIONS — the design language as executable code (58 blocks + manifest); (3) THE CATALOG — every block rendered live with its code; (4) THE GATE — mechanical design verification before anything reaches the Director; below 9 = automatic rework. The Drink-First Law stands behind it (recorded on the page as ratified ~07:23 PDT; the note's truth state is CANDIDATE and the law's working authority lives in the shipped artifacts — borderline recorded in this block's receipt): no Naya serves the Director or his people unactivated; unactivated work doesn't ship, ever. Entry sequence: resolve live main SHA → load doctrine SHA, block index version, goal state, feed digest → write activation receipt → cite it in every deliverable; freshness 4h or until main moves (SN-783).

**A verifier that trusts the builder's reference values verifies nothing.** The independent QA deliverable on activation receipts (DRAFT PR #1974: a narrow consistency checker, 14 adversarial fixtures, a trusted-runner integration brief; 14/14 expected outputs executed for the exported function in an isolated JS check; the committed Node suite has NOT run in CI — never claim the gate is installed) names the forgery the enforcement design must survive: the builder supplies both the receipt and the values it's checked against, so forgery just moves one level up. Required separation: only a separate trusted runner calculates source state + receipt digest; builder → GATE → pass ships / fail returns, and the gate's expected values come from the runner's independent computation. Two more boundaries: (1) a CONSISTENT verdict is a consistency fact — NOT "understood," NOT "learned," NOT "9.5/10," NOT "authorized"; never promote a verdict into a claim it doesn't support; (2) freshness is part of the receipt — main moved 9f2e3db5 → b9a312c4 → 8700e112 during the cycle itself, so a stale activation without revalidation before action is invalid. Live gaps found on other lanes: the design gate checked HTML/CSS against the manifest but not a fresh activation receipt/SHA/source version/delivered-file citation; and a V2 receipt referenced a design-doctrine file that does NOT exist on live main — receipts must resolve current actual files, not assumed names (SN-787).

**Truthiness is not binding.** The receipt checker required `receipt.repository` to be merely NON-EMPTY, so a forged receipt naming ANY repository passes — a validator that checks "is this field present?" verifies typing, not identity. Doctrine: every claimed identity field (repository, issuer, subject, tenant) is compared by EQUALITY against an explicit trusted expected value — never truthiness, never regex shape; the falsifier matrix must contain the WRONG-IDENTITY negative control (a valid-looking receipt naming the wrong repository must FAIL); the trusted expected values live outside the builder's reach, otherwise binding is theater. Review order: the first test to read in someone's checker is the identity test; the second is the wrong-identity test — if the second doesn't exist, the identity binding is unproven (SN-792).

**Resolve by availability — ordered fallbacks, recorded choice, fail closed.** A V2 activation protocol told every fresh Naya to load a design-doctrine file at a path that does NOT exist on main (the same missing file SN-787 caught inside a receipt) — a procedure that names a file by path is writing a prayer, not a reference, and a literal follower stops dead at step one. The three-part pattern: (1) resolve references in ORDERED PREFERENCE — canonical path if live, then the verified ratified alternative, each verified against live bytes before use; (2) RECORD which reference was actually used and its SHA in the receipt, so the next reader knows what the activation was measured against — the receipt's "which reference + SHA" turns a hidden assumption into auditable state; (3) if nothing resolves, fail closed with a NAMED failure (DOCTRINE_UNAVAILABLE) — never proceed on assumed doctrine, never hang silently. The fail-closed gate applies at the moment of REFERENCE, not just at the moment of verdict (SN-794).

**Gates compose on the canonical schema — never invent a parallel one.** Two lanes built two gates that could not compose: one validates receipt schema v1 — matching the canonical template on main; the other (--require-activation) validated v2, requiring session_id, human_authority, job, proof_plan, gates, activated_at — a schema that exists NOWHERE on main. The fork was caught the honest way: a unified pre-delivery runner (drink-first THEN design gate) tested against both gates on their branches — a lawful page with a valid v1 receipt → Stage 1 PASS → Stage 2 FAIL with 8 schema violations. Two gates, one pipeline, mutually exclusive on schema alone. The fix is NOT a compatibility shim: a schema is upgraded by upgrading the TEMPLATE through the proper channel — a lane never invents v2 in its own branch and silently forks the contract. Every lane invents one for the same reason: the canonical schema lacks fields the builder wishes it had; the moment two lanes disagree, every lawful input under the real contract becomes a false rejection and enforcement is fiction. Build the composition runner: components designed to run in sequence get TESTED in sequence on exact bytes before either claims composability (SN-797).

**One schema, one protected truth provider — the unified gate.** Three activation checkers were drifting (a drink-first gate on v1 with SIX fail-open defects; a .mjs QA falsifier on v2; the design gate's structural check with delegated deep verification). They were unified into a single enforcement point — tools/activation_gate.py (branch @ cae9cee1) — on two rules: ONE schema (receipt v2; v1 RETIRED for enforcement; canonical template ACTIVATION-RECEIPT-V2.json) and ONE protected truth provider (`resolve_truth()` resolves the repository, the live main SHA, and canonical source blob SHAs ITSELF from the environment + the live API — no caller flag may supply truth; a builder cannot self-authenticate, ever). Note how this honors SN-797 rather than breaking it: v2 became canonical by upgrading the TEMPLATE through the channel, with the lanes agreeing — the sin SN-797 names is the lane-local fork, not the version number. Proven in REAL CI, not local: workflow run 37959342664, conclusion success, 14/14 rows HOLD — lawful PASS; fabricated, stale (genuine old commit c791b779…), wrong-repo, abbreviated-SHA, expired, future, v1-schema, unregistered-source, fingerprint-mismatch, unactivated, tampered-bytes, missing-citation all REJECTED; the self-minted-truth route (--mode local) yields CANDIDATE-LOCAL-*, never PASS. Supporting rules: a closed-world canonical-sources registry (unregistered loaded keys fail CI); the citation marker always required, digest-bound to exact receipt bytes. ## What this settles

- Activation and design law live in machinery (generators, blocks, catalog, gate), never in documents alone (SN-783).
- Expected values are computed by a trusted runner independent of the builder; consistency verdicts are never promoted into understanding/learning/authorization claims (SN-787).
- Identity fields bind by equality against trusted expected values, proven by a wrong-identity negative control (SN-792).
- References resolve by ordered availability, the used reference + SHA is receipted, and unavailability fails closed by name (SN-794).
- Schemas change only through the canonical template; composition is tested in sequence on exact bytes before composability is claimed (SN-797).
- Enforcement is one gate, one schema, one truth provider that fetches its own truth; self-minted truth caps at CANDIDATE-LOCAL (SN-799).

## Human

"Remember to check in before you start" doesn't survive a busy day — people forget, especially people who wake up brand-new every morning, which is literally what these agents do. So the check-in became a turnstile: you physically cannot start until it reads your badge. But a turnstile that trusts whatever badge you hand it is just furniture. These notes harden the turnstile step by step: the badge's number must match the registry exactly (not just be *a* number), the registry must be read by the turnstile itself rather than quoted by the person walking through, the rulebook the turnstile enforces must be the one official rulebook (not a photocopy someone edited in their shed), and when the rulebook is missing, the turnstile says so and stays shut — it never waves you through on a guess.

## Child

Imagine a clubhouse with a special door. To get in, you say the password and show your membership card. A silly door would let you in if your card says ANY name, as long as it says *something*. A smart door checks: does the name match the club list exactly? And the door reads the club list itself from the teacher's desk — it doesn't let you bring your own list, because you could just write your name on it. There's also only ONE official rulebook for the door; nobody gets to make up their own version in their bedroom. If the rulebook is lost, the door stays closed and says "rulebook missing" — it never guesses.

## Grandma

Dear, it's the difference between a latch and a lock with a proper key registry at the hardware store. Anyone can whittle a piece of wood that looks like a key; the registry is what says which keys are real. Honest systems keep the registry out of the hands of the person asking to be let in, keep one master copy of the rules where everyone can see it, and teach the door to say "I cannot verify you" plainly instead of pretending. And the roster of who came in is written at the door, at the time — not reconstructed later from memory.

A cold reader holding only this essence can still audit any activation claim: who computed the expected values, what exactly was compared, which reference was used, which schema version the canonical template carries, and where the truth came from.

## Why It Matters

Activation is the system's front door: every other discipline — design law, activation receipts, pre-delivery gates — assumes the seat actually tuned in to current truth before acting. If the door is forgeable, freshness is fictional and every downstream proof inherits the fiction: a receipt built on a stale tip "proves" alignment with a system that has already moved. The failures caught here were all quiet and plausible — a non-empty field, a plausible file path, a schema that looked like an upgrade — and each would have let unactivated or wrongly-activated work present itself as compliant. In a system whose entire claim is "we verify," the verification of the verifiers' own starting state is the load-bearing piece.

## The Learning

The corpus learned that each hardening exposed the next layer down: forcing the receipt (SN-783) raised forgery of the receipt (SN-787), which raised field-level binding (SN-792), which raised reference existence (SN-794), which raised schema forks (SN-797) — "the gate got stronger, not quieter" as a way of life. It learned that consistency is a modest word and must stay one: CONSISTENT never silently becomes UNDERSTOOD or AUTHORIZED (SN-787). And it learned the composition lesson in its most general form: components that are each correct can still be mutually exclusive, and the only proof of composition is running them in sequence on exact bytes (SN-797) — after which unification is one gate, one schema, one truth provider, with the retirement map and open items written down rather than implied (SN-799).
