## In a Nutshell
Project Intelligence is the one record the whole system works from: every piece of work is an item with an honest state, every act of work ends as a visible state change with proof or it counts as waste, and "done" is a database write the system refuses without evidence from a different seat. Its loop is PRODUCE → PROVE → PUBLISH → SEE, its face is a derivation from the record (never a report typed beside it), and its build order runs claim → build → scorecard → verify → land, stopping only when the whole scope is done and proven. Underneath sits the definition that makes it intelligence rather than bookkeeping: to "get it" is for understanding to finish its journey into changed behavior — and PI is the project's model of itself.

## Essence
The spec's core law: every act of work ends as a visible state change with proof, or it counts as waste — production is a verified state transition to done-proven (the same event the Smart Ledger chains), waste is activity that produced no transition and no evidence, and the ratio between them is published daily: baseline 173:1 at the 2026-10-22 audit, target under 60:1 by 2026-10-30 (SN-0835). Its six waste classes, each with a detector and a cure: W1 zero-output loop (runs ≥20/24h, transitions 0) · W2 built-but-invisible (no live proof in 24h) · W3 aging (no transition ≥3 days) · W4 duplicate claim · W5 report churn (no transition, no decision) · W6 verification debt (more than one director pass) (SN-0835). The refresh computes the production block honestly — the ratio is null until both sides honestly exist, never faked (SN-0835). The canon record holds seven honest states — queued, claimed, in_progress, verifying, done_proven, blocked, needs_shawn — and enforces them as database law, refusals not warnings: done_proven requires an evidence_url and a prover_seat with prover ≠ maker; blocked requires a complete blocker {what, owner, since, clearing_action}; needs_shawn requires a queue packet in the same transaction; every state write writes its ledger_entries row in the same transaction (SN-0839). The old state's evidence is why: of 31 items marked "done and proven," 10 carried no proof link at all, there was no blocked state, and the scoreboard counts disagreed (Ledger 30, done-proven 31; proof coverage 68% at filing) — the migration flips the 10 proof-less items to verifying, each with an alarm (SN-0839). One derivation job, change-triggered and idempotent by input hash, emits the state, the face payload, and per-project projections atomically — the face is a derivation, never a report (SN-0839). The build order that fills the record runs five motions: claim (the claim is the lock) · build (to the one spec — harvest, never invent) · scorecard (a genuinely different login scores grounding, function, performance, usefulness, and runs the journey three times) · verify (at the real address: live bytes, render, data) · land (9+ and verified; production also takes Shawn's word) — in priority order P0 trusted core, P1, P2, with DONE defined by a conjunction: the 30-second test ∧ cold orientation ∧ proof-coverage 100% ∧ 7 days of zero ledger-missing landings ∧ a clean Page Test week ∧ every node mapped (SN-0840). And the record is only intelligence if it is gotten: to get it is heard → stored → understood → embodied, proven by a four-part test — (1) behavior changes without being taught again; (2) it transfers to new ground at speed; (3) it can be handed on so the next one gets it in one shot; (4) it is declared — what was not got before, what is done differently now (SN-1896). The feeling of knowing is a signal, not a proof; understanding claims without a behavior receipt are CLAIMED-UNVERIFIED; and by Conant–Ashby, every good regulator of a system must be a model of that system — which is what PI is for the project (SN-1896).

## What this settles
- One record, one derivation, one face: numbers computed from the record at read time, never typed beside it.
- States are honest or the write is refused: proof from a different seat is a database constraint, not a custom.
- Waste is a measured set of six named classes, each with a detector — not a feeling about the week.
- The ratio is the headline: production over activity, published daily, null rather than faked.
- A record nobody's behavior changes because of is storage, not intelligence.

## What It All Means
A collective can only be as intelligent as its shared model of itself. PI is that model made operational: a record that enforces honesty at write time, derives every face from one truth, and measures the one ratio that separates production from motion. The "get it" doctrine is its soul: the record exists so that behavior changes — a project that understands itself regulates itself.

## Why It Matters
Because without it, the system runs on reports about the work instead of the work's own state — and reports drift, flatter, and expire, as the 31-items-10-proofless audit showed. With it, anyone — human, Naya, or a cold successor — can open one record and know what is real: what is done and who proved it, what is blocked and who clears it, what little is genuinely waiting on Shawn.
