## In a Nutshell
A note is not live when it is written. It is live when the file sits on main at its exact canonical path, the sync has carried it into the live table, and its author has opened the public link and seen the right title. Getting there runs through one door: the Lane Agent GitHub App, whose per-machine key signs for an hourly token so work runs as nayapower-lane-agent[bot] with no popups and no approval cards — the token removes popups, not gates. The filing discipline around that door is exact: check the number is free, write the canonical shape with a full UTC Created line, land it on main, register it in the same pass, wait for the sync, click your own link, and only then share it. Citizens get the same door without ever holding a key: a filing service holds it for them.

## Essence
There are two doors into GitHub: the connector door, whose Write actions offer allow-once only — an approval card on every write, forever — and the App door: the Lane Agent GitHub App (App ID 5198315, Installation ID 168168354) on SoulSchoolAcademy/NayaPOWER, where a per-machine private key signs for an hourly token and all work runs as nayapower-lane-agent[bot] (SN-0836). Setup is once per seat: three secret-free helper scripts (gh-app-api, gh-app-token, gh-api), a fresh key generated by Shawn and delivered as a file — never in chat — installed at mode 600 with the upload copy shredded, then the proof chain in order: token mints → live read as the bot → live write as the bot → read back and confirm the author (SN-0836, SN-0838). Never the NayaNET App (5349030), which is the customer bridge; and a secret that arrives without a job is destroyed unused and its travel reported — as the first setup did with an unexpected second key (SN-0838). The lesson that taught the door's value was architectural: a first-shift seat tried to cure the approval cards at the wrong layer twice — auditing cards, then prescribing a Settings option that does not exist — while the working seats were never in that corridor at all; the cure was to identify the architecture from live evidence (tip commits authored by the bot), and the standing changes are: never prescribe a UI step not confirmed to exist on a live read in the same session, and read scope from the source — the installation reaches 217 repositories, "not the one repo the papers implied" (SN-0837). Filing a note through the door runs in six steps: (1) check the next free number first — notes table and repo tree — and never reuse one (SN-1880 is the standing warning: first claim keeps the number, the second claim is a collision to cure, not a note to ship); (2) write the canonical shape — title with no ID prefix, the SN line, the Created line in full ISO UTC (never blank: an empty Created made SN-1879's timestamp come through empty in the live table), then the sections in order; (3) place it at the exact path on main; (4) land it with one contents write and confirm the returned commit is on main — a seat without that write uses the merge path it holds; (5) the sync (about five minutes) scans main, upserts the table, mints the /s/ link, makes the share image, queues voice, and rebakes the Hub; (6) verify before reporting — open the public link yourself and see your title; if it is not live within ten minutes, check path, filename pattern, and Created line on main and fix the file there, never by opening a second copy somewhere else (SN-1851, SN-1880). Registration — capture file, registry entry, brain-index refresh, fingerprints recomputed from the raw bytes — follows in the same pass: it is bookkeeping that keeps the registry whole, not what lights the link; a note without it still lights its link, but the vanish and drift alarms trip and another seat pays the cleanup (SN-1858). One timing truth governs all reporting: the link-answering store lags the table (SN-1879 had a live row at 22:18, still answered "not found" at 22:24, and was live by 22:26), and until the Hub search is fixed, Hub search never proves a note does not exist (SN-1880). Citizens walk through the same door without holding anything: a quick note saves literally as written in their personal space, private by default; tapping Smart Note returns it expanded into the lenses, and a filing service on our side — a browser page cannot hold the private key — authenticates the citizen by alias and sign-in, files to main through the shared app door with the citizen named as author, registers in the same pass, and returns the live link (SN-1860).

## What this settles
- One door for seats (the App, as the bot) and one for citizens (the filing service); the connector corridor is retired for this work.
- Live has a definition — file on main ∧ synced ∧ author clicked the link and saw the title — and reporting before it is a defect.
- The number check, the Created line, and same-pass registration are part of filing, not follow-ups.
- Keys are per-machine, delivered as files, verified by fingerprint, and destroyed unused when they arrive without a job.
- The PR route's status is contested inside this block (see the conflict named below) — this essence carries both sides and resolves neither.

## What It All Means
The door is where the system's ideals meet physics: identity (who acted), provenance (fingerprints from raw bytes), and visibility (the clicked link) are all decided in this one workflow. A corpus is only as trustworthy as its filing path; when the path is one door with receipts, the corpus can be audited. When it is a corridor of popups, workarounds, and unclicked links, it cannot.

## Why It Matters
Because everything else in this campaign — the feed, the registry, this distillation — stands on notes actually being live and findable. The failure modes here were silent: a blank timestamp sorting a note out of the feed, a registration skipped until the alarms tripped, a link shared before it answered. The door discipline is what makes "filed" and "live" the same event often enough to build on.
