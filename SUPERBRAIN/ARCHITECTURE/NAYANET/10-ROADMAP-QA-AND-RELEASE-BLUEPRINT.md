# 🔱 NAYANET — ROADMAP / QA / RELEASE BLUEPRINT

## 1. Build strategy

Plan globally. Build modularly. Verify concretely.

## 2. Phases

### Phase 0 — Foundation
Master directive, architecture, UX, design, intelligence, security, network, media, and release specifications.

### Phase 1 — E01
Welcome + Living Naya + free identity experience.

### Phase 2 — E02–E05
Naya Power, Powercast, Ask Naya, Five-Day Challenge.

### Phase 3 — E06
Intelligent Hub / Toolbox.

### Phase 4 — E07–E08
Superbrain + Collective Intelligence contracts and integration-ready UX.

### Phase 5 — E09
Activation, continuity, return loop.

### Phase 6 — Production integration
Authentication, GitHub App, Supabase, LLM/Naya runtime, event store, contribution processing, notifications, network discovery.

## 3. Block completion

Each block must have:

- specification;
- implementation;
- static test;
- behavioral test;
- responsive test;
- accessibility test;
- media test if relevant;
- Cloudflare deployment proof;
- human inspection;
- Oscar inspection;
- final URL;
- Groove embed verification;
- frozen version.

## 4. Device matrix

At minimum:

320 / 360 / 375 / 390 / 414 / 480 / 600 / 768 / 900 / 1024 / 1280px.

## 5. Quality questions

### Human

Can someone understand it immediately?

### Product

Does it provide real value?

### Design

Does it feel extraordinary rather than templated?

### Engineering

Is it simple, reliable, maintainable, and isolated?

### Intelligence

Does Naya genuinely help rather than merely speak?

### Trust

Is every capability and boundary truthful?

### Network

Does it create useful connection without coercion?

### Collective

Does shared intelligence preserve sovereignty?

## 6. Release evidence

Every release record must state:

- commit SHA;
- artifact path;
- deployment URL;
- test result;
- known limitations;
- human verification state;
- Groove verification state.

## 7. Regression law

A later block must not silently break a frozen block.

If shared contracts change, version them and retest affected blocks.

## 8. Stop-the-line failures

Do not ship if:

- private data can leak;
- authentication can be bypassed;
- critical CTA does not work;
- core navigation is broken;
- mobile layout is unusable;
- accessibility is materially impaired;
- the product claims a capability it does not have;
- a deployment state is misrepresented.

## 9. Final release law

> **We do not ship because the code exists. We ship because the experience works and the evidence says it works.**
