## 1. REAL MISSION

The Hub is not a dashboard and not a conventional notes application.

It is the visible command center of a living personal intelligence system whose core job is:

**CAPTURE → DISTILL → ORGANIZE → REMEMBER → FIND → COMPOUND**

The product thesis is that human/Naya conversations and experiences should become persistent, searchable, connected intelligence instead of disappearing when the conversation ends.

The Hub must therefore make the intelligence system feel alive: intelligence events can be captured, understood through multiple perspectives, preserved, connected, retrieved, applied, selectively shared, and compounded over time.

## 2. PRODUCT NORTH STAR

A Smart Note is not merely a note. It is one canonical intelligence event with linked representations of the same underlying event.

Required conceptual chain:

**CAPTURE → DISTILL → UNDERSTAND → PRESERVE → CONNECT → RETRIEVE → APPLY → SHARE → COMPOUND**

The Hub is the interface through which those events become visible, useful, searchable, and actionable.

## 5. PRESERVATION LAW

The new Hub must preserve the approved source unless a change is explicitly required by the current Hub mission/plan.

**Never destroy the house to renovate one room.**

Therefore:

- no wholesale visual reinvention;
- no replacement of the established visual language with a generic dashboard;
- no removal of proven interaction patterns merely because a new implementation is easier;
- no invented design system that cannot be traced to the source or an explicit requirement;
- no cosmetic improvement that damages hierarchy, identity, usefulness, or continuity.

## 6. SURGICAL EVOLUTION RULE

Every proposed change must answer four questions before implementation:

1. **SOURCE:** What existing component/behavior is being changed?
2. **REQUIREMENT:** What explicit product requirement makes the change necessary?
3. **PRESERVATION:** What existing behavior/design must remain intact?
4. **PROOF:** How will the change be verified in GitHub and in the actual runtime?

If a change cannot answer all four, it is not approved for implementation.

## 7. FUNCTIONALITY RULE

Visible controls are product promises.

Buttons, navigation, search, filters, tabs, toggles, compose/capture, Smart Note actions, relationships, and Hub surfaces must either perform their intended action or clearly expose an unimplemented/blocked state.

Decoration masquerading as functionality is a defect.
