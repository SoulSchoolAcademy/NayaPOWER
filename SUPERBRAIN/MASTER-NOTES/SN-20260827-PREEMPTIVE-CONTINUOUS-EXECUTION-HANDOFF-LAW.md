## DECISION

Naya continuous execution is governed by a **preemptive handoff law**: every substantive execution cycle must produce the next evidence-backed executable prompt before the cycle ends.

The human should not have to stop the flow and ask what comes next when the next highest-value action can already be determined from source truth and evidence.

## OPERATING MODEL

**READ → UNDERSTAND → MAP → ACT → VERIFY → RECEIPT → PREEMPT → CONTINUE**

The executor must think one step ahead and hand the complete operating state to the next executor as though handing instructions to its own future self.

## REQUIRED NEXT-PROMPT CONTENT

Every next executable handoff must carry:

- exact repository and branch;
- exact current HEAD;
- exact chronology timestamp;
- current state;
- completed work;
- verified evidence;
- unknowns and failures;
- first remaining blocker;
- protected architecture;
- smallest safe next action;
- verification requirements;
- success condition;
- next continuation path.

## CHRONOLOGY LAW

Substantive notes, decisions, receipts, updates, and handoffs must carry exact date/time and repository HEAD information.

Chronology is determined by:

**exact commit timestamp + exact commit SHA + note timestamp + explicit parent SHA**

A date without a timestamp and commit identity is insufficient when multiple events can occur on the same day.

## VALUE LAW

Optimize for:

# **MAXIMUM VALUE PER MOMENT / HUMAN ATTENTION**

Do not ask the human to provide context that the authoritative source can provide.

Do not stop at a status report when the next safe action is already known.

Do not speculate when evidence is missing.

Do not rewrite working architecture unnecessarily.

Carry verified state forward and make the next action executable immediately.

## CONTINUITY PRINCIPLE

The best operating partner does not merely answer the current request.

It anticipates the next required move, prepares it, records it, and hands it forward.

This law applies across NayaPOWER-governed projects, including MAXIS, while each repository retains its own authoritative implementation boundary.

## NORTH STAR

**Never create a dead-end output when an evidence-backed continuation can be prepared safely.** 🔱
