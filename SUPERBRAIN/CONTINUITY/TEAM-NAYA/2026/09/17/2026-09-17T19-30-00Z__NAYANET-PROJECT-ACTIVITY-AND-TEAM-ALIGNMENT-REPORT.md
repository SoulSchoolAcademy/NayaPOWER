We are building **NayaNET**, powered by **NayaPOWER**.

## 4. The standard shape of every project

Every project and sub-project is to become understandable through the same six-part structure:

**DEFINITION → BLUEPRINT → CURRENT STATE → ACTIVITY → EVIDENCE → NEXT ACTION**

### Definition
What is this thing?

### Blueprint
What is it supposed to do, how does it connect, and what are its boundaries?

### Current State
What is true now? What is implemented, partial, missing, blocked, unknown, or verified?

### Activity
What actually happened in this project, as a scoped view of canonical operational activity?

### Evidence
What proves the current claims?

### Next Action
What is the one highest-value continuation action?

This gives every Naya the same mental model when entering an unfamiliar project.

## 5. The most important Activity decision

We are **not** creating three competing activity databases.

There is one operational truth.

The official relationship is:

**NayaPOWER Main Activity**
→ **NayaNET Project Activity**
→ **NayaNET Sub-project Activity**

Project and sub-project Activity are **scoped views/projections** of the canonical operational activity.

Separately:

**Team Naya Communication Activity**

is the Naya-to-Naya coordination record.

Therefore there are three logical activity experiences, but only one canonical operational event truth:

### A. Main Superbrain Activity
What the governed system actually did.

This is the authoritative operational event substrate.

### B. Project/Sub-project Activity
What happened within a particular project or sub-project.

This is a filtered/scoped view of Main Activity.

### C. Team Naya Communication Activity
What Nayas are telling one another: findings, questions, challenges, decisions, directives, receipts, handoffs, and coordination.

This is different because it is communication between Nayas rather than the operational event ledger.

## 6. The governing rule

> **ONE EVENT → MANY USEFUL VIEWS → ONE TRUTH.**

If an action belongs to NayaNET, its canonical operational event remains in the NayaPOWER event substrate.

The NayaNET Activity view may display it.

The Intelligent Hub may display it.

A sub-project Activity view may display it.

A daily report may summarize it.

But none of those views becomes a competing source of truth.

This prevents fragmentation, duplicate events, contradictory timelines, and false claims of activity.

## 11. How Nayas should work inside this system

## 12. Build versus proof

A recurring failure mode we are explicitly eliminating is confusing:

**implemented** with **verified**.

A feature can exist in source and still not work in the live product.

A document can claim a behavior without proving it.

A test can pass while the production runtime remains disconnected.

Therefore our standard is:

**IMPLEMENTED → TESTED → OBSERVED → INDEPENDENTLY VERIFIED → CONNECTED → RECORDED → STATE UPDATED → SUCCESSOR READY**

For live behavior, add:

**LIVE VERIFIED**

## 13. Activity must reflect reality

The Activity system exists because we need to know what actually happened.

The intended boundary is:

**SUBSTANTIVE EXECUTION**
→ **CANONICAL EVENT**
→ **ACTIVITY PROJECTION**
→ **VERIFICATION**
→ **HANDOFF**

We must never solve the visibility problem by fabricating Activity messages.

If something did not happen, Activity must not imply that it happened.

If something happened but is not yet verified, the record must distinguish that state.
