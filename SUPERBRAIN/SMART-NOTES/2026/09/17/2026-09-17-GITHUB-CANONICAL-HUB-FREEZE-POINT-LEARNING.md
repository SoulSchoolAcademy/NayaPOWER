## WHAT WE LEARNED

The most important work is not getting Vercel automation working right now.

The immediate success condition is making GitHub itself reliable enough that any Naya can enter the project and know exactly:

- what the current Hub is;
- what is protected;
- what may be edited;
- where the canonical source lives;
- how a new Hub version is created;
- how the change is verified;
- how the freeze point is handed back to Shawn;
- what the next Naya should do.

## EVIDENCE

Shawn identified the current known-good Hub artifact as:
`2026 09 17 NAYANET HUB.html`

GitHub source:
https://github.com/SoulSchoolAcademy/NayaPOWER/blob/main/2026%2009%2017%20NAYANET%20HUB.html

The repository also contains a React Hub implementation under:
`NAYANET/HUB/`

This means the repository currently contains more than one Hub representation. Without an explicit canonical routing contract, a cold Naya can reasonably select the wrong artifact or wrong work lane.

The existing GitHub-first delivery standard already says the source and freeze point are primary and live deployment is secondary. The new learning is that this rule must be made Hub-specific and operationally unambiguous.

## LESSON

**Repository organization is part of Superbrain intelligence.**

Documentation alone is not enough if the retrieval path permits multiple plausible answers to “Which Hub are we working on?”

## MACHINE CONSEQUENCE

Future Hub work must follow:

**PROTECT → INSPECT → CREATE NEW → VERIFY → FREEZE → HAND OFF → REPEAT**

The protected current Hub freeze point must not be overwritten during ordinary Hub iteration.

A new Hub artifact becomes the candidate next freeze point only after the requested change is verified and Shawn receives the direct GitHub link.
