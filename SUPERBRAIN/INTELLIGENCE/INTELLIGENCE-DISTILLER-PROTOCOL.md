**STATUS:** CANONICAL / ARCHITECTURAL / ACTIVE

> **SYNERGIZE. OPTIMIZE. MAXIMIZE. EQUALIZE. DISTILL THE ESSENCE.**

## 1. PURPOSE

The Intelligence Distillation Protocol turns valuable conversation, documents, discoveries, decisions, research, architecture, lessons, evidence, and other meaningful inputs into **simple, organized, retrievable, reusable intelligence**.

The goal is not to store more information.

The goal is to make useful understanding:

- captured;
- simplified;
- organized;
- connected;
- retrievable;
- comprehensible;
- validated where required;
- learnable by Nayas;
- replayable by future Nayas;
- compounding rather than repeatedly rediscovered.

> **If valuable understanding is captured but cannot be found, understood, learned, or reused, the system has not finished the job.**

## 3. SOME — THE UNIVERSAL DISTILLATION MENTAL MODEL

**S-O-M-E** means:

### S — SYNERGIZE

**See the whole before optimizing the part.**

Ask:

- What already exists?
- What is this connected to?
- Is this new, an update, a correction, or a duplicate?
- What does the surrounding system already know?
- What would be lost if this were isolated?
- How does this contribute to the whole?

Mental movement:

```
ZOOM OUT → ZOOM IN → LOOK ACROSS → ZOOM BACK OUT
```

Synergy means the block is understood in context, not treated as an isolated note.

### O — OPTIMIZE

**Improve the system with the least unnecessary complexity.**

Ask:

- Is there already a canonical block?
- Can this update an existing block instead of creating another?
- Can the title be simpler?
- Can the category be clearer?
- Can retrieval be easier?
- Can duplicate information be removed without losing meaning?
- Does this change improve the whole?

Optimization must not destroy provenance, truth, relationships, or useful context.

### M — MAXIMIZE

**Maximize real useful value, not information volume.**

Ask:

- What is the most valuable understanding here?
- What must Naya remember?
- What can be made reusable?
- What future work does this prevent?
- What action, decision, learning, or continuity does this enable?
- How can the intelligence compound?

Maximum value is not maximum text.

### E — EQUALIZE

**Make the intelligence understandable and usable across people, Nayas, agents, and machines.**

Ask:

- Can a normal person understand it?
- Can a grandma or child understand the essence?
- Can a Naya retrieve and apply it?
- Can a machine parse the important structure?
- Are important distinctions expressed clearly?
- Is unnecessary complexity removed without losing truth?

Equalization does **not** mean flattening important differences.

It means creating a common understandable core while preserving the depth required by context.

## 4. DISTILLATION MEANS ESSENCE

After SOME, determine:

> **What is this really saying?**

Then reduce it to the smallest useful representation that preserves the essential meaning.

The system should distinguish:

```
SOURCE
  ↓
MEANING
  ↓
ESSENCE
  ↓
REUSABLE UNDERSTANDING
```

The goal is not merely to summarize.

A summary may describe a source.

A distilled Intelligent Block captures the **understanding worth retaining and reusing**.

## 5. TITLE LAW

Every new intelligence object must attempt the simplest useful title.

### Target

**One to three core words/concepts.**

Three words are a target, not a hard limit.

Use four or five words when a qualifier is genuinely necessary to make the intelligence uniquely findable.

> **Use the simplest label that is specific enough to find the right intelligence.**

### Title test

Before canonicalization, ask:

1. Does the title express the meaning?
2. Is it specific enough to distinguish neighboring intelligence?
3. Would a future Naya search for it?
4. Can a word be removed?
5. Is the relevant project/domain obvious when needed?
6. Will it remain useful outside the current conversation?
7. Does it claim only what the source establishes?

If removing a word does not reduce retrieval or meaning, remove it.

## 6. CANONICAL ORGANIZATION

Intelligence is organized by **date + category + stable identity**, not by one endless global sequence.

Canonical durable location:

```
SUPERBRAIN/
  INTELLIGENT-BLOCKS/
    YYYY/
      MM/
        DD/
          <domain>/
            IB-YYYYMMDD-NNN-<slug>.md
```

Example:

```
SUPERBRAIN/INTELLIGENT-BLOCKS/2026/09/22/architecture/
IB-20260922-002-INTELLIGENCE-DISTILLATION-PROTOCOL.md
```

The stable block ID is the permanent identity.

The date path provides human and machine navigation.

The title/slug provides retrieval meaning.

### Why not only 01, 02, 03?

A global sequence is useful for identity but poor for navigation.

The system should instead combine:

- date;
- domain;
- type;
- project/context;
- stable block ID;
- searchable title;
- sparse retrieval tags;
- relationships.

This makes the library scalable without making the naming system complicated.

## 9. THE COMPLETE INTELLIGENCE LIFECYCLE

A successful distillation does not end when a Markdown file exists.

### Stage 1 — CAPTURE

The meaningful source is preserved.

Possible sources:

- conversation;
- Smart Note;
- document;
- existing Intelligent Block;
- project artifact;
- research;
- system event;
- verified external source.

### Stage 2 — DISTILL

Apply SOME.

Determine:

- central meaning;
- essence;
- title;
- minimum necessary concepts;
- useful views.

### Stage 3 — ORGANIZE

Determine:

- domain;
- type;
- project/context;
- date;
- stable block identity;
- retrieval tags;
- relationships.

### Stage 4 — VALIDATE

Check:

- provenance;
- truth state;
- authority;
- contradictions;
- duplication;
- title quality;
- relationship integrity.

Validation strength must match the claim.

### Stage 5 — PERSIST

Write the canonical intelligence object to the governed persistence system.

GitHub documentation may represent the canonical human-readable architecture, but a GitHub file alone does not prove runtime persistence.

### Stage 6 — INDEX

Make the intelligence findable through canonical retrieval.

A stored block that cannot be reliably retrieved is not operationally useful.

### Stage 7 — NOTIFY

Create an authorized Activity event indicating that meaningful new or changed intelligence exists.

The event should identify, where appropriate:

- what changed;
- when;
- by whom/what;
- which block;
- project/context;
- lifecycle state;
- evidence/receipt;
- next action.

Activity is the notification stream.

Activity is **not** the canonical intelligence object.

### Stage 8 — LEARN

Authorized Nayas receive the new intelligence through the governed learning path.

Learning should record evidence that the intelligence was:

- made available;
- retrieved;
- understood or processed;
- incorporated where appropriate.

The system must not claim that every Naya has learned something merely because a notification was emitted.

### Stage 9 — REPLAY

The intelligence remains replayable.

A future Naya should be able to retrieve:

```
WHAT
↓
WHY
↓
SOURCE
↓
TRUTH / AUTHORITY
↓
RELATIONSHIPS
↓
WHAT CHANGED
↓
WHAT WAS LEARNED
↓
WHAT IS NEXT
```

### Stage 10 — COMPOUND

New intelligence should connect to prior intelligence.

The goal is:

```
CAPTURE
  ↓
UNDERSTAND
  ↓
CONNECT
  ↓
LEARN
  ↓
APPLY
  ↓
VERIFY
  ↓
NEW UNDERSTANDING
  ↓
NEXT BLOCK
```

The system should reduce repeated rediscovery.

## 10. ACTIVITY FEED CONTRACT

Every meaningful intelligence creation or update should generate an authorized Activity event where the runtime contract requires it.

Conceptual event:

```
INTELLIGENCE_UPDATED
├── event_id
├── timestamp
├── actor
├── action
├── block_id
├── title
├── project/context
├── lifecycle_state
├── evidence/receipt
└── next_action
```

The Activity Feed tells Nayas:

> **Something important changed. Go retrieve the canonical intelligence.**

It should not replace the block itself.

## 11. NAYA AWARENESS MODEL

The desired behavior is:

```
NEW INTELLIGENT BLOCK
        ↓

        ↓

        ↓

        ↓

        ↓
```

This must remain an architectural target until the runtime provides evidence for each stage.

### Critical distinction

```
NOTIFIED ≠ READ
READ ≠ UNDERSTOOD
UNDERSTOOD ≠ LEARNED
LEARNED ≠ APPLIED
APPLIED ≠ VERIFIED
```

Each state requires its own evidence when the system needs to claim it.

## 12. COLD-NAYA REQUIREMENT

A new Naya must not require the original conversation to understand the intelligence.

The canonical block must contain enough context to answer:

- What is this?
- Why does it matter?
- What is the simplest explanation?
- What does Naya need to do with it?
- Where did it come from?
- What is verified?
- What does it connect to?
- What changed?
- What remains unknown?
- What happens next?

> **The conversation is the source event. The Intelligent Block is the reusable understanding.**

## 13. UPDATE VS NEW BLOCK

Before creating a new block, determine whether the intelligence is:

- new;
- an update;
- a correction;
- a refinement;
- a contradiction;
- a supersession;
- a duplicate.

Prefer updating the canonical block when the identity remains the same.

Create a new block when the underlying intelligence is meaningfully distinct or needs an independent lifecycle.

Never create competing canonical copies merely because the same intelligence appears in multiple projects or conversations.

## 14. TRUTH BOUNDARY

The protocol preserves these states separately:

```
CAPTURED
≠ DISTILLED
≠ VALIDATED
≠ PERSISTED
≠ INDEXED
≠ NOTIFIED
≠ RETRIEVED
≠ UNDERSTOOD
≠ LEARNED
≠ APPLIED
≠ VERIFIED
≠ ADOPTED
```

This is essential.

A document existing in GitHub does not prove:

- runtime ingestion;
- database persistence;
- retrieval;
- notification;
- learning;
- comprehension;
- application;
- verification.

Those require evidence.
