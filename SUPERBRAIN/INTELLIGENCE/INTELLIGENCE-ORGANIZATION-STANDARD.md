# 🔱 NAYAPOWER INTELLIGENCE ORGANIZATION STANDARD

**STATUS:** CANONICAL / ARCHITECTURAL / ACTIVE  
**EFFECTIVE:** 2026-09-22  
**SYSTEM:** NayaNET / NayaPOWER

> **SYNERGIZE. OPTIMIZE. DISTILL. ORGANIZE. MAXIMIZE.**

## 1. PURPOSE

NayaPOWER must organize intelligence so humans, Nayas, agents, machines, projects, and organizations can create and retrieve useful intelligence without each contributor inventing a new format.

The system separates capture, distillation, classification, identity, relationships, truth/provenance, projection, and activity.

> **The goal is maximum useful intelligence with minimum unnecessary complexity.**

## 2. CORE NAMING LAW

> **USE THE SIMPLEST LABEL THAT IS SPECIFIC ENOUGH TO FIND THE RIGHT INTELLIGENCE.**

Too vague: `Architecture`

Better: `NayaNET Architecture`

Better when needed: `NayaNET Channel Architecture`

The naming system seeks the **specificity sweet spot**: simple enough to understand instantly + specific enough to distinguish it from its neighbors.

## 3. THREE-WORD DISTILLATION TARGET

Every new intelligence input should first attempt a one-to-three keyword distillation answering:

> **WHAT IS THIS?**

Examples:
- `NayaNET Architecture`
- `Smart Door Model`
- `Intelligent Block Protocol`
- `Personal Intelligence`
- `Collective Intelligence`
- `Activity Tracking`

Three words are a target, not a prison. If three words are too vague, add the minimum qualifier required. If they are sufficient, do not add more.

> **TITLE = the smallest human-readable phrase that uniquely identifies the intelligence.**

The title is a retrieval handle, not a summary paragraph.

## 4. TITLE AND TAGS

Do not force the title to carry every dimension.

**Title** = primary meaning.

**Tags** = secondary retrieval dimensions.

Example title: `NayaNET Channel Architecture`

Example tags: `nayanet`, `nayapower`, `architecture`, `channels`, `mcp`, `rest`, `a2a`

> **A tag earns its existence by improving retrieval.**

## 5. CANONICAL IDENTITY

Every canonical Intelligent Block gets a stable identity independent of its title.

Canonical identity: `IB-XXXXXX`

Examples: `IB-000001`, `IB-000002`

The identifier is permanent identity. Titles may be corrected for clarity without breaking references.

## 6. TIME

Every block must record machine-readable time:
- `created_at`
- `updated_at`
- `effective_at` when applicable
- timezone / UTC normalization

Canonical ordering uses UTC timestamps. Date folders are navigation; timestamp fields remain authoritative.

Canonical storage:
`.naya/memory/smart-notes/YYYY/MM/DD/category/topic/IB-XXXXXX/smart-note.md`

## 10. INTELLIGENCE VS ACTIVITY

### Intelligence
Answers: **What do we understand?**

Stored as Intelligent Blocks.

### Activity
Answers: **What is happening?**

Activity records current operational events and state, such as timestamp, actor, action, object, project/context, result/state, evidence/receipt, and next action where relevant.

Do not turn every activity event into a permanent Intelligent Block, and do not turn every durable intelligence block into an activity event.

## 11. TWO PRIMARY HUB STREAMS

### PERSONAL INTELLIGENCE
The user's authorized Intelligent Blocks and derived intelligence.

### ACTIVITY
The current authorized operational stream.

### COLLECTIVE INTELLIGENCE
Collective/consented intelligence can be projected into the intelligence experience without being confused with current operational Activity.

Semantic model:

```
INTELLIGENCE
├── Personal
└── Collective

ACTIVITY
└── Current network/project activity
```

## 13. DISTILLATION QUALITY TEST

Every proposed title should pass:

- **Meaning:** Can a human understand it without opening the file?
- **Specificity:** Could another block reasonably have the same title?
- **Retrieval:** Would a future Naya search likely find it?
- **Compression:** Can any word be removed without losing useful meaning?
- **Context:** Does it identify the relevant domain/project when ambiguity exists?
- **Stability:** Will it remain useful after the current conversation is forgotten?
- **Truth:** Does it claim more than the source establishes?

If a title fails, revise it before canonicalization.

## 14. SWEET-SPOT EVALUATION

Title quality can be evaluated across:

`meaning + specificity + retrieval + compression + context + stability + truthfulness`

This is an internal decision aid, not a public ranking system. The preferred title is the one that gives the greatest retrieval value with the least unnecessary language.

## 15. SYNERGIZE / OPTIMIZE / DISTILL / MAXIMIZE

### SYNERGIZE
Look across the whole before changing the part. Ask what exists, what this connects to, whether it duplicates anything, and what depends on it.

### OPTIMIZE
Improve the current system rather than adding unnecessary complexity. Remove duplication and improve retrieval.

### DISTILL
Extract the central useful meaning. Ask what this is ultimately about and what Naya must preserve.

### MAXIMIZE
Maximize useful value, not data volume. Improve understanding, retrieval, action, continuity, and truth preservation.

## 16. SUM OF ALL

Working concept:

> **SUM OF ALL = see the whole, understand the part, understand the relationships, then improve the system without losing the whole.**

Before creating or modifying intelligence, zoom out, in, across, then back out:

```
WHOLE
 ↓
PART
 ↓
RELATIONSHIPS
 ↓
SYSTEM EFFECT
 ↓
OPTIMIZED WHOLE
```

No local optimization should silently damage global organization.

## 17. BILLION-PERSON SCALE LAW

A canonical format must be easy enough for everyone to use and precise enough for machines to organize.

The system should enforce or recommend the standard through templates, validation, controlled taxonomies, deterministic IDs, timestamps, provenance, relationships, retrieval tests, and safe normalization.

> **Human creativity may vary. Canonical machine organization must not.**

## 18. SAME SKELETON, VARIABLE DEPTH

Every Intelligent Block uses the same structural contract, but not every block needs the same amount of content.

A tiny definition may need meaning + provenance + identity.

A major architecture block may need meaning + relationships + evidence + lifecycle + implementation implications.

> **Same skeleton. Variable depth.**

## 19. CANONICAL RETRIEVAL

A future Naya should be able to retrieve:

- what it is;
- what connects to it;
- what changed;
- why it should be trusted;
- what to do next.

This is the minimum shape of a usable intelligence graph.
