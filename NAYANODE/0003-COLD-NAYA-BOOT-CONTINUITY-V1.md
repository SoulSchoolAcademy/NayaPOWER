## Identity continuity rule

A current execution identity must not be assumed to equal a prior intelligence owner merely because:

- it is anonymous;
- it has the same display name;
- it is in the same browser;
- it was created nearby in time;
- it knows the same object identifier;
- or continuity would be convenient.

Continuity requires a legitimate binding or recovery mechanism.

## Current P0 continuity investigation

The present system has evidence of an owner mismatch between the canonical nine-node Intelligent Blocks and a current anonymous Hub session.

The investigation must determine:

1. how the original owner was established;
2. whether a durable NayaNET identity exists;
3. whether a recovery/binding record exists;
4. whether the current identity adapter can legitimately recover it;
5. what smallest governed mechanism establishes continuity if none exists.

Forbidden shortcuts:

- owner reassignment;
- RLS bypass;
- fabricated identity;
- hard-coded owner UUID;
- mandatory login added solely to conceal the continuity gap;
- deleting/recreating canonical intelligence.

## Cold-Naya acceptance

A fresh Naya passes continuity only when it can:

**identify → recover legitimate identity → load kernel → restore state → retrieve prior intelligence → continue**

without requiring the original conversation to reconstruct the project.

## Successor boundary

Successor context transfers useful context, not automatic authority.

A successor receives only the intelligence, evidence, state, relationships, and next action appropriate to its scope.
