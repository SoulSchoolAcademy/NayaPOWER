# 🔱 NAYA DESIGN PROTOCOL V1
## Signature Interface Language, Craft Standard & Builder Operating System

**Status:** Human-Director-directed synthesis candidate  
**Purpose:** Teach Naya and every builder how to recognize, reproduce, improve, and verify the distinctive NayaNET interface language without flattening it into generic SaaS or drifting into decorative excess.  
**Authority model:** This document is a synthesis/projection of existing Hub design law, Human Director taste, live NayaNET reference work, and external design research. It does not create a second design authority. Conflicts must reconcile upward into the canonical Hub Design Contract and Human Director direction.

---

# 0. THE MISSION

NayaNET should become visually recognizable in the same way a great artist, industrial designer, automotive marque, or operating system becomes recognizable.

The goal is not to make every screen identical.

The goal is that every screen carries the same **design intelligence**.

A person should be able to see:
- a button;
- a board;
- a jewel;
- a portal;
- a search surface;
- a status object;
- a Naya presence;
- a full room;

and know:

> **This is Naya.**

The desired standard is not “good for AI-generated UI.”

The reference sites are the **floor**, not the ceiling.

The target is a category-defining intelligent environment whose craft is strong enough that elite product teams would study it — while remaining clearer, more useful, more readable, more truthful, and more coherent than the reference work.

## 1.1 The style is already a language, not random taste

Across the strongest references, the same families recur:

- near-black / obsidian foundation;
- violet/purple atmospheric light;
- semantic spectral accent families;
- highly dimensional dark surfaces;
- jewel-like circular or faceted icons;
- elevated pill/action controls;
- large soft radii for major surfaces;
- hard white specular highlights used sparingly;
- multiple shadow layers rather than one generic box-shadow;
- subtle radial environmental glows;
- strong contrast between quiet background and energized interactive object;
- bold modern sans-serif for system voice;
- serif/italic voice for intimate or human/Naya editorial moments;
- “eyebrow” / kicker labels above major headings;
- premium spacing;
- cinematic composition rather than dashboard grids.

The live source confirms that this is not accidental.

Examples observed in current reference CSS include:
- near-black foundations such as `#05030a`, `#030305`, `#050408`;
- recurring violet/purple anchors such as `#a66cff`, `#9b5de5`, `#765cff`;
- full-spectrum semantic colors including gold/yellow, emerald/green, blue/sapphire, magenta and red;
- large radii such as 28–32px for important surfaces and `999px` for pill controls;
- layered shadows combining inset highlights, physical lower depth, cast shadow and local glow;
- Inter-family system typography paired in places with Georgia/serif editorial voice.

## 1.2 The strongest existing buttons are “physical light objects”

The best reference buttons do not read as flat rectangles.

They use a stack similar to:

`dark material core → top highlight → edge → lower depth → cast shadow → semantic glow → hover lift → press compression`

This is one of the most distinctive parts of the visual language.

Examples in reference source use combinations such as:
- inset white highlight;
- inset dark lower body;
- 4–5px lower physical edge;
- 12–30px cast shadow;
- local violet/magenta/gold/other color glow;
- rounded pill geometry.

**Learning:** Naya buttons should feel engineered, not merely styled.

## 1.3 The strongest boards feel like rooms inside the room

The best existing panels use:
- large radii;
- black-to-near-black directional gradients;
- precise edge light;
- faint internal reflection;
- soft environmental aura;
- substantial outer shadow;
- embedded identity object/icon.

This gives the sense that a board is a **destination / instrument**, not a card.

**Learning:** generic card grids are beneath the Naya standard.

## 1.4 The icons are closer to jewelry than iconography

The strongest icon family resembles:
- gemstone/faceted material;
- white specular points;
- internal gradient;
- contained glow;
- dark housing;
- optical depth.

They feel like small precision objects, not flat symbols.

**Learning:** production NayaNET needs one coherent Intelligence Glyph family — not mixed emojis, Font Awesome, random SVG packs, and custom jewels all at once.

## 1.5 The spectrum is a semantic language

The reference work already uses more than purple:
- magenta;
- violet;
- indigo;
- sapphire/blue;
- teal;
- emerald;
- lime;
- yellow;
- gold;
- orange;
- red.

The important lesson is not “use more colors.”

It is:

> **Give every color a reason.**

Room theme, state, identity, action, value, warning and connection are different semantic jobs.

## 1.6 The current work is visually ambitious but not yet fully mature

The references also reveal why they are the floor, not the target:

- some microtype is too small;
- some glow is stronger than the information hierarchy needs;
- icon systems are not fully unified;
- density and spacing vary by page;
- some pages rely on one-off CSS rather than system tokens;
- interaction/state coverage is uneven;
- visual language can become decorative where product purpose is weak;
- pages do not yet behave as one complete product.

The next level is not “more effects.”

It is **more system, more discipline, more readability, more coherence, more causality, more finish**.

# 2. THE NAYA SIGNATURE — TEN TRAITS

A Naya interface should be recognizable through ten signature traits.

## 2.1 OBSIDIAN FOUNDATION

The environment begins dark.

Not pure flat black everywhere.

Use a controlled family:
- void / canvas black;
- recessed black;
- surface black;
- raised graphite;
- active graphite.

Darkness creates:
- calm;
- contrast;
- perceived depth;
- room for spectral light;
- visual focus.

### Do
Use subtle value differences to create structure.

### Do not
Use one `#000` background for every level.

---

## 2.2 VISUAL BLISS

The first visual law:

> **Contrast, clarity, cleanliness, hierarchy, readable type, spacing and restraint outrank every effect.**

No glow, depth, gradient, animation or spectral accent may make information harder to read.

If an effect and comprehension conflict:
**comprehension wins.**

This is what prevents NayaNET from becoming “neon cyberpunk UI.”

Naya is premium intelligence, not visual noise.

---

## 2.3 LIVING DEPTH

Objects should feel present in space.

The canonical material stack:

`environment → shadow → lower edge/depth → material body → internal gradient → luminous edge → top reflection → semantic energy`

Not every component needs every layer.

Depth should answer:
- is this passive?
- interactive?
- selected?
- floating?
- modal?
- critical?

Depth is information.

---

## 2.4 SPECTRAL INTELLIGENCE

Canonical spectrum:

**PURPLE → INDIGO → SAPPHIRE → TEAL → EMERALD → LIME → YELLOW → GOLD → ORANGE → RICH ORANGE → RED → MAGENTA → PURPLE**

Suggested semantic defaults:

- **Purple** — intelligence / emergence / identity
- **Indigo** — depth / comprehension
- **Sapphire** — knowledge / information
- **Teal** — connection / flow
- **Emerald** — healthy / live / available
- **Lime** — growth / learning
- **Yellow** — attention / signal
- **Gold** — significance / value / consequence
- **Orange** — action / movement
- **Rich Orange** — transition / momentum
- **Red** — risk / warning / destructive consequence
- **Magenta** — human significance / expression / creation

Theme ≠ status.

A purple room can still show a red error or green healthy state.

---

## 2.5 PRIMO CONTROLS

A Naya control should never look like a generic web button.

It should look:
- intentional;
- tactile;
- precise;
- accessible;
- calm at rest;
- alive under interaction.

A primary action gets stronger energy.

Secondary actions remain refined but quieter.

Not every action is primary.

---

## 2.6 INTELLIGENCE BOARDS

A board is not a rectangle around content.

It is an intelligence object with:
- identity;
- purpose;
- theme;
- truth state;
- content hierarchy;
- actions;
- provenance;
- continuity.

The user should feel able to “enter” it.

---

## 2.7 JEWEL GLYPHS

Icons should be:
- faceted;
- optically consistent;
- luminous under interaction;
- semantically themed;
- one family.

They may range from minimal line glyph to full identity jewel depending on importance.

Not every icon should be a gemstone.

But every primary icon should feel related.

---

## 2.8 CINEMATIC COMPOSITION

Naya rooms should feel composed, not tiled.

Use:
- strong focal hierarchy;
- asymmetry when useful;
- deliberate negative space;
- story order;
- controlled density;
- large “moments” balanced by quiet detail.

Do not default to:
`heading + 4 KPI cards + card grid`.

---

## 2.9 DUAL VOICE TYPOGRAPHY

Two voices are useful:

### System voice
Modern sans-serif:
- clear;
- precise;
- high legibility;
- strong hierarchy.

### Human / Naya editorial voice
Serif or italic editorial treatment:
- intimate;
- reflective;
- selective;
- never used for dense system text.

This creates the feeling that the intelligence system and the thinking partner have related but distinct voices.

---

## 2.10 TRUTHFUL LIVENESS

The interface feels alive because real state changes.

Not because decorative objects pulse.

Motion must correspond to:
- hover recognition;
- focus;
- selection;
- real loading;
- actual transition;
- success;
- error;
- speaking/listening;
- new intelligence arriving.

Fake activity is prohibited.

# 3. THE NAYA MATERIAL SYSTEM

## 3.1 Foundation levels

Recommended conceptual levels:

- **VOID** — deepest background
- **CANVAS** — normal room background
- **RECESSED** — wells, search fields, inactive panels
- **SURFACE** — standard boards
- **ELEVATED** — interactive boards / selected content
- **FLOATING** — menus, sheets, inspectors
- **CRITICAL** — modal/confirmation only

Each level should be tokenized.

## 3.2 Surface recipe

Canonical premium board recipe:

- low-chroma near-black body;
- subtle directional gradient;
- one-pixel edge with low-opacity neutral highlight;
- room-theme accent rail or local edge;
- inner top highlight;
- deep cast shadow;
- restrained room aura;
- readable neutral text.

## 3.3 Reflection

White/specular highlights create perceived material quality.

Use them:
- on top edges;
- jewel facets;
- button upper surfaces;
- active rims.

Do not use them everywhere.

## 3.4 Glow

Glow is a **secondary lighting effect**.

Use around:
- active edges;
- jewels;
- selected rails;
- local environment.

Never behind paragraphs.

If text edges lose clarity, reduce glow.

# 4. THE NAYA BUTTON PROTOCOL

## 4.1 Anatomy

Every important button defines:

1. geometry;
2. material body;
3. edge;
4. upper highlight;
5. lower depth;
6. cast shadow;
7. semantic accent;
8. icon/glyph;
9. label;
10. focus state;
11. hover state;
12. press state;
13. loading;
14. success;
15. error;
16. disabled.

## 4.2 Rest

Rest should already look clickable.

Do not require hover to discover affordance.

## 4.3 Hover

Recommended:
- 2–3px optical lift;
- slightly stronger border;
- slightly stronger semantic glow;
- clearer glyph;
- longer shadow;
- no layout shift.

## 4.4 Press

Press should:
- move down;
- reduce cast shadow;
- deepen body;
- subtly compress.

Do not use cartoon bounce.

## 4.5 Focus

Keyboard focus is a first-class design state.

It must be stronger than a vague colored glow.

Use a high-contrast focus ring that remains visible across every room theme.

## 4.6 Loading

Never replace context with an anonymous spinner.

Preserve:
- control identity;
- current operation;
- ability to understand what is happening.

## 4.7 Labels

Use outcome language:
- Enter NayaNET
- View Evidence
- Review Today
- Connect GitHub
- Open Source
- Keep Private
- Compare Reports

Avoid:
- Submit
- Go
- Click Here
- OK

## 4.8 Shape families

### Pill
High-value concise action.

### Soft rectangle
Dense action group / tool.

### Jewel action
Rare identity/hero interaction.

### Icon-only
Only when universally understandable and accessible.

## 4.9 Hard rule

> **A beautiful dead button is a defect.**

Every live button must connect to a causal path or honest unavailable state.

# 5. THE NAYA BOARD PROTOCOL

## 5.1 Board anatomy

A serious board should define:

- identity jewel/glyph;
- title;
- orientation sentence;
- truth/provenance state;
- theme;
- summary;
- primary intelligence;
- nested perspectives;
- actions;
- evidence;
- continuity.

## 5.2 Layer hierarchy

Typical intelligence hierarchy:

1. **In a Nutshell**
2. Human Note
3. Child / Simplified
4. Grandma / Why Notice
5. Naya Note
6. Machine / Evidence Boundary
7. Learning
8. What It Means
9. How To Use It
10. What's In It For You

These are nested perspectives of one intelligence object.

They should not become ten equally loud cards.

Use progressive disclosure.

## 5.3 Theme

A board has one dominant spectral identity.

The theme may affect:
- accent rail;
- icon;
- small section markers;
- active controls;
- local aura.

It should not recolor all body copy.

## 5.4 Board states

- REST
- HOVER / AWARE
- SELECTED
- LOADING
- EMPTY
- BLOCKED
- NOT_VERIFIED
- VERIFIED
- ERROR

Every state should remain visually beautiful.

# 6. THE NAYA GLYPH / ICON PROTOCOL

## 6.1 One family

Production must converge to one Intelligence Glyph family.

Desired traits:
- geometric precision;
- faceted/jewel logic;
- consistent optical weight;
- coherent stroke/fill strategy;
- high-quality light behavior;
- semantic accent.

## 6.2 Importance tiers

### Utility glyph
Minimal line/solid icon.

### Navigation jewel
Contained dimensional icon.

### Board identity jewel
Larger, distinctive, themed.

### Naya identity/emblem
Highest visual significance.

## 6.3 No emoji dependence

Emoji can remain in informal content.

They should not be the final primary navigation icon system.

## 6.4 Icon motion

Icon liveness should be subtle:
- brighten;
- small facet shift;
- tiny glow expansion;
- selected state.

Avoid continuous spinning/pulsing unless it communicates real process.

# 7. TYPOGRAPHY PROTOCOL

## 7.1 Human comfort

Body text target:
**17–18px**

Normal floor:
**16px**

Controls:
**15–16px**

Support:
**14px+**

Metadata:
**13–14px normally**

Critical information is never microtype.

## 7.2 Hierarchy

Use a consistent semantic type ladder:
- Display
- Page Title
- Section Title
- Object Title
- Body
- Support
- Metadata
- State / Kicker

## 7.3 Eyebrows / kickers

The reference work uses small uppercase pre-headlines effectively.

Naya version:
- concise;
- high tracking;
- semantic color or neutral;
- never primary reading text;
- not too small.

## 7.4 Editorial voice

Serif italic should be rare.

Use for:
- Naya reflection;
- human note;
- intimate transition;
- a short quote / emotional anchor.

Do not mix serif into dense controls or data.

## 7.5 Line length

Long intelligence text should generally remain around 55–80 characters per line.

---

# 8. SPACING & GEOMETRY

## 8.1 Spacing is part of the brand

Naya should feel generous, not cramped.

Use a finite spacing scale.

Recommended base family:

`4 · 8 · 12 · 16 · 20 · 24 · 32 · 40 · 48 · 64 · 80`

## 8.2 Board padding

Large boards should have generous internal breathing room.

Do not solve density by shrinking everything.

## 8.3 Radius family

Define a limited family:

- small: 10–12px
- control: 14–18px
- board: 22–32px
- portal: 28–36px
- pill: 999px

The existing reference work already clusters strongly around 16px, 28–32px, and pill geometry.

## 8.4 Shape variation

Do not make every surface a 24px rounded rectangle.

Use:
- capsules for controls;
- large soft boards;
- circles/facets for jewels;
- recessed wells for inputs;
- occasional sculptural irregularity for special identity moments.

# 9. LAYOUT & COMPOSITION

## 9.1 The Naya frame

The normal desktop Hub composition:

`stable left rail → quiet top context → prominent intelligence search → room canvas`

Naya remains contextual, not a permanent giant chatbot panel.

## 9.2 The eye path

Every screen must intentionally answer:

1. Where am I?
2. What matters?
3. What is the primary instrument?
4. What can I do?
5. What is supporting detail?

If the eye has five competing destinations, simplify.

## 9.3 Search

Search is a primary intelligence door.

It should be:
- prominent;
- spacious;
- understandable;
- semantic;
- visually important.

Do not bury it as a tiny icon.

## 9.4 Mobile

Mobile is not desktop stacked vertically.

Preserve:
- room identity;
- readable type;
- depth;
- meaningful actions;
- current location.

Transform navigation, density, and detail presentation intentionally.

# 10. NAYA PRESENCE

Naya is the intelligent partner inside the system.

She is not:
- a floating customer-support bubble;
- a giant permanent right rail;
- decorative AI theater.

Naya should appear contextually.

Examples:
- Today: “What matters most today?”
- Reports: “What changed across this period?”
- Library: “What am I missing?”
- Ledger: “Explain this causal chain.”
- Connect: “Which Door should I use?”
- Connections: “Why does this relationship matter?”

Her visual presence should feel premium, calm and aware.

# 11. MOTION LANGUAGE

## 11.1 Signature motion

Preferred motion:
- short;
- smooth;
- physical;
- restrained;
- interruptible;
- state-driven.

Suggested ranges:
- micro response: 100–180ms
- standard: 180–280ms
- room/context transformation: 280–500ms

## 11.2 Motion does not equal liveness

Infinite breathing/pulse should be rare.

The interface can feel alive while mostly still.

## 11.3 Reduced motion

Reduced motion must preserve:
- hierarchy;
- state;
- focus;
- meaning.

# 12. EXTERNAL DESIGN RESEARCH — WHAT THE BEST SYSTEMS CONFIRM

The Naya design language should remain original, but elite systems validate several principles.

## 12.1 Dieter Rams — usefulness, understandability, honesty, detail

Rams' principles reinforce:
- useful before decorative;
- understandable;
- honest;
- thorough to the last detail;
- as little design as possible without removing what matters.

Naya translation:

> **Maximum intelligence. Minimum unnecessary interface.**

This does not mean visually plain.

It means every effect earns its place.

## 12.2 Apple — feedback must match significance

Elite interfaces continuously communicate:
- status;
- success/failure;
- warning;
- next opportunity.

Naya translation:

A control is incomplete until the human knows what happened.

## 12.3 Nielsen Norman — visibility of system status

Predictable feedback creates trust.

Naya translation:

The system must show:
- READY;
- BLOCKED;
- NOT VERIFIED;
- VERIFIED;
- ERROR;
- loading/progress;
- consequence.

Truthful state is part of visual design.

## 12.4 Microsoft Fluent — hierarchy and semantic color

Fluent emphasizes typographic hierarchy, legibility, and standardized palettes with intentional roles.

Naya translation:

Do not treat the spectrum as decoration.

Use tokens and semantic aliases.

## 12.5 Atlassian — tokens reduce drift

Tokens create a shared language for:
- color;
- spacing;
- typography;
- elevation;
- opacity.

Naya translation:

A room can have its own theme without inventing its own physics.

## 12.6 Carbon — consistent spacing creates coherent layout

Spacing systems create functional, cohesive experiences.

Naya translation:

Spacing should be governed like color.

## 12.7 WCAG — accessibility is measurable craft

Naya should exceed minimums:
- readable contrast;
- visible focus;
- generous target size;
- text scaling;
- keyboard operation.

Premium design is comfortable for more humans.

# 16. THE NAYA ROOM DESIGN METHOD

For every room:

## Step 1 — Human job
Define:
> “When I enter this room, what one human job should become easier?”

## Step 2 — Signature instrument
Define one unique interaction object.

Examples:
- Feed → Intelligence Stream
- Today → Daily Intelligence Story
- Reports → Time Synthesis Reader
- Library → Semantic Search + Inspector
- Connect → Smart Door Instrument
- Ledger → Causal Receipt Timeline
- Connections → Relationship Inspector
- Lists → Mission Table
- Mail → Signal + Context Reader
- Spaces → Context Environment
- Settings → Control Deck

## Step 3 — First three seconds
Draw exactly what the user sees first.

## Step 4 — Control inventory
List every visible control:
- placement;
- purpose;
- frequency;
- consequence;
- state.

## Step 5 — Data contract
State:
- canonical source;
- object IDs;
- projection rules;
- unavailable behavior.

## Step 6 — State matrix
Design all applicable truth states.

## Step 7 — Mobile transformation
Decide what collapses, what stays, what moves.

## Step 8 — Visual theme
Define:
- room accent;
- density;
- primary material;
- signature jewel;
- motion level.

## Step 9 — Annotated visual
Render the intended room before production implementation.

## Step 10 — Human taste review
Review image + spec together.

## Step 11 — Freeze
Freeze:
- spec;
- visual;
- machine contract;
- acceptance journey.

## Step 12 — Build
Builder executes rather than inventing product.

## Step 13 — Render / interact / verify
Test behavior and visual fidelity.

## Step 14 — Independent eye
Independent reviewer verifies.

## Step 15 — Ratchet
Freeze accepted room baseline.

Then move to the next room.

# 18. VISUAL QUALITY CHECKPOINTS

## Checkpoint A — silhouette
Blur/squint at the screen.

Can the major hierarchy still be understood?

## Checkpoint B — grayscale
Does hierarchy work without spectral color?

If not, color is doing too much.

## Checkpoint C — no glow
Temporarily remove glow.

Does the interface still feel coherent?

If not, geometry/material hierarchy is weak.

## Checkpoint D — reduced motion
