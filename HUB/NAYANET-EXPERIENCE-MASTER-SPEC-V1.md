# 2. WHAT NAYANET IS

NayaNET is the **human-facing experience and network of interfaces over NayaPOWER**.

NayaPOWER is the governed intelligence substrate.

The Hub is the principal human cockpit/projection.

The rooms are purpose-built views into that governed intelligence.

The system should feel like one intelligent environment, not eleven applications.

### Whole-product definition

**NayaNET should:**

1. understand the human's current context;
2. retrieve or receive canonical intelligence;
3. distill what matters;
4. present the right depth of understanding;
5. make the next useful action obvious;
6. execute only through governed capability and authority;
7. report truthful state and provenance;
8. preserve continuity;
9. turn verified outcomes into learning;
10. return that improved intelligence to future experiences.

### The core experience equation

```
SOPHISTICATED INTELLIGENCE
→ SIMPLE HUMAN UNDERSTANDING
→ OBVIOUS ACTION
→ TRUTHFUL RESPONSE
→ VERIFIED OUTCOME
→ LEARNING
→ BETTER FUTURE EXPERIENCE
```

# 4. THE HUMAN JOURNEY

The canonical journey is:

```
WELCOME
→ IDENTITY
→ MAIN SHOW / HUB
→ CHOOSE OR FOLLOW INTELLIGENCE
→ ENTER ROOM
→ INSPECT / ACT
→ OBSERVE RESULT
→ VERIFY / UNDERSTAND PROOF
→ LEARN / CONTINUE
→ RETURN
```

### The arrival should feel like continuity, not setup.

**Welcome:** invitation.

**Identity:** recognition + trust.

**Main Show:** Naya has already done useful cognitive work.

**Room:** the human enters a purpose-built mode of thought.

**Object:** the meaningful unit becomes inspectable.

**Action:** the system makes one useful next move obvious.

**Outcome:** the human sees what happened.

**Proof:** truth and provenance are available at the right depth.

**Learning:** verified improvement becomes part of the system's future advantage.

### Time-horizon contract

**1 second:** presence and orientation.

**3 seconds:** what matters is legible.

**30 seconds:** one useful action is obvious.

**Return visit:** the system feels continuous and remembers relevant context without pretending to remember unsupported things.

# 5. THE MAIN SHOW

## 5.1 Job

**Arrive inside NayaNET already oriented, recognized and ready to move.**

Main Show is not a dashboard and not a generic homepage.

It is the first visible proof that the underlying intelligence is doing work.

### Main questions

- **WHERE AM I?** Inside my Intelligent Hub.
- **WHAT MATTERS?** The few highest-value things Naya has already distilled.
- **WHAT CAN I DO?** Open the dominant intelligence, ask Naya, or enter a room.
- **WHAT HAPPENS NEXT?** The selected path carries context forward.

## 5.2 Experience arc

```
PRESENCE
→ RECOGNITION
→ DISTILLATION
→ INVITATION
→ FLOW
```

## 5.3 Main Show composition

The composition is subordinate to the information architecture.

Recommended hierarchy:

1. Naya presence / identity
2. dominant current intelligence
3. concise why-now / relevance
4. obvious next move
5. supporting intelligence
6. quiet navigation
7. deeper evidence on demand

The human should be able to understand the point without opening every object.

## 5.4 The Main Show must never become

- a KPI grid merely because metrics exist;
- a social feed merely because events exist;
- a feature catalog merely because capabilities exist;
- a decorative hero hiding the real intelligence;
- a fake-activity animation;
- a second command center that bypasses room/function contracts.

## 5.5 The wow principle

The first wow should come from:

> **Naya already understood what mattered.**

Visual craft amplifies that realization.

Visual craft must not substitute for it.

# 7. THE FUNCTION-FIRST DESIGN LAW

Every visible visual decision must be traceable to a human or system job.

Use this sequence:

```
HUMAN JOB
→ 3-SECOND UNDERSTANDING
→ INFORMATION HIERARCHY
→ PRIMARY ACTION
→ STATES
→ CAUSAL PATH
→ COMPONENTS
→ VISUAL FORM
→ MATERIAL / MOTION
```

### Therefore:

A card is not a reason.

A board is not a reason.

A glow is not a reason.

A graph is not a reason.

A modal is not a reason.

A button is not a reason.

They are solutions to previously understood functional needs.

### Every element must answer

1. What job do you do?
2. What information do you make easier to understand?
3. What action do you enable or explain?
4. What truth/state do you communicate?
5. What happens when the human uses you?
6. What proves the result?
7. What happens to continuity afterward?

If those questions cannot be answered, the element is not yet justified.

# 11. UNIVERSAL STATE CONTRACT

All rooms inherit the same semantic state vocabulary.

```
LOADING
EMPTY
READY
BLOCKED
UNAUTHORIZED
NOT_VERIFIED
VERIFIED
ERROR
OFFLINE
DISABLED
UNKNOWN
```

### State honesty rules

- LOADING never pretends to be READY.
- EMPTY never invents sample data.
- BLOCKED never looks like completion.
- UNAUTHORIZED never masquerades as disconnected data.
- NOT_VERIFIED never renders as VERIFIED.
- VERIFIED only appears where evidence supports it.
- ERROR explains enough to recover.
- OFFLINE distinguishes cached context from live truth.
- UNKNOWN remains unknown.
- DISABLED remains clearly unavailable.
- No animation may imply activity that did not happen.

### UI state is itself a claim

A visible state must be generated from real system state or from an explicitly labeled design/test fixture.

# 12. CAUSAL ACTION LAW

Every interactive element must have a complete causal path.

Minimum shape:

```
HUMAN INTENT
→ CONTEXT
→ AUTHORITY SCOPE
→ RUNTIME OPERATION
→ OBSERVATION
→ RESULT
→ UI STATE
→ EVIDENCE WHERE REQUIRED
```

### Therefore

A button is not complete because it is clickable.

A search field is not complete because it accepts text.

A filter is not complete because the screen changes.

A connection is not complete because a badge says connected.

A save is not complete because local state changes.

A persisted-looking object is not complete because it survives one repaint.

Completion belongs to the **causal path**, not the appearance of the control.
