# 🔱 NAYA DESIGN DO / DON'T CHECKLIST V1

**Status:** CONVERGED CANDIDATE projection of the Naya Design Protocol; not a second score system or authority.  
**Parent:** `HUB/DESIGN/NAYA-DESIGN-PROTOCOL-V1.md`  
**Use:** mechanical critique before freeze, during build, and during independent verification.  
**Rule:** a checklist tick never overrides a hard gate or D1–D8 evidence.

---

# 100 DOs

## Meaning, language, hierarchy — 1–10
1. State the human job before drawing the interface.
2. Name one primary question the surface answers.
3. Make the first-three-seconds outcome explicit.
4. Give every region one job.
5. Write button labels as concise outcome-oriented verbs.
6. Name sections by what they help the human understand or do.
7. Prefer recognition over recall; keep important actions discoverable.
8. Use plain human language before backend terminology.
9. Make one focal hierarchy obvious in each viewport.
10. Remove words the structure, icon, state, or control already communicates.

## Readability and typography — 11–20
11. Keep normal body text at 16px minimum; target 17–18px.
12. Keep controls/navigation at 15px minimum.
13. Keep support text at 14px minimum.
14. Keep metadata at 13px minimum and non-critical.
15. Keep eyebrows/kickers at 12px minimum.
16. Keep critical truth/privacy/authority/warning/state/action text at 14px minimum.
17. Use approximately 1.5–1.7 line-height for body.
18. Keep long reading measures roughly 55–80 characters.
19. Reflow layout before shrinking readable text.
20. Test 125%, 150%, and 200% zoom with no clipped critical content.

## Color and contrast — 21–30
21. Let purple/deep-purple, obsidian, and white carry Naya identity.
22. Give every accent a semantic reason.
23. Use hierarchy, position, weight, and spacing before hue.
24. Keep primary reading text high-contrast neutral.
25. Use teal for connection/flow only when the room/context contract supports it.
26. Use emerald for healthy/available/confirmed operational state only when true.
27. Use red only for risk, destructive consequence, or warning.
28. Reserve yellow/gold for necessary semantic states; never as Naya brand accent or default room/action hue.
29. Pair meaningful color with text/icon/shape so color is never the only signal.
30. Check the screen in grayscale; hierarchy should still work.

## Controls — 31–40
31. Build controls from the canonical Power Object anatomy.
32. Keep touch targets at least 44×44 CSS px.
33. Make the control visibly actionable at rest.
34. Give desktop hover a physical recognition response without layout shift.
35. Give press a physical compression/depth response.
36. Give keyboard focus a clear treatment independent of hover.
37. Preserve label/context during loading.
38. Render disabled controls as clearly non-live but still readable.
39. Show real consequence as the primary proof of success.
40. Trace consequential controls through intent → authority/scope → capability → operation → observation → result → state/evidence.

## Boards and content — 41–50
41. Treat boards as intelligence destinations, not generic cards.
42. Give each board identity, title, orientation, truth/provenance, theme, intelligence, action, evidence, and continuity where applicable.
43. Keep one idea per region.
44. Use progressive disclosure for depth.
45. Put human-readable meaning before machine detail.
46. Keep the eight Smart Board intelligence layers in their canonical order when applicable.
47. Keep furniture and optional extensions separate from the eight canonical layers.
48. Keep Naya interpretation labeled as interpretation, never source truth.
49. Distill each intelligence layer until it reads in one breath where practical.
50. Make evidence reachable without turning the primary surface into a proof dump.

## State and truth — 51–60
51. Design all applicable truth states: LOADING, EMPTY, READY, BLOCKED, UNAUTHORIZED, NOT_VERIFIED, VERIFIED, ERROR, OFFLINE, DISABLED.
52. Design all applicable interaction states: REST, HOVER, FOCUS, PRESSED, SELECTED, LOADING, SUCCESS, ERROR, DISABLED.
53. Make EMPTY mean the system successfully knows there is no applicable content.
54. Keep UNKNOWN explicit when the system cannot resolve state.
55. Show VERIFIED only with applicable evidence.
56. Show CONNECTED only with applicable backend evidence.
57. Timestamp changing state when staleness matters.
58. Make errors answer what failed, whether anything changed, and what action is safe next.
59. Label fixture/sample data or do not render it as current truth.
60. Make important displayed claims re-derivable from canonical state/evidence.

## Icons and signature — 61–70
61. Use one Naya glyph family.
62. Use Jewel Marks for identity/high-significance moments.
63. Use Action Glyphs for controls and compact utility.
64. Use only 16/24/32/48/64/96 production size tokens.
65. Keep the family light source consistent.
66. Keep glyph cores high-contrast neutral/white.
67. Put semantic energy in rim/field/facet/aura rather than destroying glyph contrast.
68. Test a glyph at its smallest intended token before approving it.
69. Pair unfamiliar icons with text labels at first use.
70. Keep the Naya emblem reserved for Naya presence and at least 32px.

## Motion, responsive, accessibility — 71–80
71. Animate only state, causality, orientation, transition, or meaningful spatial relationship.
72. Use the signature easing and governed duration tiers.
73. Prefer transform/opacity for motion.
74. Stop loading/processing motion when the underlying state stops.
75. Preserve full meaning under prefers-reduced-motion.
76. Test 320/375/390/430/768/820px.
77. Preserve hierarchy, current location, task flow, identity, and primary action on mobile.
78. Make every required function keyboard operable where platform norms support it.
79. Use semantic elements/landmarks and accessible names.
80. Test focus order, touch targets, error recovery, screen-reader meaning, and no color-only communication.

## Craft, freeze, verification, learning — 81–100
81. Restore current canonical project/design intelligence before designing.
82. Archaeologize existing work before replacing it.
83. Classify existing elements KEEP / IMPROVE / REPLACE / REMOVE with reasons.
84. Preserve the strongest distinctive baseline until superiority is proven.
85. Extract tokens before hand-tuning components.
86. Use canonical components before creating new ones.
87. Freeze spec + annotated visual + machine contract together.
88. Re-render the visual when the spec materially changes.
89. Re-check the spec/machine contract when the visual materially changes.
90. Compile execution-consequential laws into measurable predicates.
91. Render in a real browser before approval.
92. Capture applicable state and responsive evidence.
93. Measure performance rather than assume it.
94. Self-score D1–D8 with evidence, but never self-close the final gate.
95. Require every material D1–D8 dimension to reach at least 9.5 for acceptance.
96. Require D1=10, V1–V9≥9.5, and V10=10 for Signature/Masterpiece graduation.
97. Send exact branch/SHA to an independent reviewer who may FAIL/UNKNOWN/BLOCK.
98. Protect independently accepted artifacts as regression baselines.
99. Promote a lesson only after evidence, independent verification, and a durable mechanism update.
100. End each cycle with the next room inheriting the proven grammar and lessons without shrinking the declared complete-app scope.

# 100 DON'Ts

## Meaning and language — 1–10
1. Don't start from a card, modal, dashboard, or button before defining the human job.
2. Don't explain in prose what a clear control can communicate.
3. Don't make a section label describe implementation instead of human purpose.
4. Don't use jargon when a plain human verb exists.
5. Don't use "Submit", "OK", or "Click Here" when the outcome can be named.
6. Don't let help text compensate for a confusing interface.
7. Don't duplicate the same explanation in multiple regions.
8. Don't give one viewport multiple competing heroes.
9. Don't expose all technical depth by default.
10. Don't confuse more content with more intelligence.

## Typography/readability — 11–20
11. Don't render normal body below 16px.
12. Don't render controls/navigation below 15px.
13. Don't render support text below 14px.
14. Don't render critical truth/action content as microtype.
15. Don't render eyebrows/kickers below 12px.
16. Don't use thin low-contrast body text.
17. Don't put glow, blur, or gradient fill on primary reading text.
18. Don't use all-caps paragraphs.
19. Don't center long paragraphs by habit.
20. Don't shrink text to rescue a cramped layout.

## Color — 21–30
21. Don't use color without a semantic reason.
22. Don't let a room become a rainbow.
23. Don't use hue as the only hierarchy mechanism.
24. Don't use yellow/gold as Naya brand accent, default room identity, generic highlight, or body/headline color.
25. Don't use green/emerald as a generic "media/action" hue.
26. Don't use red for ordinary emphasis.
27. Don't use theme color to impersonate universal status.
28. Don't flood reading surfaces with saturated spectral color.
29. Don't let an accent outshine the actual primary action or truth.
30. Don't hard-code arbitrary hex values throughout component code.

## Controls — 31–40
31. Don't ship a button that does nothing.
32. Don't make a dead control look live.
33. Don't make every action primary.
34. Don't hide essential controls behind hover.
35. Don't use hover that shifts layout.
36. Don't remove focus without an equal-or-better replacement.
37. Don't replace loading context with an anonymous spinner.
38. Don't leave a failed operation looking successful.
39. Don't use opacity so low that disabled text becomes unreadable.
40. Don't claim a consequential operation succeeded before observation/evidence supports it.

## Boards and composition — 41–50
41. Don't use flat generic SaaS cards as the default visual language.
42. Don't force every room into the same grid composition.
43. Don't create a KPI wall because dashboards usually have one.
44. Don't use borders around every nested thing.
45. Don't let theme flood body copy.
46. Don't present ten nested intelligence perspectives as ten equally loud cards.
47. Don't call Smart Board furniture/extensions canonical intelligence layers.
48. Don't resurrect the contradictory "15 canonical layers" language.
49. Don't put architecture explanations in the live room when the user needs an action/answer.
50. Don't fill empty space just because it exists.

## Truth/state — 51–60
51. Don't show fake loading.
52. Don't show fake connected state.
53. Don't show fake verified state.
54. Don't show fake activity or fake counts.
55. Don't present sample data as current truth.
56. Don't convert UNKNOWN into EMPTY.
57. Don't convert NOT_VERIFIED into VERIFIED.
58. Don't hide staleness when it changes meaning.
59. Don't show an error with no recovery path when the system knows one.
60. Don't let local/client state become a shadow canonical truth.

## Icons/signature — 61–70
61. Don't use emoji as primary production navigation iconography.
62. Don't mix unrelated icon packs.
63. Don't stretch or squash glyphs.
64. Don't invent CSS icon sizes outside 16/24/32/48/64/96 to fix weak artwork.
65. Don't tint the glyph core until it loses contrast.
66. Don't make every utility icon a giant gemstone.
67. Don't use the Naya emblem as a generic sparkle.
68. Don't animate an icon merely to look intelligent.
69. Don't ship an ambiguous icon-only control without accessible name/learning support.
70. Don't accept a generic icon replacement that weakens a distinctive proven baseline.

## Motion/responsive/accessibility/performance — 71–80
71. Don't use perpetual decorative pulse.
72. Don't animate when nothing real is happening.
73. Don't let motion delay action or reading.
74. Don't create a mobile black gutter.
75. Don't permit unintended horizontal overflow.
76. Don't turn mobile into a compressed desktop or generic stacked-card clone.
77. Don't create duplicate navigation at smaller widths.
78. Don't require color alone to understand state.
79. Don't make pointer use mandatory for required actions.
80. Don't trade performance/accessibility for visual spectacle.

## Architecture, QA, locking, learning — 81–100
81. Don't create another design protocol, constitution, scorecard family, app shell, or room authority when the canonical owner exists.
82. Don't let one room invent new shared physics.
83. Don't duplicate canonical objects per room.
84. Don't replace a stronger baseline solely for cleaner code.
85. Don't call "route renders" complete.
86. Don't call "implemented" verified.
87. Don't use screenshot-only proof for interactive functionality.
88. Don't allow the builder to certify its own final quality gate.
89. Don't average away a hard-gate failure.
90. Don't use a high overall average to hide one material D1–D8 dimension below 9.5.
91. Don't use the historical visual blueprint score as product acceptance.
92. Don't freeze a room without spec + annotated visual + machine predicates.
93. Don't build around unresolved critical product/taste unknowns.
94. Don't wait for all 11 rooms before learning from the first frozen implementation.
95. Don't let the first successful room become the stopping rule for the declared app.
96. Don't regress an independently accepted room/component without explicit evidence-based supersession.
97. Don't promote a design lesson because it was written down.
98. Don't treat a Smart Note/comment as proof of retained learning.
99. Don't inherit authority from a learned pattern.
100. Don't claim LOCKED, RATIFIED, VERIFIED, CANONICAL, or PRODUCTION-PROVEN merely because the protocol is implemented.

## MECHANICAL USE

Run this checklist:
1. before a room freeze;
2. after implementation;
3. during independent review;
4. against every regression candidate.

For any failed item, record:
- item number;
- exact artifact/state;
- failed protocol predicate/hard gate;
- repair;
- evidence after repair.

**Acceptance remains owned by the Masterclass D1–D8 model + Protocol hard gates. This checklist is a critique instrument, not a second score.**
