# Smart Connect — AI Builder Spec

**Read first:** parent Hub contracts + FUNCTIONAL-SPEC + DESIGN-CONTRACT.

## Intent
Render Smart Doors from canonical registry/runtime truth. Never hardcode a roadmap example as live. Keep connection, authentication, authorization and health as separate states.

## Build order
1. Preserve shared Hub shell and Naya context.
2. Implement ORIENTATION → CURRENT STATE → INTELLIGENCE → ACTION → PROOF.
3. Build signature instrument before secondary controls.
4. Bind controls to governed runtime or honest unavailable states.
5. Preserve canonical object identity across handoffs.
6. Implement full state matrix.
7. Prove keyboard, responsive, reduced-motion, performance and continuity.

## Required components / views
- NayaPowerCore
- DoorPortal
- DoorStatusStack
- DoorCapabilitySheet
- AuthorityState
- ConnectionHealth
- RoadmapHorizon
- AccessibleDoorList
- ReceiptLink

## Primary causal actions
- CONNECT_AUTHENTICATE
- CONFIGURE
- VIEW_CAPABILITIES
- VIEW_REQUIRED_AUTHORITY
- TEST_IF_SUPPORTED
- VERIFY_CONNECTION
- DISCONNECT_REVOKE_IF_ALLOWED
- VIEW_RECEIPTS
- ASK_NAYA_WHICH_DOOR

## Data / runtime
Canonical Smart Door contract/registry + governed runtime health/auth state. Roadmap inputs are non-live metadata.

## Anti-patterns
- dead connect buttons
- roadmap door presented as live
- connected == authorized
- generic integrations marketplace
- fake success animation

## Acceptance proof
- door inventory matches canonical registry
- contract-only/roadmap never appear live
- connected/authenticated/authorized/healthy are distinct
- connect actions are real or honestly unavailable
- receipts/health are inspectable
- accessible list matches portal view
