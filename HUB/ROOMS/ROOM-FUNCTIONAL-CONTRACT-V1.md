# 🔱 NayaNET Hub — Room Functional Contract V1

**Purpose:** define how every primary Hub room functions as a complete intelligent environment.

## 0. Hub projection boundary

**The Hub is an output/projection experience over canonical intelligence.** It does not own Smart Note creation, canonical report generation, or manual activity publishing. Those are upstream Naya/runtime processes. Hub rooms receive, organize, explain, navigate and act on projected intelligence without becoming a second source of truth.

Canonical projected input classes: **Smart Notes / Intelligent Blocks · Activity · Intelligence Reports**.

See `HUB/INTELLIGENCE-PROJECTION-CONTRACT-V1.md`.

## 1. Room = experience + instrument + causal function

A room is complete only when all three are true:

**EXPERIENCE** — visually distinctive, coherent, beautiful and immediately understandable.  
**INSTRUMENT** — the human can inspect, navigate, filter, focus and act.  
**CAUSAL FUNCTION** — controls reach real governed capability or show an honest unavailable state.

A room is not complete because its shell renders.

## 2. The five-layer room law

Do not force every room into the same layout. Reuse components, not compositions.

Every room MUST express the Human Director's five semantic layers:

### 1. ORIENTATION — Where am I?
Room identity, current context, Space, essential truth state and one-line human promise.

### 2. CURRENT STATE — What is happening here right now?
Real numbers, states, intelligence, relationships or events appropriate to this room. No decorative metrics.

### 3. INTELLIGENCE — What does Naya understand?
Interpretation, synthesis, relevance, relationships, gaps and uncertainty — not merely raw records.

### 4. ACTION — What can I actually do?
A small number of real primary actions, context-aware secondary actions and honest disabled/blocked states.

### 5. PROOF — Why should I trust it?
Source, timestamp, provenance, status, evidence, consent/authority and receipts where relevant.

### Visual translation

A room MAY express these layers through a common visual grammar:

**HERO → INTELLIGENCE WALL → ACTION DECK → EVIDENCE LAYER → NAYA LAYER**

but the composition must remain room-specific.

### Signature instrument

Each room also has one unique primary instrument — live stream, highlight reel, report/time machine, semantic vault, portal bay, receipt chain, relationship constellation, mission table, signal console, context world or control deck.

The signature instrument is the reason the room exists.

## 3. Universal control rules

- Primary action: visually dominant, normally 1 per context.
- Secondary actions: 2–5 context actions.
- Overflow: low-frequency operations.
- Search/filter controls appear only where they materially reduce burden.
- No dead button.
- No fake live state.
- Dangerous/consequential actions surface authority/confirmation as required.
- Every action has a defined destination/result state.

## 4. Cross-room object identity

The same intelligence object keeps one canonical ID when projected across rooms.

Example:
`IB-123` may appear as:
- a Feed item;
- a Today highlight;
- evidence inside a Report;
- a Library result;
- an item inside a Smart List.

Those are views of one object, not five copies.

## 5. Global object actions

Where applicable, intelligence objects may expose:

- **Open**
- **Ask Naya**
- **Save / Favorite**
- **Add to List**
- **Open Source / Evidence**
- **Open Relationships**
- **Share / Connect** (governed)
- **Open in originating room**

Low-value social reactions should not crowd every surface. Actions are context-sensitive.

## 6. Shared room state model

Minimum runtime states:

`LOADING · EMPTY · READY · BLOCKED · UNAUTHORIZED · NOT_VERIFIED · VERIFIED · ERROR · OFFLINE · UNKNOWN · DISABLED`

A state has:
- machine state;
- human wording;
- visual treatment;
- available actions;
- evidence.

## 7. Spatial/context law

Current **Space**, identity and privacy scope should be visible where they materially affect results.

Switching Spaces changes context, not the underlying identity.

## 8. Naya presence law

Naya is available everywhere, but should not dominate every screen.

Contextual Naya behaviors:
- summarize;
- explain;
- compare;
- surface missing information;
- recommend the next useful action;
- tell the human when evidence is insufficient.

Naya must distinguish suggestion from fact and capability from authority.

## 9. Functional quality gate per room

A room cannot pass until:

1. purpose is obvious;
2. signature composition is distinctive;
3. primary user jobs are covered;
4. every primary control has a real causal path;
5. honest states exist;
6. canonical data owner is identified;
7. cross-room handoffs preserve object identity;
8. accessibility passes;
9. mobile preserves the room's identity;
10. error/offline behavior is designed;
11. provenance/authority is visible where required;
12. performance is measured;
13. independent reviewer can execute its acceptance journey.

## 10. Primary-room boundary

Primary rail remains the canonical eleven-room architecture.

Smart Notes is an **upstream Naya intelligence-production process whose results project into the Hub**, not a Hub capture room/control. System health is an advanced control/diagnostic surface. Promote either concept to primary-room status only through an explicit product decision backed by evidence.
