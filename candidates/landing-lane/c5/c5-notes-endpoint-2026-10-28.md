## 0. Problem, in one paragraph

Resolve's independent re-score (2026-10-28, all 43 preview blocks) found
standing notes device-local and note feeds EMPTY on the face. The face has
no record-backed place to read or write notes. C5 is that place: one
endpoint class the face calls for notes, backed by the shared record,
never device-only. This spec covers notes + feed. The Conversation
endpoint class (merged item 2, per-block discussion control) is a
SEPARATE beat; it consumes C5, it is not C5. Per-area note feeds are
NOT in v1 — areas do not exist in schema yet (no area_key column);
they ride the area-schema change (merged item 10), never invented here.

## 2. Note object (canonical, for all NEW appends)

```json
{
  "at": "2026-10-28T17:50:00Z",
  "from": "naya-power",
  "note": "text of the note",
  "client_id": "uuid-v4, client-generated"
}
```

- `at`: server-set at append time (UTC Z). A client-sent `at` is
  ignored, never trusted.
- `from`: seat alias, required, non-empty. The writer's alias, never
  another seat's.
- `note`: text, required, non-empty. The whole note, not a summary.
- `client_id`: UUID v4, required, generated by the CALLER once per
  note and kept until the append response is confirmed. It is the
  idempotency key: a retry MUST reuse the same client_id, never mint
  a new one per attempt. A retry with a new client_id is a NEW note
  by construction, and the face must never do that.

## 3. Operations

### 3.1 List — feed read

```
GET /notes              -> project feed (hub-row notes array)
GET /notes?item=<key>   -> that item's notes.entries
```

Response (200):

```json
{"notes": [ {note}, ... ], "count": 43, "item": null}
```

- `notes` in STORED order, oldest first. The face renders in the
  order returned, never re-sorts.
- `item`: null for the project feed, the item_key otherwise.
- No pagination in v1 (feeds are tens of entries, not thousands;
  pagination is a later extension, not invented now).
- Legacy entries missing `note` are returned as-is; the face renders
  them provenance-only (`from` + `at`), never with invented text.

### 3.2 Append — guarded, append-once

```
POST /notes
{"item": "<key>" | null, "from": "naya-power",
 "note": "text", "client_id": "uuid-v4"}
```

Response (200):

```json
{"note": {note}, "position": 44, "duplicate": false}
```

- `position`: 1-based index of the note in the feed after append.
- `duplicate: true` when the client_id was already present: the
  existing note is returned, NOTHING is appended. An idempotent retry
  is a success, not an error — never a 409.
- `item: null` (or omitted) appends to the project feed (hub row);
  an item_key appends to that row's `notes.entries`.

### 3.3 Errors (exact)

- Record unavailable (any read or verify step fails):
  `503 {"error": "notes_unavailable"}` — the body carries NO `notes`
  key, by construction, same as B1's 503 carrying no items/counts.
  A caller that renders notes from a 503 body is misusing it.
  NEVER a snapshot fallback, NEVER device-local notes, NEVER an
  empty feed presented as success. An empty feed is only valid when
  the read SUCCEEDED and the store is genuinely empty.
- Validation (missing/empty `from`, `note`, or `client_id`):
  `400 {"error": "invalid_note", "detail": "<field>"}`.
- Unknown item_key (read succeeded, key not found):
  `404 {"error": "unknown_item"}`. Distinct from 503: 404 means the
  record answered and the key is not there; 503 means the record
  did not answer.

## 4. Append algorithm (the guarded-write rule, normative)

The proven rule, applied to both homes: read state before any retry,
verify after write, every retry is a new decision.

```
append(store, item, from, note, client_id):
  1. validate(from, note, client_id)            -> 400 on failure
  2. entries = store.read(item)                  -> 503 on failure
  3. if any(e.client_id == client_id for e in entries):
       return existing entry, duplicate=true     (NO write)
  4. store.append_guarded(item, new_note, expected_len=len(entries))
       -> 503 on failure (length guard: the store refuses the write
          if the length moved since step 2 — a race, not a success)
  5. verify = store.read(item)                   -> 503 on failure
  6. if len(verify) == len(entries)+1 and tail.client_id == client_id:
       return new note, duplicate=false
  7. else: re-read once more (lost-response rule: the write may
     have landed while its response was lost). If the note is now
     present, return it (duplicate=false, it landed). If still
     absent, raise unavailable -> 503. NEVER blindly re-append:
     a re-read that proves the write landed means DONE, never re-sent.
```

On a length-guard refusal (step 4): the caller re-runs the WHOLE
algorithm from step 2 as a new decision (fresh read, fresh
client_id check, fresh guard). It never forces the write past the
guard. This is what makes concurrent appends safe: two appends
interleaved produce both entries, in order, each exactly once.
Bounded: more than 5 guard refusals in one call ends in 503, so
sustained contention cannot spin forever (prototype constant
MAX_GUARD_RETRIES = 5).

## 5. SQL shape for the landing implementer (not executed here)

Resolve by item_key; write by uuid-literal primary key. NEVER an
`id::text` scan (it evaluates the array-length function over other
rows and fails 22023 on non-array notes values — the known trap).

Project feed (hub row, resolved by item_key `14q-pi-hub-10star`):

```sql
-- read
SELECT jsonb_array_length(notes) FROM work_items
 WHERE id = '<hub-uuid>'::uuid;
-- append (length guard N = read length)
UPDATE work_items
   SET notes = notes || jsonb_build_object(
         'at', '<now Z>', 'from', '<alias>', 'note', '<text>',
         'client_id', '<uuid>')
 WHERE id = '<hub-uuid>'::uuid AND jsonb_array_length(notes) = N;
-- verify: count = N+1 AND tail client_id matches
```

Per-item entries (row resolved by item_key, id `<row-uuid>`):

```sql
-- read
SELECT notes->'entries' FROM work_items WHERE id = '<row-uuid>'::uuid;
-- append, entries PRESENT (length guard N):
UPDATE work_items
   SET notes = jsonb_set(notes, '{entries}',
                 COALESCE(notes->'entries', '[]'::jsonb)
                 || jsonb_build_object('at','<now Z>','from','<alias>',
                                       'note','<text>',
                                       'client_id','<uuid>'))
 WHERE id = '<row-uuid>'::uuid
   AND jsonb_array_length(notes->'entries') = N;
-- append, entries ABSENT (guard is IS NULL, same SET clause):
 ... WHERE id = '<row-uuid>'::uuid AND notes->'entries' IS NULL;
-- verify: entries length = N+1 (or 1) AND tail client_id matches
```

The client_id pre-check (step 3) is a scan of the READ entries in
the service layer, before any write — the same shape as the proven
mail guard (WHERE NOT EXISTS on the writer's own rows). The length
guard is the race guard. Both are required; neither alone is enough.

## 6. What Nitro's face needs to call it

1. `GET /notes` for the project feed; `GET /notes?item=<item_key>`
   for a block's notes. Render in returned order.
2. `POST /notes` with `{item, from, note, client_id}`; generate
   `client_id` once per note (crypto.randomUUID) and KEEP it until
   the 200 is confirmed — retry with the SAME id, never a new one.
3. On 503: show an honest "notes unavailable" state. Never an empty
   feed, never device-local notes, never a cached snapshot.
4. On 200 with `duplicate: true`: render the returned note once;
   do not render a second copy.
5. Legacy entries without `note` text: render `from` + `at` only.
6. The face NEVER writes notes anywhere else (no localStorage, no
   device-only array). If the endpoint is unreachable, the note is
   not "saved" — the user is told so, plainly.
