# 0. THE BUILD LAW

Naya Power Player is not a dashboard, landing-page shell, visual mockup, or collection of disconnected embeds.

It is a **premium intelligent application experience** and the customer-facing front door to the broader **NayaNET intelligent network**.

The application must be built from a complete blueprint rather than inventing the next block after the previous block is finished.

**MASTER BLUEPRINT → BLOCK SPEC → FABRICATION → QA → OSCAR → DEPLOY → HUMAN TEST → GROOVE → VERIFY → LEARN → UPDATE BLUEPRINT → NEXT BLOCK**

The blueprint defines the destination. Individual blocks are bounded construction units.

## Non-negotiable quality standard

Build as if engineering a world-class product: precise architecture, deliberate interaction design, exceptional visual craft, truthful capability claims, responsive behavior, maintainability, accessibility, performance, and evidence-based verification.

**No guessing where canonical documentation can answer the question.**

## NayaNET

**NayaNET** is the new intelligent network: an interconnected system of intelligent systems designed to connect intelligence, extract intelligence, compound intelligence, and make that power accessible through a simple human-first experience.

## Collective Intelligence

Selected, consented, generalized intelligence can become new Collective Intelligence Events. Collective intelligence is not repository synchronization and is not a copy of a person's private memory.

# 3. FREE ACCOUNT / NAYANET IDENTITY MODEL

## 3.1 Default entry

Every person who lands on the NayaNET/Naya Power experience is invited to create a free NayaNET account.

The initial account creation should be deliberately frictionless.

### Initial required input

**Name only.**

Do not require email, Google, Facebook, Apple, or another identity provider at first account creation unless a later security or product requirement makes it necessary.

The purpose is immediate participation, not form completion.

## 3.2 Immediate welcome

After entering their name, the person receives:

- a NayaNET identity;
- a Smart Name / username;
- a personal NayaNET link/portal;
- a free Intelligent Hub;
- a personal toolbox/command station;
- an invitation to the Five-Day Challenge;
- an optional invitation to begin the Naya Power free trial.

The UX should communicate the feeling:

> **Welcome to NayaNET. You are in. This is your place in the new network.**

## 3.3 Smart Name / Smart Link

The user's NayaNET username becomes a durable identity primitive and eventually can serve as:

- profile address;
- personal NayaNET portal;
- network badge/share link;
- referral/attribution link where appropriate;
- Smart Mail identity;
- connection address;
- future personal AI/Naya address.

The exact public domain/path is implementation-dependent and must be established as a canonical product contract before production naming is frozen.

## 3.4 Secure the account later

After the person is inside, the Hub should gently offer:

**Secure your account**

Possible methods may include email or supported identity providers. These are account-hardening options, not the first barrier to entry.

Email becomes useful for optional services such as:

- notifications;
- intelligent reports;
- Maxis/assessment reports;
- recovery;
- important account notices.

Do not require email simply to receive the basic NayaNET identity unless the chosen production authentication architecture requires it.

# 19. VISUAL DESIGN SYSTEM

## Foundation

**Black / near-black** provides the deep-space canvas.

**White** is the primary text color.

**Purple** is the core Naya Power identity.

**Magenta → Purple → Blue → Green → Yellow** forms the established color rhythm when semantic progression is useful.

**Gold** is a premium accent and should be used deliberately rather than everywhere.

## Contrast law

Allowed high-contrast combinations include:

- white on black;
- white on dark purple;
- dark/black on white;
- accessible bright accent on dark surfaces.

Avoid purple-on-purple combinations that reduce legibility.

## Typography

Use a modern, premium, highly legible type system with strong hierarchy:

**HEADLINE → SUPPORTING STATEMENT → DETAIL**

Typography should communicate intelligence and warmth rather than enterprise bureaucracy.

## Shape language

The core visual language is:

- circles;
- rings;
- orbits;
- soft glass/depth surfaces;
- luminous edges;
- restrained cards;
- generous negative space;
- premium media frames.

Do not turn every component into a rounded rectangle.

# 21. RESPONSIVE ARCHITECTURE

Design mobile-first but scale elegantly to desktop.

Required QA widths:

**320, 360, 375, 390, 414, 480, 600, 768, 900, 1024, 1280 px**

The iframe content must be responsive internally. Groove does not automatically make an iframe's internal layout responsive.

Avoid fixed-height designs that clip important content.

---

# 22. MEDIA / VOICE ARCHITECTURE

Audio and video should be initiated by clear user interaction where browser autoplay policies require it.

Voice features must degrade gracefully:

**voice available → voice experience**

**voice unavailable → excellent text experience**

The UI should never break because microphone/speech APIs are unavailable.

If microphone access is needed inside an iframe, the production embed must provide the appropriate iframe permissions.

---

# 23. CLOUDFLARE STATIC-FIRST ARCHITECTURE

The first Player generation must be deployable as static assets without Wrangler through the proven Cloudflare direct-upload path.

## Static ZIP may contain

- HTML;
- CSS;
- JavaScript;
- JSON data/config;
- images;
- SVG;
- fonts where licensing permits;
- audio/video assets within platform limits;
- other static resources required by the block.

## Direct-upload ZIP must not depend on

- Wrangler runtime;
- Node build execution at upload time;
- server-side secrets;
- uncompiled source requiring a build step;
- Worker-only APIs for basic rendering.

A block that requires server-side logic becomes a separate architecture decision and must not silently contaminate the static deployment contract.

## Principle

> **Make the Cloudflare artifact boring. Make the experience extraordinary.**

---

# 24. GROOVE EMBED ARCHITECTURE

Each finished Cloudflare block produces a stable URL.

Groove embeds that URL as an iframe.

The source code does not need to be copied into Groove.

## Construction sequence

```text
BLOCK SPEC
   ↓
BUILD
   ↓
LOCAL QA
   ↓
STATIC ZIP
   ↓
CLOUDFLARE DEPLOY
   ↓
LIVE URL
   ↓
HUMAN TEST
   ↓
GROOVE EMBED
   ↓
RESPONSIVE TEST
   ↓
FREEZE
```

Do not generate the final Groove embed code until the block is ready.

## Iframe behavior

Dynamic parent-height communication may use a minimal, documented `postMessage` protocol if testing demonstrates that static sizing is insufficient.

Do not introduce cross-frame communication merely because it is possible.

The default should be independent, self-contained blocks.

# 41. OSCAR REVIEW QUESTIONS

Before declaring a block complete, ask:

- Would a world-class designer be proud of this?
- Does this look like Naya Power rather than generic SaaS?
- Is the first action obvious?
- Is the interface simpler than the underlying technology?
- Does the Living Sun feel alive?
- Does every animation have a purpose?
- Is there unnecessary complexity?
- Does the mobile version feel intentional?
- Does the user receive real value immediately?
- Is anything pretending to be more connected than it really is?
- Does the block fit the master journey?
- Did this implementation accidentally constrain a future block?
- What would make this a 10/10?

If the answer to the final question is obvious, repair it before deployment.
