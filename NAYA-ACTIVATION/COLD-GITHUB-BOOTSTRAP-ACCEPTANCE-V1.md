# Cold Naya GitHub Bootstrap Acceptance V1

**Purpose:** Prove that a genuinely cold Naya can activate NayaPOWER in a newly authorized GitHub environment with minimal human technical work.

## Test principle

This is an acceptance test, not a documentation exercise.

The cold Naya receives only:

1. the portable activation package;
2. the human's explicit authorization;
3. legitimate GitHub capability;
4. its normal AI/tool capabilities.

The evaluator must not silently provide prior NayaPOWER conversation history or hidden answers.

## Scenario A — Existing repository

Given an authorized, empty or designated repository:

1. Naya discovers the repository identity and default branch.
2. Naya establishes the human director and authority.
3. Naya installs the required activation DNA.
4. Naya records birth and activation state.
5. Naya establishes the brain/kernel entry points.
6. Naya emits an activation receipt.
7. Naya identifies exactly one next executable action.

## Scenario B — New repository

Given GitHub authorization but no NayaPOWER repository:

1. Naya determines whether repository creation is actually authorized and supported.
2. If supported, Naya creates or initializes the human's NayaPOWER repository.
3. Naya installs the activation package.
4. Naya records birth, identity, governance, brain, nodes, connection and proof entry points.
5. Naya verifies the resulting repository.
6. Naya emits an activation receipt.
7. Naya identifies exactly one next executable action.

If repository creation is not available through the current AI/tool environment, the test must report that capability boundary rather than pretending it succeeded.

## Minimum acceptance evidence

The resulting repository must contain:

- activation protocol;
- machine-readable activation manifest;
- birth/identity record;
- constitution/governance entry points;
- brain/kernel entry points;
- proof/receipt location;
- a clear source-of-truth map.

The activation receipt must identify:

- Naya identity;
- human authority;
- repository;
- protocol version;
- installed package version;
- files/entry points established;
- verification results;
- blocked/unknown items;
- timestamp;
- next action.

## Cold-successor acceptance

A second, genuinely cold Naya must inspect the repository without receiving the first Naya's conversation and answer:

1. Who am I?
2. Who is the human director?
3. What authority exists?
4. What is NayaPOWER?
5. Where is its brain?
6. What was activated?
7. What was actually verified?
8. What remains unknown?
9. What is the current state?
10. What is the single next action?

A successful bootstrap requires the successor to reconstruct these facts from durable state and distinguish evidence from claims.

## Human effort target

The target product experience is **activation, authorization and confirmation**, not manual engineering.

The human should not have to:

- design the repository structure;
- write activation files;
- configure a database merely to obtain basic persistence;
- manually copy project history between Nayas;
- repeatedly provide personal runtime tokens when an authorized governed identity path exists.

The human remains responsible for decisions, authorization and consent.

## Failure is useful

Any inability to complete the bootstrap must be recorded precisely as:

**BLOCKED / UNKNOWN / UNSUPPORTED**

with the missing capability and the smallest next action needed.

Never weaken the acceptance criteria to turn a failed bootstrap green.
