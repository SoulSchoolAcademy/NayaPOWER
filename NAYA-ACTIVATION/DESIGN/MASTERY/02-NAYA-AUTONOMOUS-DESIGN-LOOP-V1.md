# 🔱 NAYA AUTONOMOUS DESIGN LOOP V1
## How Naya takes a smart app from intent to qualified release candidate

**Status:** PROPOSED CANONICAL OPERATING PROTOCOL  
**Parent:** Naya Design Mastery Constitution V1  
**Important:** “Autonomous” means autonomous reasoning/execution inside granted authority. It does not bypass human production authorization, privacy, safety or governance.

---

# 1. ONE LOOP, FOUR MODES

```
RESTORE
→ SPECIFY
→ DESIGN
→ BUILD
→ RENDER
→ USE
→ SCORE
→ CHALLENGE
→ REPAIR
→ REGRESS
→ COMPLETE
→ LEARN
→ REUSE
```

The loop runs at four scales:

1. **Component** — button, board, glyph, field, state object.
2. **Page/Room** — one complete human experience.
3. **Application** — routes, cross-page flows, persistence and return session.
4. **Design intelligence** — patterns, examples, anti-examples, reusable lessons.

Never confuse success at a smaller scale with closure at a larger scale.

---

# 2. STAGE 0 — RESTORE CURRENT TRUTH

Before design work:

- read current `main`;
- read project intelligence;
- read design contract;
- read current completion matrix;
- inspect current implementation;
- inspect current screenshots/browser artifacts;
- inspect open overlapping design PRs;
- identify current canonical sources;
- identify current Human Director decisions;
- identify current unknowns.

Output:

```
CURRENT_SOURCE_SHA
CANONICAL_DESIGN_SOURCES
APP_SCOPE
FROZEN_BASELINES
OPEN_DECISIONS
KNOWN_RUNTIME_LIMITS
CURRENT_SCORE / EVIDENCE
OVERLAPPING_WORK
```

**Failure prevented:** session amnesia, duplicate systems, stale design decisions.

---

# 3. STAGE 1 — SPECIFY THE HUMAN EXPERIENCE

For each page/room, define before visual build:

### A. Human question
What question is this surface answering?

### B. Human outcome
What can the person understand/do after using it?

### C. First-frame truth
What must be obvious in the first 3 seconds?

### D. Primary instrument
What unique interaction/object makes this page itself?

### E. Primary action
What is the highest-value next move?

### F. Intelligence
What does Naya know or interpret here?

### G. Proof
What evidence/provenance must be reachable?

### H. States
Which normal/failure/authority/offline states apply?

### I. Cross-page handoffs
What canonical IDs/context move in/out?

### J. Completion
How will we know this page is finished?

This is the **Page Intelligence Contract**.

No code until this exists at sufficient fidelity.

---

# 4. STAGE 2 — DESIGN THE EXPERIENCE ARC

Define the emotional/cognitive arc.

Typical Naya arc:

**CURIOSITY → RECOGNITION → ORIENTATION → TRUST → COMMAND → FLOW → MASTERY → CONTINUITY**

Not every page uses every stage.

Map:
- first impression;
- first useful comprehension;
- first action;
- feedback;
- deeper exploration;
- proof;
- return state.

Output: **EXPERIENCE ARC**.

---

# 5. STAGE 3 — COMPOSITION OPTIONS BEFORE COMMITMENT

When composition is underdetermined, create **3 genuinely different structural options**.

Each option describes:
- focal point;
- layout regions;
- primary instrument;
- action placement;
- density;
- mobile transformation;
- strongest advantage;
- biggest risk.

Do not create three cosmetic variants of the same grid.

Score options against:
- purpose;
- hierarchy;
- clarity;
- signature;
- mobile;
- complexity;
- implementation risk.

Select or synthesize.

**Failure prevented:** coding the first plausible composition and spending 30 iterations polishing the wrong structure.

---

# 6. STAGE 4 — TASTE / SIGNATURE LOCK

Before full implementation, bind project design language:

- visual foundation;
- palette semantics;
- typography roles;
- spacing scale;
- radius/geometry family;
- material/elevation rules;
- icon/glyph family;
- button physics;
- board/surface physics;
- motion timings;
- Naya presence;
- state grammar;
- copy voice.

Classify each as:

`INVARIANT · PROJECT-SPECIFIC · PAGE-SPECIFIC · OPTIONAL`

This avoids both drift and template sameness.

---

# 7. STAGE 5 — BUILD IN DEPENDENCY ORDER

Build order:

1. tokens;
2. primitives;
3. layout shell;
4. page signature instrument;
5. normal READY state;
6. loading/empty/error/blocked/unknown states;
7. primary causal actions;
8. secondary actions;
9. responsive transformations;
10. accessibility;
11. performance;
12. cross-page integration.

For a multi-page app:
- first excellent page calibrates the system;
- then reuse proven primitives;
- keep the complete application scope machine-visible;
- never stop because the reference page works.

---

# 8. STAGE 6 — RENDERED OBSERVATION

Observe the result in real rendering.

Required where applicable:
- large desktop;
- laptop;
- tablet;
- phone;
- small phone;
- 125% zoom;
- 150% zoom;
- 200% zoom;
- reduced motion;
- keyboard-only path.

Capture:
- screenshots;
- console errors;
- horizontal overflow;
- layout jumps;
- stale overlays;
- loading/empty/error;
- hover/focus/press;
- responsive identity.

The builder must **look at the product**.

---

# 9. STAGE 7 — USE IT LIKE A HUMAN

Do not only inspect pixels.

Perform the actual human job.

Ask:
- Can I find the main action?
- Does it work?
- Do I understand what happened?
- Do I know what is true?
- Can I recover from failure?
- Does back/reload make sense?
- Can I return later?
- Does the same object remain the same object across pages?
- Am I reading too much explanation?
- Is the interface doing unnecessary work?

Record friction.

---

# 10. STAGE 8 — SELF-ANALYZE

The builder performs a structured critique before scoring.

Required critique lenses:

### PURPOSE
Does every visible region earn its place?

### HIERARCHY
Where does the eye land first, second, third?

### COMPOSITION
Is the page composed or tiled?

### TEXT
Is copy doing a component's job?

### MATERIAL
Are objects physically coherent?

### COLOR
Does every accent have meaning?

### ICONS
One family? Correct importance?

### MOTION
Real state or theater?

### CONTROLS
Real causal paths?

### STATE
All applicable states designed?

### MOBILE
Same identity, correct transformation?

### ACCESSIBILITY
Keyboard, focus, contrast, semantics, zoom?

### PERFORMANCE
Does it feel immediate?

### HONESTY
Any implied live/verified/complete state without evidence?

### DISTINCTION
Could this be generic SaaS?

### COMPLETION
Any missing page/function disguised by a strong first frame?

---

# 11. STAGE 9 — SCORE

Use the product's canonical scorecard.

For NayaNET Hub:
- D1 Visual Excellence
- D2 Functional Completeness
- D3 Intelligence
- D4 Honesty
- D5 Performance
- D6 Reliability & Continuity
- D7 Accessibility
- D8 Craft

Do not invent a competing overall score.

Design Mastery diagnostics in `03-NAYA-DESIGN-QUALIFICATION-V1.md` feed evidence into those dimensions.

Score with links to:
- screenshots;
- tests;
- measurements;
- runtime proof;
- known limitations.

A number without evidence is commentary, not measurement.

---

# 12. STAGE 10 — INDEPENDENT CHALLENGE

An independent reviewer must attempt to falsify the builder's assessment.

They should look specifically for:
- over-scoring;
- generic composition;
- text overload;
- weak mobile;
- tiny type;
- misleading state;
- dead controls;
- accessibility failures;
- performance regressions;
- inconsistent design grammar;
- missing product scope;
- hidden regression.

The independent reviewer may score lower.

That is useful.

---

# 13. STAGE 11 — REPAIR LOOP

Repairs are prioritized:

```
HARD GATE FAILURE
→ LOWEST MATERIAL SCORE
→ HIGHEST USER BURDEN
→ HIGHEST REGRESSION RISK
→ HIGHEST REUSE VALUE
```

For each repair:

```
FINDING
→ ROOT CAUSE
→ LAW VIOLATED
→ CHANGE
→ RENDER
→ RETEST
→ RESCORE
```

Do not change unrelated variables unless necessary.

---

# 14. STAGE 12 — NON-REGRESSION

Before accepting an improvement:
- compare against prior accepted baseline;
- preserve approved information architecture;
- preserve or improve readability;
- preserve or improve interaction;
- preserve accessibility;
- preserve performance;
- preserve causal behavior;
- preserve identity.

If code quality improves but human experience worsens, the change is not yet an improvement.

---

# 15. STAGE 13 — FULL PRODUCT COMPLETION

For application scope, require:
- all declared pages/routes;
- shared navigation;
- shared search/context;
- complete primary actions;
- honest unavailable paths;
- cross-page canonical identity;
- persistence;
- return session;
- error/offline/unauthorized flows;
- responsive;
- accessibility;
- performance;
- browser proof;
- independent review;
- applicable production parity.

Use the machine completion matrix.

Only two end states:

### TERMINAL
Declared scope genuinely closed with evidence.

### SUCCESSOR-READY
Not done, but exact first failing gate and all remaining scope are durable.

There is no “looks pretty enough, stop.”

---

# 16. STAGE 14 — DESIGN LEARNING

After a qualifying outcome:

Capture:
- lesson;
- before;
- after;
- why it improved;
- evidence;
- project/context;
- applicable components/pages;
- contradictions;
- known limits.

Truth progression remains governed.

A lesson begins as candidate intelligence.

Do not universalize one accepted page into a universal law without reuse evidence.

---

# 17. STAGE 15 — REUSE

A cold successor must retrieve:
- Constitution;
- Signature Language;
- current project contract;
- tokens;
- gold examples;
- anti-examples;
- open completion matrix;
- current score;
- current weakest gate.

Then continue.

The next app should begin ahead.

---

# 18. AUTOMATION BOUNDARIES

Safe candidates for automation:
- lint;
- screenshot capture;
- viewport matrix;
- DOM/accessibility checks;
- contrast;
- font-size checks;
- horizontal overflow;
- dead-link/control checks;
- state-fixture rendering;
- performance metrics;
- completion-matrix consistency;
- visual regression comparison;
- score evidence collection;
- PR evidence package assembly.

Require human/independent judgment for:
- aesthetic quality;
- emotional resonance;
- final composition;
- signature strength;
- meaningful originality;
- whether a visual change is genuinely better when evidence is ambiguous.

Automate measurement aggressively.

Do not pretend taste is fully reducible to a linter.
