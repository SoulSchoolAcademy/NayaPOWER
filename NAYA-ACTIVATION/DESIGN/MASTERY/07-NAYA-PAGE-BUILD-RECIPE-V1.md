# 2. THE 10-MINUTE DESIGN PASS

Before code, answer:

1. What is the one thing the eye should see first?
2. What is the one useful thing this page does better than every other page?
3. What is the page's signature instrument?
4. What can be removed?
5. What text could become structure/control/state?
6. Which information deserves depth?
7. Which color has semantic meaning?
8. What happens if there is no data?
9. What happens on a phone?
10. What evidence proves the page is truthful?

---

# 3. COMPOSITION OPTIONS

When the page is not already frozen, create three structural choices.

## OPTION A — HERO INSTRUMENT

Best when:
- one task dominates;
- one live object is central.

Shape:
```
ORIENTATION
↓
LARGE SIGNATURE INSTRUMENT
↓
SUPPORTING INTELLIGENCE
↓
PROOF / SECONDARY ACTIONS
```

## OPTION B — STORY FLOW

Best when:
- interpretation unfolds in sequence;
- reports, Today, onboarding.

Shape:
```
ORIENTATION
↓
WHAT CHANGED
↓
WHY IT MATTERS
↓
WHAT TO DO
↓
EVIDENCE
```

## OPTION C — WORKBENCH

Best when:
- human is actively manipulating a system;
- lists, connections, settings, building tools.

Shape:
```
CONTEXT / STATE
↓
PRIMARY WORK AREA + CONTROL REGION
↓
DETAIL / INSPECTOR ONLY WHEN NEEDED
```

Do not use these as rigid templates. They are composition families.

# 4. EXAMPLE — YOUR INTELLIGENCE TODAY

## Weak AI-default version

- title;
- 4 KPI cards;
- “recent activity” card list;
- purple gradient;
- Naya summary paragraph;
- three generic CTA buttons.

Why it fails:
- page is a dashboard, not a highlight reel;
- metrics become the hero rather than meaning;
- Naya is text added after the fact;
- no narrative;
- no evidence relationship;
- could belong to any app.

## Naya version

Human question:
**What actually mattered today?**

Primary instrument:
**Today Pulse + What Changed Narrative**

Composition:
1. quiet date/context;
2. one human sentence summarizing the day;
3. 3–5 selected highlights with reason/evidence;
4. Naya reflection grounded in those objects;
5. open loops / carry-forward;
6. quiet-day state that stays quiet.

Signature:
- magenta/human-significance energy;
- highlights feel like scenes, not cards;
- counts subordinate to meaning;
- evidence reachable;
- no manufactured activity.

# 5. EXAMPLE — SMART CONNECT

## Weak AI-default version

- integration marketplace grid;
- app logos;
- Connect buttons everywhere;
- green “available” badges;
- “Connect your tools” headline.

Why it fails:
- capability marketplace ≠ governed Smart Doors;
- connected can be mistaken for authorized;
- status may be fake;
- no reason to feel like NayaNET.

## Naya version

Human question:
**How can this intelligence connect, and what does that connection actually permit?**

Primary instrument:
**Door Portal + state stack**

Each Door shows:
- identity;
- capability;
- connection;
- authentication;
- authorization;
- health;
- evidence/contract;
- honest action.

Composition:
- portal-bay orientation;
- live/contract/roadmap distinctions;
- focused Door inspector after selection;
- Law visible in concise form:
  **CONNECTED ≠ AUTHORIZED**

Signature:
- semantic teal/emerald for connection/health;
- door is a dimensional object;
- state is more important than logo;
- no fake handshake.

# 6. EXAMPLE — SMART MAIL

## Weak AI-default version

- Gmail clone;
- fake inbox rows;
- unread count;
- AI Compose button;
- dummy messages to make it look alive.

Why it fails:
- fake data;
- generic product clone;
- AI theater;
- no intelligence value;
- no authority boundary.

## Naya version

Human question:
**What communication actually needs my attention, and why?**

Primary instrument:
**Signal List + Context Reader**

Possible honest states:
- RUNTIME UNAVAILABLE;
- NO MAIL;
- ACCESS BLOCKED;
- READY.

When live:
- IMPORTANT;
- RESPOND;
- FOLLOW UP;
- DRAFTS;
- SENT.

Selected message reveals:
- message;
- person/context;
- related intelligence;
- why it matters;
- suggested draft;
- send authority state.

Signature:
- message meaning before inbox chrome;
- real context;
- no fake mailbox;
- drafting ≠ authorized sending.

# 7. BAD / BETTER MICRO-EXAMPLES

### Copy

Bad:
“Click here to view the full evidence supporting this intelligence object.”

Better:
**View Evidence**

Bad:
“The system is currently unable to load your data due to the runtime not being connected.”

Better:
**Runtime unavailable**  
Connect the governed runtime to load your intelligence.

### State

Bad:
Green pulsing dot on every screen.

Better:
Green illumination only when health evidence reports ACTIVE/HEALTHY.

### Layout

Bad:
Four equal cards for four unequal ideas.

Better:
One dominant object, two supporting items, one quiet detail region.

### Controls

Bad:
Six bright purple buttons.

Better:
One primary action, refined secondary actions, low-energy utility actions.

### Mobile

Bad:
Desktop cards stacked top-to-bottom.

Better:
Reprioritize content; convert navigation; move secondary evidence behind disclosure; keep primary instrument first.

# 8. BUILD PROMPT FOR ANY NAYA / CODER

Use this internal directive:

> Restore current canonical project/design intelligence and the complete declared product scope. Do not invent a parallel design system. Define the surface's human question, first-frame truth, primary instrument, actions, states, canonical data owner, cross-surface handoffs, responsive transformation and proof before coding. When composition is not frozen, generate three structurally different options and select the strongest by purpose/hierarchy/signature. Build from shared tokens/primitives while giving the page its own composition. Every control must have a real causal path or an honest unavailable state. Render at desktop/mobile/zoom/reduced-motion, use the actual human flow, self-critique against the Naya Design Qualification lenses, score through the canonical product scorecard, obtain independent challenge, repair the weakest material dimension, preserve the accepted baseline, update the app completion matrix, and capture only evidence-backed reusable learning. Do not stop at a shell or first slice.

---

# 9. DEFINITION OF DONE — PAGE

A page is locally done only when:

- purpose is obvious;
- visual hierarchy is intentional;
- signature instrument exists;
- applicable states exist;
- primary actions are causal/honest;
- data/truth source is correct;
- responsive transformation works;
- keyboard/focus/zoom/reduced-motion work;
- performance is acceptable;
- rendered QA is complete;
- self-score has evidence;
- independent review passes;
- no material regression is known.

Local page completion does not close the whole app.

---

# 10. DEFINITION OF DONE — APPLICATION

An application is done only when the complete declared scope and cross-page journeys also pass.

This is the bridge between Design Mastery and SN-019 Complete the App Doctrine.
