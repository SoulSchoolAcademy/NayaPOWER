# 🔱 NayaNET — Primo Button Law V1

**Status:** PROPOSED CANONICAL — HUMAN DIRECTOR RATIFICATION REQUIRED  
**Scope:** Navigation buttons, primary actions, secondary actions, icon buttons, room actions and other tactile interactive controls.

## 1. Button purpose

A button is a promise.

Its visible affordance says:
**“You can do something here.”**

Therefore:

> **A beautiful dead button is a defect. A functional button that visually lies about what it can do is also a defect.**

## 2. Anatomy

A production Primo Button SHOULD contain a coherent combination of:

**material body  
→ precise edge  
→ internal highlight  
→ physical depth  
→ meaningful icon  
→ readable label  
→ theme energy  
→ state indicator**

Not every button needs every treatment at maximum intensity.

Visual Bliss controls intensity.

## 3. Base state

Default buttons MUST:
- look intentional;
- be visually distinct from background;
- be easy to locate;
- have sufficient text/icon contrast;
- communicate whether they are primary, secondary or contextual;
- avoid appearing disabled when enabled;
- avoid appearing active when merely idle.

## 4. Material

Primary controls use an obsidian/graphite material language.

Preferred qualities:
- subtle raised body;
- precise edge;
- restrained internal highlight;
- credible shadow;
- controlled thematic illumination.

Flat generic rectangles are below the NayaNET bar for primary tactile controls unless a specific context benefits from them.

## 5. Theme

A button MAY inherit a semantic room or action color.

Theme color MUST:
- correspond to meaning or room identity;
- remain secondary to readable content;
- not overwhelm the label;
- not become the sole state signal.

Purple remains the core NayaNET identity.

Yellow/gold are not default button colors for arbitrary importance.

## 6. Hover

Hover MAY communicate:
**lift + sharpen + brighten + slightly stronger shadow/energy**

Recommended motion is small and physical.

Hover MUST NOT:
- move the control enough to cause layout instability;
- obscure nearby controls;
- become a light show;
- imply a state change that did not happen.

## 7. Press

Press communicates:
**contact with the surface**

A pressed control SHOULD:
- compress slightly;
- reduce perceived elevation;
- reduce cast shadow;
- preserve label readability.

Press must feel physical, not cartoonish.

## 8. Active/selected

Selected state MUST remain visibly selected.

It SHOULD use:
- persistent edge energy;
- stable elevation;
- a semantic rail/indicator;
- restrained illumination.

Active does not mean “more glow for no reason.”

## 9. Focus

Keyboard focus MUST be unmistakable.

Focus must:
- meet accessibility requirements;
- remain visible over dark material;
- not depend only on subtle glow;
- not be removed because it looks less polished.

Elegant focus is part of premium design.

## 10. Disabled

Disabled controls MUST visibly lose interactive energy.

They MUST NOT:
- appear connected;
- appear active;
- appear ready to execute;
- animate as though processing.

The label should remain readable enough to understand why the control exists.

Where helpful, the reason for disabled/unavailable should be discoverable.

## 11. Loading

A loading button MUST communicate:
**the requested operation is actually in progress.**

It MUST NOT merely spin because a designer wants motion.

Loading must protect against accidental repeat execution when appropriate.

## 12. Success and error

Success may illuminate briefly when actual success is observed.

Error must be:
- readable;
- specific enough to act on;
- visually distinct;
- persistent enough to notice when material.

Do not replace truth with a generic “Done” toast.

## 13. Typography

Button labels must be readable.

MUST NOT:
- depend on tiny text;
- use decorative typefaces that reduce scan speed;
- use low-contrast accent text for long labels;
- hide the action through excessive all-caps tracking.

## 14. Icon + label law

For major navigation and actions:
**icon supports label; icon does not replace meaning unless universally understood and documented.**

Icons must belong to the same NayaNET icon family.

Emoji MAY be used in human-authored content but SHOULD NOT be the canonical production icon for a system action.

## 15. Sizing

Primary buttons should have generous touch/click targets.

Spacing around labels and icons must support:
- mouse;
- keyboard;
- touch;
- visual scanning.

Do not optimize for the smallest possible button footprint.

## 16. Placement

A button's position communicates priority.

Primary action:
- easy to find;
- visually dominant within its local context;
- not competing with unrelated actions.

Destructive or consequential actions:
- visually distinct;
- never disguised as ordinary navigation;
- confirmation/authority requirements shown where applicable.

## 17. Causal path

Every button MUST be mapped to:

**CONTROL → INTENT → AUTHORITY/SCOPE → CAPABILITY → OBSERVATION → STATE → EVIDENCE WHERE REQUIRED**

A static prototype control may be shown only when its non-live status is explicit.

## 18. No button soup

Do not give every action equal visual weight.

Use:
**primary / secondary / tertiary / contextual**

A button hierarchy is an information hierarchy.

## 19. Motion discipline

Motion SHOULD be fast, smooth and restrained.

Preferred signature from the existing Hub:
**0.22s cubic-bezier(.16,.84,.22,1)**

This is a reference, not permission to animate everything.

Respect reduced-motion settings.

## 20. Button 10/10 gate

A button is accepted only when:

- identity is clear;
- purpose is clear;
- readability is excellent;
- affordance is truthful;
- base state works;
- hover works where applicable;
- press works where applicable;
- active state works;
- focus works;
- disabled works;
- loading works where applicable;
- success/error behavior is defined;
- action is causally real;
- semantics are accessible;
- motion is restrained;
- visual treatment does not harm clarity.

**Primo means premium in perception AND truthful in behavior.**
